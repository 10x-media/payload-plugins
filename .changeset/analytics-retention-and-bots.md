Everything the native engine stores has an end, and automated traffic does not count.

**Behavioral:** crawlers, link-preview fetchers, monitors and headless clients are dropped at ingest by default, decided from the request's `user-agent` before the body is read. A dropped beacon answers exactly what a kept one answers, `202` with `{ ok: true }` and the same headers, and a recognized marker logs nothing at all: automated traffic is expected on a public endpoint rather than a misconfiguration to report. An empty or absent agent counts as automated, since every real browser sends one. Native numbers therefore fall on upgrade, to what real visitors did, with the `other` bucket of the `browser` breakdown dropping the most; nothing is backfilled, so a range spanning the upgrade mixes filtered days with unfiltered ones. `trackServerEvent` writes through its own path and is never filtered, whatever agent it attributes the event to.

**Behavioral:** the nightly prune task (`analytics-prune-events`) is registered only on an install that sets `retentionDays` or the new `rollupRetentionDays`, and it sweeps the daily visitor salts as well as the collections whenever it runs. An install that sets neither registers no task, so it gains no jobs config it did not ask for. Setting a window on an install that had no tasks or workflows at all does give it Payload's `payload-jobs` collection and, for a scheduled task, the `payload-jobs-stats` global: push-mode installs pick the tables up on the next boot, and a migrate-mode Postgres install creates them in a migration, the same as for any other new collection. That was already true of `retentionDays` before this release and is unchanged by it.

**Additive:** `native({ rollupRetentionDays })` deletes rollup rows whose `period` is older than the window. Off by default, because rollups are the long-term store and an unfiltered day-granularity read is served from them alone. It takes a whole number of days above zero, requires `retentionDays`, and may not be shorter than it; both rules fail the boot rather than the sweep. Pruning rollups while keeping raw events forever would make an unfiltered long window answer less than the same window filtered, and a shorter rollup window would make a two-year report show less than a three-month one. Once a rollup row is pruned, the day it covered reports nothing rather than falling back to raw events. `retentionDays` itself is unchanged, including that zero or less still means keep everything.

**Additive:** `native({ filterBots })` takes `false` to count every beacon, or a `(ua: string) => boolean` predicate that replaces the built-in rule rather than extending it. A predicate that throws keeps the event and warns once per process, naming `filterBots`: a broken filter must not discard a site's traffic, and it must not do it in silence either.

**Additive:** a beacon that arrives with no user agent at all is dropped like any other automated traffic, and warns once per process that an intermediary may be stripping the header. A proxy that strips it would otherwise take an install's numbers to zero with nothing in the log to look at, while a recognized marker stays silent.

**Additive:** `isBot` and the `BotFilter` type are exported from `@10x-media/analytics/adapters/native`, so the same rule can run in an install's own middleware or edge config, or be composed with a filter of its own. It matches a small hand-held set of lowercase substrings anywhere in the agent, covering crawlers, link-preview fetchers, monitors and audits, headless and automation drivers, and the default agents of HTTP libraries; the docs table lists the families, and the set itself is deliberately not exported. There is no third-party list and no new dependency. Matching mid-word is what makes `bot` cover `Googlebot` and `AhrefsBot` without an entry each, so `Cubot` handset models are stripped from the agent before the scan and a Cubot phone stays a visitor.

**Fixed:** the daily visitor salts in `payload.kv` accumulated forever, one key per UTC day, with nothing ever deleting one. A first event of a new UTC day now deletes the seven days before the two most recent, at ingest, fire and forget, so no install needs a jobs runner to stop them piling up; the nightly task sweeps the days 2 to 62 back when it runs. Today's and yesterday's are always kept, since an event arriving just before midnight is still hashed with yesterday's. Keys are deleted by computed name rather than by listing them, so a sweep costs no scan, works on every kv adapter, and a day already gone is a no-op. An install down for longer than 62 days keeps the salts older than that, inert and one small value per day.

**Fixed:** the prune loaded every document it deleted. Deletes now go through the database adapter's bulk delete, so nothing is read in order to be removed, whatever the window matches. The task's output is consequently `{}` rather than `{ deleted: number }`: a count would cost exactly the read the bulk delete avoids. Collection hooks and access control are bypassed by a database-level delete, and the three collections involved use neither.
