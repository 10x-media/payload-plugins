Everything the native engine stores has an end, and automated traffic does not count.

**Behavioral:** crawlers, link-preview fetchers, monitors and headless clients are dropped at ingest by default, decided from the request's `user-agent` before the body is read. A dropped beacon answers exactly what a kept one answers, `202` with `{ ok: true }` and the same headers, and logs nothing at all, not even once per process: automated traffic is expected on a public endpoint rather than a misconfiguration to report. An empty or absent agent counts as automated, since every real browser sends one. Native numbers therefore fall on upgrade, to what real visitors did, with the `other` bucket of the `browser` breakdown dropping the most; nothing is backfilled, so a range spanning the upgrade mixes filtered days with unfiltered ones. `trackServerEvent` writes through its own path and is never filtered, whatever agent it attributes the event to.

**Breaking:** the nightly prune task (`analytics-prune-events`) registers on every native install, not only on one with `retentionDays` set, because the daily visitor salts accumulate either way. An install that had no Payload tasks or workflows at all now has a jobs collection: Payload registers `payload-jobs` as soon as one task exists, and the `payload-jobs-stats` global as soon as one carries a schedule. Push-mode installs pick the tables up on the next boot. **A migrate-mode Postgres install must create them in a migration**, the same as for any other new collection, before the runner can write a job row. Nothing is deleted on an install that sets no window: without `retentionDays` and without `rollupRetentionDays` the task sweeps only the salts.

**Additive:** `native({ rollupRetentionDays })` deletes rollup rows whose `period` is older than the window. Off by default, because rollups are the long-term store and an unfiltered day-granularity read is served from them alone. It takes a whole number of days above zero and may not be shorter than `retentionDays`, which fails the boot rather than the sweep: a range reaching past raw-event retention is answered from rollups, so a shorter rollup window would make a two-year report show less than a three-month one. Once a rollup row is pruned, the day it covered reports nothing rather than falling back to raw events. `retentionDays` itself is unchanged, including that zero or less still means keep everything.

**Additive:** `native({ filterBots })` takes `false` to count every beacon, or a `(ua: string) => boolean` predicate that replaces the built-in rule rather than extending it. A predicate that throws keeps the event: a broken filter must not discard a site's traffic in silence.

**Additive:** `isBot`, `BOT_MARKERS` and the `BotFilter` type are exported from `@10x-media/analytics/adapters/native`, so the same rule can run in an install's own middleware or edge config, or be composed with a filter of its own. `BOT_MARKERS` is a small hand-held set of lowercase substrings matched anywhere in the agent, covering crawlers, link-preview fetchers, monitors and audits, headless and automation drivers, and the default agents of HTTP libraries. There is no third-party list and no new dependency. Matching mid-word is what makes `bot` cover `Googlebot` and `AhrefsBot` without an entry each, so `Cubot` handset models are stripped from the agent before the scan and a Cubot phone stays a visitor.

**Fixed:** the daily visitor salts in `payload.kv` accumulated forever, one key per UTC day, with nothing ever deleting one. The nightly task now sweeps the days 2 to 62 before today, leaving today's and yesterday's, since an event arriving just before midnight is still hashed with yesterday's. Keys are deleted by computed name rather than by listing them, so the sweep costs no scan, works on every kv adapter, and a day already gone is a no-op.

**Fixed:** the prune loaded every document it deleted. Deletes now go through the database adapter's bulk delete, so nothing is read in order to be removed, whatever the window matches. The task's output is consequently `{}` rather than `{ deleted: number }`: a count would cost exactly the read the bulk delete avoids. Collection hooks and access control are bypassed by a database-level delete, and the three collections involved use neither.
