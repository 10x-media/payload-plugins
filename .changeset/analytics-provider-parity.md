**Additive: comparison for every source.** Period-over-period comparison used to be a capability only the native and memory adapters declared. The previous-window read is done by the engine and works the same against any source, so it is now on for every adapter unless one sets `capabilities.comparison: false`; the four providers no longer opt out, and `comparison` is optional on `AnalyticsCapabilities` for adapters of your own (the serialized form the pickers read still carries a boolean). The compare toggle, the widgets' compare checkbox and `compare=previous` on the query endpoint therefore work on Plausible, GA4, Umami and PostHog. A source with `maxLookbackDays` cannot answer a previous window that starts before its lookback, measured from today: the view hides the toggle for such a window, the widgets and display fields omit the delta, and the endpoint answers the read without `comparison` instead of failing it. A far-past absolute range on such a source is still served (the engine clamps against the read's own end) but loses its comparison.

**Additive: the filter operators each provider API supports.** Plausible applies `eq`, `contains` and `matches` on every dimension it filters by (`is`, `contains`, `matches` in its Stats API v2 grammar, re2 full match). GA4 applies the same three through `stringFilter` (`EXACT`, `CONTAINS`, `FULL_REGEXP`), with exact and regex matches case-sensitive and `contains` case-insensitive like native and Umami. Umami now targets Umami 3.x: fifteen filterable dimensions (`page`, `referrer`, `browser`, `os`, `device`, `country`, `region`, `city`, `language`, `event` and the five `utm*`) with `eq`, `contains` and `matches` written as the API's `eq.`, `c.` and `re.` value prefixes, so `contains` is a case-insensitive substring and `matches` a case-insensitive partial regex there. Regex stays provider-only; native offers `eq` and `contains`. Umami accepts one value per query parameter, so two `eq` filters on one dimension with different values answer an empty result without a request, any other collision keeps the first filter (a per-page read keeps its page), an `eq` value carrying a comma is left out entirely because Umami reads such a value as a list and offers no escape, and what was not applied is reported in a new `meta.unappliedFilters` on the result.

**Behavioral (Umami):** the page breakdown asks `/metrics?type=path`; `type=url` was the 2.x name and Umami 3.x rejects it. Umami's breakdown rows report distinct sessions, so every breakdown row now carries `visitors` rather than a number labelled with whatever metric was asked for, and the view's breakdown charts the first metric the rows do carry when the selected one is absent. `event` is filterable but no longer groupable on Umami, since the install-wide `events` metric has no source in `/stats`.

**Additive: goals and conversions on every provider.** `conversions` and the `goal` dimension are served by Plausible (`event:goal`, conversions from `events` on goal rows, revenue from `total_revenue`), GA4 (`eventName` with `keyEvents`), PostHog (`event` with `count()`) and Umami (`/metrics?type=event`). A provider does not know which of its events are this install's goals, so reads that ask about goals carry the scope's goal slugs as `AnalyticsQuery.goalSlugs`, set by the query endpoint, the widgets and the display fields, and partitioning the cache. The slug of a goal must equal the provider's own name for it: the goal's display name on Plausible, the event name on PostHog and Umami, and on GA4 the slug normalized to a valid GA4 event name (hyphens become underscores, other characters outside letters, digits and underscores are dropped, a name not starting with a letter gains an `e_` prefix, 40 characters at most), which is also the name the GA4 sink sends; that normalization is exported as `ga4EventName` from `@10x-media/analytics/adapters/ga4`, so a host that dispatches its own gtag events can send the name the adapter reads back. A goal read with no goals in scope, or whose goal request the provider rejected, keeps its site numbers and reports `meta.goalsUnresolved`. A rejected goal request is cached for the source's realtime TTL rather than its aggregate one, so a transient provider failure does not pin "no conversions" for an hour, and every goal surface (the view's goals panel and goal breakdown, the goals widget, the goals breakdown widget) renders an empty state that says the goals could not be read instead of the plain no-data one. A filter the source could not carry raises a notice of its own on the view and on the metric, trend and breakdown widgets. When conversions ride along with site metrics, Plausible and GA4 issue a second, goal-filtered request and merge it per row, so such a read costs up to two provider requests; the second one runs after the first, inside the same limiter permit. GA4's `keyEvents` counts only events the property marks as key events. Umami serves conversions as goal rows and a range total only, so a conversions trend there shows no data, and the view's trend renders its empty state rather than a flat line of zeros. The goals widget and the goals tab now register for every provider.

**Behavioral (providers):** `conversions` on a provider means completions of this install's goals, as it does on native, rather than GA4's unfiltered key-event count. An install with no goals configured reads no conversions from a provider.

**Additive: Plausible `revenueCurrency`.** Plausible's `total_revenue` requires a revenue goal, so the adapter now declares `revenue` only when `revenueCurrency` (the ISO code of the site's revenue goals) is set, in config or on the provider document, and requests it only inside a goal-filtered request. Before, any read asking for revenue sent `total_revenue` unfiltered, which the API rejects.

**Additive: GA4 capture.** Set `measurementId` on the adapter or the provider document and the GA4 source fills a capture slot: the gtag tag loads from Google's own domain (no first-party proxy; the descriptor declares no routes), `gtag('config')` sends the first page view and history-change page views come from the web data stream's enhanced measurement (on by default, and the sink does not forward pageviews so it never double counts; an install that turns that stream option off should turn it back on), and the tracker forwards events and goals with `gtag('event', name, params)`. Consent is required by default, so the tag is not in the HTML before consent and is injected by the tracker once granted. The measurement id must match `^[A-Za-z0-9-]+$`; the provider document validates it and the adapter fills no slot otherwise. The tracker's own `file_download` auto-capture overlaps with enhanced measurement's, so downloads count twice on a GA4 slot unless one side is turned off. The sink is exported as `createGa4Sink` from `@10x-media/analytics/tracker`, beside the other vendor sinks. **Behavioral:** `CaptureClientKind` gains `'ga4'`, so an exhaustive `switch` over it in consumer code needs a new arm.

**Behavioral (PostHog):** the query's time bounds are sent as `toDateTime('...', 'UTC')`. HogQL reads a bare literal in the project's timezone, so a project set to anything but UTC was reading a window shifted by its offset; buckets are still cut in the reporting timezone.

**Fixed: two attacker-keyed lookups answer through the prototype.** `extractUtm` matched a page's query keys against an object literal, so `?constructor=x` or `?__proto__=x` resolved an inherited member and wrote a key `UtmParams` does not declare into the event row. The medium table the new `source` classifier reads is keyed by `utm_medium`, which is attacker-written in the same way, and an object literal there would have put a function in the `source` column, which a Postgres batch write rejects outright. Both lookups are `Map`s now, which answer nothing for a prototype name and make the return type honest; the view's channel-label table is guarded by a type predicate for the same reason.

**Breaking (native installs): `source` is a traffic channel.** The native `source` dimension buckets each pageview into `direct`, `search`, `social`, `email`, `paid` or `referral`, classified at ingest from `utm_medium` first, then paid click ids in the query (`gclid`, `fbclid`, `msclkid`, `ttclid`), then the referrer host against a small built-in list of search engines and social networks (a brand's country sites count, `google.co.uk` and `google.de`, while a host that merely contains the brand, `google.evil.com`, does not); no referrer or a same-site referrer is `direct`, any other host `referral`. Webmail hosts (`mail.google.com` and the like) count as `referral`, since a referrer cannot prove a newsletter. The `referrer` dimension keeps the host. The six channel values are stored as lowercase tokens and rendered through typed translations in the view and the widgets, so a Sources tab reads **Search** or **Direct** in the admin's locale while filters and links carry the token; they are exported as `TRAFFIC_CHANNELS` and the `TrafficChannel` type from `@10x-media/analytics/types`. Only a native row is named that way: a provider serves `source` as a raw `utm_source`, where a row reading `email` is the campaign parameter and not the Email channel, so those rows are shown as stored. Rows ingested before the upgrade keep the host values `source` used to store, and nothing is backfilled, so a Sources tab spanning the upgrade mixes the two until the old days age out of the window.
