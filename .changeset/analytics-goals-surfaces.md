"@10x-media/analytics": minor
---

**Additive: goal surfaces.** `goals.collection` (`true`, or `{ enabled, slug, scopeField, access, overrides }`) enables an `analytics-goals` collection scoped exactly like providers: rows filter by the request's resolved scope, `scope` is stamped on write and a forged one is refused, platform admins read every scope, and slugs are unique per scope, checked on every write and backed by a unique index on `slug` for an unscoped install or on `(slug, scope)` once a `scopeResolver` is configured and the plugin owns the scope field. Two cases stay hook-guarded only: install-wide rows on a scoped Postgres install (Postgres treats a NULL scope as distinct), and a host-owned `scopeField`, which the plugin does not index. Enabled collection goals merge over config goals by slug, cached for 30 seconds per scope and invalidated on change (one read serves at most 500 enabled goals per scope), and reach the native ingest, the browser tracker config and the new `GET /api/analytics/goals` endpoint (authenticated, per scope, `{ goals: [{ slug, name, source }], collection }`).

`goalField()` is a field factory that stores a goal slug behind a picker of the request's goals, with `goalSlug()` for renderers; the picker follows native field rules (`admin.condition`, `admin.width`, `admin.description`, `admin.placeholder`), and it, `SourceSelectField` and `MetricSelectField` now resolve their path through Payload's field context, so all three behave inside blocks and array rows. `@10x-media/analytics/client` gains `GoalSelectField` and `useAnalyticsGoals` plus the `GoalsResponse` and `WireGoal` wire types, and `GoalFieldOptions` is exported from both the root and `/types`.

`trackServerEvent(payload, event, { req, flush })` records a pageview, event or goal from server code through the native ingest (no HTTP round trip, same sanitizers and goal matching). With `req` the event inherits that request's headers, so geo, device and the visitor hash follow the real request; with neither a `req` nor an explicit `userAgent` it is attributed to a stable synthetic server visitor per day per hostname and reports no device at all rather than counting as desktop. `flush: true` awaits a buffered write. An explicit `scope` is ignored on an unscoped install and is never validated against the scopes that exist. A missing required field rejects with `AnalyticsTrackError` naming the field, and nothing is written. Needs the native adapter.

`trackGoalAction({ hostname, path, scope })` returns a form-builder action definition (type `analyticsGoal`, exported as `GOAL_ACTION_TYPE`) with no form-builder dependency; register it as `actions: { [GOAL_ACTION_TYPE]: trackGoalAction({ hostname: 'example.com' }) }`. Treat `hostname` as required wherever a jobs runner queues actions, and `scope` as required there on a scoped install: a queued run carries the runner's request rather than the submitter's, so the fallback chain (option, request host, `serverURL` host, then throw) has nothing useful to fall back to. The action is not `essential`, so a failed write never fails the submission.

**Breaking (scoped installs on a custom scope field):** where `providers.collection.scopeField` or `goals.collection.scopeField` names a field the plugin does not own, the plugin no longer adds its own hidden `scope` text field to that collection, since shadowing the host's field stored the scope twice. Generated types change accordingly, and a scoped Postgres install on a custom `scopeField` wants a migration dropping the now-unused `scope` column. Boot also fails with a named error when the collection carries no field of that name (`analytics: goals.collection.scopeField "tenant" does not exist on analytics-goals; register the collection with your tenant plugin or use the default scope field`), where the same misconfiguration previously booted and misbehaved silently.

**Behavioral:** `resolveGoals` on the adapter register context and on the runtime resolves per scope once the collection is enabled, and a collection goal replaces the config goal of the same slug. The public tracker config, which was a snapshot of the config goals, now carries the request scope's merged goals, still trimmed to `slug`, `match`, `value` and `currency`, so an editor's fixed value and currency reach `trackGoal()` defaults and vendor sinks; a change reaches browsers within the 30 second resolver cache plus that endpoint's own `Cache-Control: private, max-age=60`. `AnalyticsAdapter.ingest` gains an optional `track`.

**Consumer steps:** regenerate the admin import map (`payload generate:importmap`) once a `goalField()` is in the config, so `GoalSelectField` resolves. On Postgres, enabling `goals.collection` adds a table: run `payload migrate:create` in the app afterwards, which generates the DDL from the collection config the way every other schema change in this plugin does.

Multi-tenant note: the goals collection uses the plugin's own `scope` field and the plugin's scope resolver. Registering it with `@payloadcms/plugin-multi-tenant` (a `tenant` relationship through `scopeField` plus an entry in that plugin's `collections`) is not supported yet: it hangs a tenant user's admin panel in the dev app and the cause is not diagnosed. Providers still support that wiring (`isGlobal: true`). Goals scope correctly either way (access, stamping, per-scope uniqueness, the picker, the tracker config and the endpoint all follow the resolved scope); what a multi-tenant install gives up today is the tenant selector filtering the goals list view. A fix is planned.
