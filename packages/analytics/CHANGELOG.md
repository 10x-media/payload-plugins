# @10x-media/analytics

## 1.0.0-beta.10

### Minor Changes

- **Additive: a configuration change invalidates that scope's cached reads.** Correcting a provider document, or adding or editing a goal, used to leave every cached read in place until its TTL ran out, up to an hour on most sources, because only the in-process lookup maps were cleared. Every cache key now carries a per-scope cache epoch, an opaque token kept in `payload.kv`. Saving or deleting a provider document or a goal document bumps the epoch of the scope it belongs to, and of the scope it left when a document moves between scopes, so the next read of that scope misses and asks the source again. Old entries are not deleted; they expire by TTL under keys no read asks for. An instance reads a scope's token at most once every ten seconds, so a change made on one instance reaches the others within ten seconds. A token that cannot be read falls back to `0` with a warning logged once per process, not once per incident, and never fails an analytics read; for that ten second window the instance may serve entries written before the bump it could not see. A bump that fails, or has not settled after two seconds, is logged and dropped rather than failing the save that triggered it; a save that moved a document between scopes bumps both of them under that one two second deadline.

  **Additive: `POST /api/analytics/refresh` and a Refresh button.** The endpoint bumps one scope's epoch and answers `{ "epoch": "<token>" }`. It takes the same authentication and `access.read` as the read endpoints, and decides scope through the same code the query endpoint reads with, so it refuses every request that endpoint refuses: only a platform reader may name a `scope` in the JSON body, and on a scoped install a request that resolves no scope at all is refused too, both with `400 untrusted_scope`. `scope: "*"` bumps the install-wide epoch, which is what a cross-scope read's entries key on; a tenant's reads key on that tenant's own epoch and are not refreshed by it. A body over 4 KiB answers `413 payload_too_large`. **Breaking for exhaustive switches:** `QueryErrorCode`, exported from `@10x-media/analytics/types`, gains `payload_too_large`, so a `switch` over it with a `never` default needs a new arm. One instance bumps a given scope at most once every five seconds for this endpoint, answering the token already in force inside that window, so a looped call cannot turn a scope's cached reads into provider calls over and over; the document hooks are never debounced. The endpoint is state-changing and cookie-authenticated, so configure Payload's `csrf` allowlist on any install that exposes it. The analytics view's toolbar gains a **Refresh** button that calls it and reissues the cards, trend, breakdown and goals sections; the realtime strip and already-rendered dashboard widgets pick the bump up on their own next read. `refreshCache(apiRoute, { scope, signal })` is exported from `@10x-media/analytics/client` beside `fetchQuery`, with `RefreshRequest` and `RefreshResponse` in `@10x-media/analytics/types`.

  **Behavioral: the cache key format changed.** Every key now carries the epoch as its second segment, so entries written by the previous release are never read again and every read misses once after the upgrade. Nothing needs to be cleared by hand, and the orphaned entries expire on their own.

- **Breaking (contract): `channel` is a new dimension.** `DIMENSION_KEYS` gains `channel`, right after `source`. Code holding an exhaustive `Record<DimensionKey, ...>` needs the new key. `source` and `channel` now mean the same two things on every adapter that serves them: `source` is the visit's named origin (the `utm_source` tag when there is one, otherwise the referrer), and `channel` is the classification of that origin into an acquisition channel, in each source's own vocabulary. `TRAFFIC_CHANNELS` and `TrafficChannel`, exported from `@10x-media/analytics/types`, go from six tokens to twelve, so an exhaustive `Record<TrafficChannel, ...>` needs the new members.

  **Breaking (native installs): `source` stores the named origin again, and `channel` stores the classification.** The previous release stored one of six channel tokens in `source`. Native now stores `utm_source` lowercased, else the referring host, else the token `direct` in `source`, and one of twelve tokens in the new `channel` column: `direct`, `organic-search`, `paid-search`, `organic-social`, `paid-social`, `organic-video`, `paid-video`, `email`, `affiliate`, `display`, `referral`, `paid-other`. A paid visit is one whose `utm_medium` is `cpc`, `ppc` or starts with `paid`, or whose query carries a Google Ads, Microsoft Ads or TikTok Ads click id (`gclid`, `gbraid`, `wbraid`, `msclkid`, `ttclid`); the platform comes from the referrer host, from `utm_source` by name when there is no referrer host at all, and on the paid path from `utm_source` too when the host names no platform, so an ad click arriving through a network's redirect host keeps its platform. `utm_medium` values `email`, `newsletter`, `affiliate`, `affiliates`, `display`, `banner`, `cpm`, `retargeting`, `remarketing`, `social`, `social-media`, `sm`, `organic` and `search` classify directly. Events also carry `channelVersion`, the version of the rules that classified them, so a later reclassification can find rows written under older rules. The events collection gains the `channel` and `channel_version` columns: Postgres migrate-mode installs add them with the updated snippet in the native docs; Mongo and push-mode installs need nothing. Nothing is backfilled, so rows written by the previous release keep the token they stored in `source`. The `channelSearch`, `channelSocial` and `channelPaid` translation keys are gone, replaced by `channelOrganicSearch` / `channelPaidSearch`, `channelOrganicSocial` / `channelPaidSocial` and `channelPaidOther`; an override of a removed key fails to compile. Because `source` now holds lowercased `utm_source` values (capped at 128 characters), its rollup rows grow with the number of distinct values an install's traffic carries, one row per value per hostname family, where the old six-token set bounded them.

  **Fixed: `fbclid` no longer reads as paid.** Facebook appends `fbclid` to every outbound link, organic posts included, so the previous release overcounted paid traffic. It is now a social signal only: with no referrer host, and when no `utm_source` names a platform either, it names the social platform inside whichever of the paid or organic branches the other signals chose, so a visit carrying nothing but `fbclid` is organic social.

  **Fixed: a row with no value reads "Not set" and offers no filter.** A source can answer a row with no value for the dimension it was grouped by, PostHog's empty `$channel_type` for a pageview captured outside a session among them. The bar carried no label, and clicking it built an `eq ''` filter the query endpoint rejects, since a filter value is one character at minimum. Such a row now renders the new translated `valueNotSet` key on every dimension and every source, and is inert in the view's breakdowns while the rows beside it keep their click.

  **Additive: providers serve `channel` too.** Plausible maps it to `visit:channel`, GA4 to `sessionDefaultChannelGroup`, PostHog to the session's `$channel_type`, and Umami to `/metrics?type=channel`. Each returns its own channel names, rendered as they arrive; native's tokens render through twelve typed `channel*` translations. `channel` is filterable on native, Plausible, GA4 and PostHog, and groupable only on Umami, whose API takes no channel filter.

  **Behavioral: the Sources tab opens on channels.** The tab's dimensions now lead with `channel`, then `source`, then `referrer` and the campaign keys, so it opens on the channel overview wherever the source serves one; the named origin and the referring host are one pick away in **Group by**. PostHog gains a Sources tab, which it did not have before. An existing link naming `tab=sources` opens on channels unless it also carries `dim`.

  **Additive: a channels widget.** `analytics-breakdown-channels` ranks channels on the dashboard, opening on visitors, and links into the Sources tab; `analyticsDefaultWidgets()` places it after the sources card. The sources widget keeps ranking `source`.

- **Breaking (wire): every endpoint answers errors in one envelope.** The query and refresh endpoints answered `{ "error": { "code", "message", "param"? } }`. The document, sources, goals and native ingest endpoints answered a bare string, `{ "error": "forbidden" }`, and the realtime endpoint answered one shape or the other depending on which failure it hit. All of them now answer the envelope, over one typed code vocabulary. Code that read `error` as a string from any of those endpoints reads `error.code` and `error.message` instead. Status codes are unchanged except on the document endpoint, and no success body changed. The capture proxy stays bodyless and is the one endpoint that sends no envelope: it relays a vendor SDK's own traffic, and that SDK, not admin code, reads the answer.

  **Breaking (types): the code union gains `not_found`.** It is what the document endpoint answers for a document that is not there or not this caller's to read. `QueryErrorCode` is now an alias of the plugin-wide `AnalyticsErrorCode`, so an exhaustive `switch` over either name stops compiling until it handles the new member. Treat an unrecognized code as a generic failure of its status: the union is open to additions.

  **Behavioral: the document endpoint no longer hides a broken install as a `404`.** Its catch-all answered `404` for every failure while reading a document. A document that does not exist, one this caller may not read, an unbound collection and a missing `id` are all still a uniform `404 not_found`, so analytics never confirm a document exists; `findByID` failing for any other reason is now a logged `500 internal`.

  **Behavioral: two answers changed their headers.** The goals endpoint sends `cache-control: private, no-store` on every answer, successful listings included, like every other scope-dependent endpoint whose answer is not cached at all. The document endpoint's `503` now carries `Retry-After: 30`, matching the query endpoint on the same condition. Native ingest refusals carry `no-store` as well, which is harmless on a public endpoint and keeps one builder for every error. The tracker config endpoint is deliberately untouched: it has no failure path to convert, and it keeps `private, max-age=60` with `Vary: Host, Cookie`, the one scope-dependent answer that is cached at all.

  **Behavioral: the realtime counter stops polling on a refusal aimed at the reader.** A `401 unauthorized` or a `403 forbidden` ends the interval, since no later tick talks its way out of either. An outage, an unreadable body and a body from an older server all keep polling. The counter shows the paused label it always did, so there is no new state and no new string.

  **Behavioral: `QueryFetchError.error` is undefined for a code this release does not know.** `fetchQuery` and `refreshCache` read the envelope through the same reader the rest of the package uses, so a body carrying a code a newer server added is reported as a generic failure of its status rather than typed as a `QueryErrorCode` it is not. `status` and `retryAfter` are unchanged, and `error` is still set for every code this release defines.

  **Additive: refusals name the field at fault.** Native ingest puts the first field an event failed on in `param`, checked as `type`, `path`, `hostname`, `name`; unparseable JSON names `type`, and a body that died in transit names nothing. The document endpoint names the custom range bound at fault, `from` or `to`, where it answered `{ "error": "invalid range" }` with nothing to branch on; an inverted window blames `to`.

  **Additive: `AnalyticsErrorCode`, `AnalyticsError`, `ANALYTICS_ERROR_CODES`, `analyticsError`, `readErrorCode` and `readResponseError`.** `readErrorCode(body)` answers the code of an envelope body and `undefined` for anything else, so admin code branches on a failed answer without parsing it by hand; it is exported from `@10x-media/analytics/client` and `@10x-media/analytics/types`, which both also export the `AnalyticsError` and `AnalyticsErrorCode` types. `readResponseError(res)` is the same read over a `Response` nothing has parsed yet, answering the whole error and `undefined` for a body that is not JSON, an empty and an already-consumed one included, rather than throwing; it is exported from `@10x-media/analytics/client`. `ANALYTICS_ERROR_CODES` is exported from `@10x-media/analytics/types` and the package root, and the builder `analyticsError` from the root. `QueryError` and `QueryErrorCode` stay exported under their own names as aliases.

- A native event is attributed to the request that carried it, not to the hostname its body claims.

  **Breaking:** the hostname a native event is stored under is now the host the request carried (the `x-forwarded-host` entry `n` from the right where `trustedProxyHops` is `n >= 1`, else `Host`), and the body's claim is ignored. The forwarded chain is counted from the trusted end exactly as `x-forwarded-for` is, because a proxy that appends rather than replaces leaves the client's own value at the head of it; a chain shorter than `n`, or an entry that is no hostname, falls back to `Host`, whose peer is the trusted proxy. `Origin` is never read: a scripted client can pair a valid `Host` with any `Origin` and mint unlimited hostname bucket families inside one scope, which is the hole this closes. An install whose beacons already post from the site they are counting sees no change, because the request's host is the page's host; an install whose tracker posts to a different host than the page runs on sees its stored hostname change, and should use the new `hostname` resolver form.

  **Breaking:** there is now one definition of a hostname, and config entries, the request host, a resolver's answer and a form goal action's host are all held to it. A value is lowercased and loses its port, its brackets and every trailing root dot, and must then be dot-separated labels of `a-z`, `0-9`, `_` and `-` (every IPv4 literal included) or an IPv6 literal of hex groups and colons, within 253 characters. `example.com.`, `example.com..` and `Example.COM:3000` are therefore one hostname rather than four bucket families, `[::1]:3000` is stored as `::1` rather than `[::1]`, and a name over 253 characters is refused instead of truncated into a name of its own. Anything else (a leading or doubled dot, an unclosed bracket, a percent-encoded or non-ASCII spelling, a non-numeric port, a scheme) drops the event.

  **Breaking:** on an install with a `scopeResolver`, an event whose request resolves no scope is dropped instead of being stored install-wide, unless its resolved hostname is listed in the native adapter's `platformHostnames`. A dropped event answers exactly what an accepted one answers, `202` with `{ ok: true }`, and nothing per event is logged, so the endpoint is no oracle for which hosts or tenants exist.

  **Behavioral:** the first drop of each reason writes one `warn` line, naming the `scopeResolver` or the `hostname` option to look at, and every later drop of that reason is silent for the life of the process. A public endpoint must not be a log amplifier, since an attacker would otherwise choose how much it writes, but a misconfigured resolver discarding all traffic should not be invisible either.

  **Breaking:** the ingest body's `hostname` is optional, and a body carrying one is only type-checked. A missing `hostname` no longer answers `400`; a non-string one still does. `trackServerEvent` is unaffected and still requires its own, since trusted server code has no request to attribute an event to.

  **Additive:** `native({ hostname })` takes `'request'` (the default), a list of hostnames (the request host is stored only when the list holds it, and this is the form to use on a single-site install with no `scopeResolver` and no edge validating `Host`), or an `EventHostnameResolver`, `({ claimed, req, scope }) => string | null`, that decides per event, where `null` drops it and a throw drops it too. It is named apart from the binding `HostnameResolver`, which names the hostname a document is read under. A resolver's answer must itself be a hostname: an id, a slug or a label drops the event rather than being stored as free text per event. List entries are validated at boot: a scheme or a port in an entry, or an empty list, fails the boot rather than silently dropping every event.

  **Additive:** `native({ platformHostnames })` names the platform's own domains on a scoped install, which ingest under the null scope rather than being dropped. The list is static on purpose: those domains change with a deploy, not with a signup. Tenant domains never belong in it, because a tenant's custom domain is tracked the moment its document is saved, through the install's own `scopeResolver`.

  **Additive:** `analytics({ trustedProxyHops })` sets how many proxies in front of the app are trusted, counted from the right of `x-forwarded-for`. It is plugin-level because one helper reads the client address for the native visitor hash, for geo, and for the capture proxy's upstream `X-Forwarded-For`. Unset keeps today's leftmost entry, which is correct for honest traffic and client-writable otherwise. At `n >= 1` the forwarded chain is the only source, and a chain shorter than `n` yields no address rather than falling back to the client-writable `x-real-ip`. There is no default of `1`: an install behind a CDN plus a proxy would then read the CDN's address for every visitor, collapsing geo and the visitor hash onto one value.

  **Additive:** `GeoResolver` gained an optional second argument carrying `trustedProxyHops`, so a resolver that does its own IP lookup reads the same address the rest of the pipeline does. `maxmindResolver` honors it. A one-argument resolver still type-checks and still runs. `GeoResolverOptions`, the type of that argument, is exported from `@10x-media/analytics/geo` beside `GeoResolver`.

  **Behavioral:** a binding's `hostname` is reduced to the bare lowercased host before it reaches an adapter query, so a tenant domain stored as `https://Example.com/` or with a port still matches the hostnames the native engine writes, which are compared exactly. A value that is no hostname at all reaches the adapter unchanged.

  **Breaking:** `trackGoalAction` no longer stores the submitting request's `Host` as given. It resolves the `hostname` option first, then that request under the native adapter's own `hostname` policy (so a forged host the ingest endpoint would refuse is refused here too), then the host of `serverURL`. The scoped-install drop rule does not apply, since a submission's scope comes from the form document. With none of the three (no `serverURL`, and a request with no usable host), the completion is not recorded at all: the action writes one `warn` line for the life of the process and returns, rather than throwing inside a submission it is not essential to. The policy is read off the very adapter the event would be written through, so one adapter cannot judge a hostname another one stores. `trackServerEvent` called directly by server code is unchanged: it is trusted, supplies its own hostname, and still requires one.

  **Additive:** an adapter's `ingest` seam may expose `hostname`, which applies that adapter's own hostname policy to a request. The native adapter provides it, and it is how the form goal action attributes exactly as the endpoint does.

  **Behavioral:** an existing single-site install sees the same hostname it saw before in the common same-origin case, since the request's host is the page's host there. The visitor hash and the same-site referral check both key off the resolved hostname rather than the claimed one, so a forged body no longer splits one visitor across hostname buckets. The salt, timezone and goal resolvers now run only for an event that will be kept.

  Rate limiting is deliberately not part of this. The plugin decides what one accepted request may write; how many requests are accepted belongs to the edge, where a per-IP limit can throttle an abuser instead of the whole install's traffic.

- Staff can take themselves out of the numbers with a link, and the docs say what a stored event holds.

  **Additive:** any page opened with `?analytics_exclude=1` takes that browser out of capture, and `=0` puts it back (`true` and `false` work too). The tracker reads the parameter on boot and leaves the URL alone. While the flag is set nothing is delivered to any sink, nothing is queued for a pending consent decision, and no vendor script is injected even after consent is granted; clearing resumes from that point and replays nothing that was skipped. The flag lives in `localStorage` under `analytics:exclude`, so it is per browser and per site, and a browser with storage blocked is excluded for the page the link was opened on and no further, without throwing.

  **Additive:** `exclusionParam` on `createTracker`/`initTracker` options, beside `persistConsent`. A string renames the parameter, `false` ignores it while still honouring a flag an earlier visit set. Default `analytics_exclude`.

  **Additive:** `tracker.exclude(next)` and the read-only `tracker.excluded` on the `Tracker` interface, `setExcluded` and `excluded` on `useAnalytics()`, and `EXCLUSION_STORAGE_KEY`, `DEFAULT_EXCLUSION_PARAM`, `readExclusion`, `writeExclusion`, `readExclusionParam` and `subscribeExclusion` from `@10x-media/analytics/tracker`, for a host rendering its own switch. `AnalyticsApi` gains the `excluded` flag and is now `AnalyticsCommands` (the imperative half, also exported from `@10x-media/analytics/react`) plus that flag; nothing was removed from it, and the React context itself is not part of the package's export surface.

  **Additive:** the vendor sinks expose their own opt-out through the optional `Sink.exclude`, with `PLAUSIBLE_IGNORE_KEY`, `UMAMI_DISABLED_KEY`, `GA4_DISABLE_PREFIX` and `Ga4SinkArgs` exported alongside them.

  **Behavioral:** a visitor who arrives with the parameter is excluded from then on in that browser, and the exclusion is mirrored into each vendor's own switch for the slots the config has: `plausible_ignore`, `umami.disabled`, PostHog's `opt_out_capturing()` and GA4's `ga-disable-<measurementId>`. A snippet the server rendered for a slot that does not require consent runs before the tracker boots, so that vendor's own page view for the page the link was opened on may already have been sent; Plausible, Umami and PostHog persist their switch and are silent from the next load. GA4's is a window property that does not persist and counts only ahead of the first `gtag()` call, so the rendered GA4 snippet reads `analytics:exclude` itself and sets the switch before its own `gtag('config', ...)`: the page the link is opened on may still be measured, and from the next page load on nothing is. A gated slot, which is GA4's default, never loads while the browser is excluded. A vendor key the tracker did not set is cleared only by an explicit `=0` or `exclude(false)`, so one a staff member set by hand survives an ordinary visit; an explicit clear does clear it, which is the cost of off meaning off.

  **Breaking (types only):** the exported `Tracker` type gains two required members, `excluded` and `exclude`. Code that implements `Tracker` itself, such as a test double or a wrapper, has to add them. The same holds for `AnalyticsApi`, the return type of `useAnalytics()`, which gains a required `excluded`: a hand-built value of that type, such as a mocked hook in a test, has to add it. Callers are unaffected.

  **Behavioral:** the tracker's built entry grows by about 6 KB unminified. It stays dependency-free.

  **Additive:** a Privacy page in the docs states, column by column, what a stored native event holds and where each value comes from, that no cookie is set and which `localStorage` keys exist, how the daily-salted visitor hash works and why two days cannot be joined once its salt is swept, that the client address is used for the hash and geo and stored nowhere, that the raw query string is read for the campaign keys and the ad click ids and then discarded, what a `path` or a prop the site authors can therefore carry, and what an access or erasure request can and cannot find. It states facts about the code and makes no legal claim. Capture documents the exclusion link beside it, including what a link carrying the parameter costs when anyone sends one to a real visitor.

- Everything the native engine stores has an end, and automated traffic does not count.

  **Behavioral:** crawlers, link-preview fetchers, monitors and headless clients are dropped at ingest by default, decided from the request's `user-agent` before the body is read. A dropped beacon answers exactly what a kept one answers, `202` with `{ ok: true }` and the same headers, and a recognized marker logs nothing at all: automated traffic is expected on a public endpoint rather than a misconfiguration to report. An empty or absent agent counts as automated, since every real browser sends one. Native numbers therefore fall on upgrade, to what real visitors did, with the `other` bucket of the `browser` breakdown dropping the most; nothing is backfilled, so a range spanning the upgrade mixes filtered days with unfiltered ones. `trackServerEvent` writes through its own path and is never filtered, whatever agent it attributes the event to.

  **Behavioral:** the nightly prune task (`analytics-prune-events`) is registered only on an install that sets `retentionDays` or the new `rollupRetentionDays`, and it sweeps the daily visitor salts as well as the collections whenever it runs. An install that sets neither registers no task, so it gains no jobs config it did not ask for. Setting a window on an install that had no tasks or workflows at all does give it Payload's `payload-jobs` collection and, for a scheduled task, the `payload-jobs-stats` global: push-mode installs pick the tables up on the next boot, and a migrate-mode Postgres install creates them in a migration, the same as for any other new collection. That was already true of `retentionDays` before this release and is unchanged by it.

  **Additive:** `native({ rollupRetentionDays })` deletes rollup rows whose `period` is older than the window. Off by default, because rollups are the long-term store and an unfiltered day-granularity read is served from them alone. It takes a whole number of days above zero, requires `retentionDays`, and may not be shorter than it; both rules fail the boot rather than the sweep. Pruning rollups while keeping raw events forever would make an unfiltered long window answer less than the same window filtered, and a shorter rollup window would make a two-year report show less than a three-month one. Once a rollup row is pruned, the day it covered reports nothing rather than falling back to raw events. `retentionDays` itself is otherwise unchanged, including that zero or less still means keep everything; a value above zero now goes through the same check as the rollup window, so a window that is not a whole number of days, `Infinity` among them, fails the boot rather than the first nightly run.

  **Additive:** `native({ filterBots })` takes `false` to count every beacon, or a `(ua: string) => boolean` predicate that replaces the built-in rule rather than extending it. A predicate that throws keeps the event and warns once per process, naming `filterBots`: a broken filter must not discard a site's traffic, and it must not do it in silence either.

  **Additive:** a beacon that arrives with no user agent at all is dropped like any other automated traffic, and warns once per process that an intermediary may be stripping the header. A proxy that strips it would otherwise take an install's numbers to zero with nothing in the log to look at, while a recognized marker stays silent.

  **Additive:** `isBot` and the `BotFilter` type are exported from `@10x-media/analytics/adapters/native`, so the same rule can run in an install's own middleware or edge config, or be composed with a filter of its own. It matches a small hand-held set of lowercase substrings anywhere in the agent, covering crawlers, link-preview fetchers, monitors and audits, headless and automation drivers, and the default agents of HTTP libraries; the docs table lists the families, and the set itself is deliberately not exported. There is no third-party list and no new dependency. Matching mid-word is what makes `bot` cover `Googlebot` and `AhrefsBot` without an entry each, so `Cubot` handset models are stripped from the agent before the scan and a Cubot phone stays a visitor.

  **Fixed:** the daily visitor salts in `payload.kv` accumulated forever, one key per UTC day, with nothing ever deleting one. A first event of a new UTC day now deletes the seven days before the two most recent, at ingest, fire and forget, so no install needs a jobs runner to stop them piling up; the nightly task sweeps the days 2 to 62 back when it runs. Today's and yesterday's are always kept, since an event arriving just before midnight is still hashed with yesterday's. Keys are deleted by computed name rather than by listing them, so a sweep costs no scan, works on every kv adapter, and a day already gone is a no-op. An install down for longer than 62 days keeps the salts older than that, inert and one small value per day.

  **Fixed:** the prune loaded every document it deleted. Deletes now go through the database adapter's bulk delete, so nothing is read in order to be removed, whatever the window matches. Collection hooks and access control are bypassed by a database-level delete, and the three collections involved use neither.

  **Behavioral:** the prune task's output is consequently `{}` rather than `{ deleted: number }`, a shape change for anyone reading a job result: a count would cost exactly the read the bulk delete avoids.

### Patch Changes

- **Fixed: scroll depth read from raw events no longer collapses on Postgres.** The raw-event path (an hourly series, and any filtered read that bypasses the rollups) counted one scroll sample per event whenever the driver returned an unreported depth as `null` rather than omitting the field, which Postgres does for every event that carried no depth. The average was then divided by every event in range instead of by the pageviews that actually reported a depth, so a site whose tracker reports depth on a fraction of its pageviews saw a scroll depth several times too low on Postgres while the rollup-backed reads of the same range showed the right number. Only a depth that is a number counts as a sample now, on both adapters, and a reported `0` still counts.

## 1.0.0-beta.9

### Minor Changes

- **Fixed: a failed goal resolver no longer poisons the healthy cache entry.** When the goals resolver threw, the read carried an empty goal hint, the provider answered `meta.goalsUnresolved`, and the engine cached that answer at the aggregate TTL under the same key a healthy read with no goals uses. The hint is now three-way: the scope's slugs (an empty list when no goals are configured, which is an empty result rather than a failure), `'unresolved'` when the resolver failed (its own `goals:!unresolved` cache segment, which no list of slugs can produce, and the short realtime TTL), or absent when the read does not ask about goals.

  **Behavioral for adapter authors: `AnalyticsQuery.goalSlugs` is typed `string[] | 'unresolved'`.** An adapter that reads the hint must handle the sentinel: the slugs to filter goal rows by, an empty list to filter by none, or a failure to report as `meta.goalsUnresolved` rather than as an empty table. The built-in provider adapters answer all three through one shared helper. `GET /api/analytics/query` echoes the hint it used under `query.goalSlugs`, so a client can tell a scope with no goals from a resolver that failed.

  **Fixed: a scope with no goals says so instead of reading as nobody converting.** The goals panel, the goals widget and both goal breakdowns fell through to the plain "No data yet" whenever the scope configured no goals. They now render `stateNoGoals` ("No goals are configured for this scope", in all 11 locales) for that case, keeping the unresolved-goals state for a source that could not answer at all.

  **Fixed: a sampled native read says so everywhere.** A filtered or hourly native read that hits the event scan limit sets `meta.sampled`; `realtime()` now sets it too (both paths build their meta through one `eventScanMeta`), and the view and the widgets show a notice for it beside the clamped and stale ones instead of presenting truncated numbers as exact. **Additive:** the realtime strip and the realtime widget carry the notice through their polls, and `RealtimeCounter` gained two optional props for it, `initialSampled` and `sampledLabel`, with no notice rendered when the label is left off.

A gate that throws is not retryable and answers 500 instead, since polling again cannot fix a configuration bug. - **Additive: native dimensions.** The native engine now serves `referrer`, `region`, `city`, `browser`, `os`, `language`, `utmSource`, `utmMedium`, `utmCampaign`, `utmContent` and `utmTerm` as breakdown dimensions, from the rollup and the filtered read paths alike, and all eleven are filterable with `eq` and `contains`. Native's `filters` set is now every dimension it serves except `goal`, whose completions live in a json column rather than a field a `where` can compare.

The panel now shows its skeleton until the read for the grouping on screen lands.

Stored referrers lose their query string and fragment and are capped at 512 characters (a same-origin referrer carries the previous page's whole URL, tokens included). Geo values (`country`, `region`, `city`) are capped at 128 characters. An ingest body whose `referrer` is not a string answers `202` and drops the field instead of failing with a `500`.

  **Storage:** rollup and seen-ledger rows grow with the cardinality of the new dimensions (referrer host, city, `utmContent`, `utmTerm`), plus one extra bucket set per distinct hostname you ingest from. `retentionDays` prunes events and the seen ledger only, never rollups, so plan storage for that tail.

- **Additive: comparison for every source.** Period-over-period comparison used to be a capability only the native and memory adapters declared. The previous-window read is done by the engine and works the same against any source, so it is now on for every adapter unless one sets `capabilities.comparison: false`; the four providers no longer opt out, and `comparison` is optional on `AnalyticsCapabilities` for adapters of your own (the serialized form the pickers read still carries a boolean). The compare toggle, the widgets' compare checkbox and `compare=previous` on the query endpoint therefore work on Plausible, GA4, Umami and PostHog. A source with `maxLookbackDays` cannot answer a previous window that starts before its lookback, measured from today: the view hides the toggle for such a window, the widgets and display fields omit the delta, and the endpoint answers the read without `comparison` instead of failing it. A far-past absolute range on such a source is still served (the engine clamps against the read's own end) but loses its comparison.

  **Additive: the filter operators each provider API supports.** Plausible applies `eq`, `contains` and `matches` on every dimension it filters by (`is`, `contains`, `matches` in its Stats API v2 grammar, re2 full match). GA4 applies the same three through `stringFilter` (`EXACT`, `CONTAINS`, `FULL_REGEXP`), with exact and regex matches case-sensitive and `contains` case-insensitive like native and Umami. Umami now targets Umami 3.x: fifteen filterable dimensions (`page`, `referrer`, `browser`, `os`, `device`, `country`, `region`, `city`, `language`, `event` and the five `utm*`) with `eq`, `contains` and `matches` written as the API's `eq.`, `c.` and `re.` value prefixes, so `contains` is a case-insensitive substring and `matches` a case-insensitive partial regex there. Regex stays provider-only; native offers `eq` and `contains`. Umami accepts one value per query parameter, so two `eq` filters on one dimension with different values answer an empty result without a request, any other collision keeps the first filter (a per-page read keeps its page), an `eq` value carrying a comma is left out entirely because Umami reads such a value as a list and offers no escape, and what was not applied is reported in a new `meta.unappliedFilters` on the result.

  **Behavioral (Umami):** the page breakdown asks `/metrics?type=path`; `type=url` was the 2.x name and Umami 3.x rejects it. Umami's breakdown rows report distinct sessions, so every breakdown row now carries `visitors` rather than a number labelled with whatever metric was asked for, and the view's breakdown charts the first metric the rows do carry when the selected one is absent. `event` is filterable but no longer groupable on Umami, since the install-wide `events` metric has no source in `/stats`.

  **Additive: goals and conversions on every provider.** `conversions` and the `goal` dimension are served by Plausible (`event:goal`, conversions from `events` on goal rows, revenue from `total_revenue`), GA4 (`eventName` with `keyEvents`), PostHog (`event` with `count()`) and Umami (`/metrics?type=event`). A provider does not know which of its events are this install's goals, so reads that ask about goals carry the scope's goal slugs as `AnalyticsQuery.goalSlugs`, set by the query endpoint, the widgets and the display fields, and partitioning the cache. The slug of a goal must equal the provider's own name for it: the goal's display name on Plausible, the event name on PostHog and Umami, and on GA4 the slug normalized to a valid GA4 event name (hyphens become underscores, other characters outside letters, digits and underscores are dropped, a name not starting with a letter gains an `e_` prefix, 40 characters at most), which is also the name the GA4 sink sends; that normalization is exported as `ga4EventName` from `@10x-media/analytics/adapters/ga4`, so a host that dispatches its own gtag events can send the name the adapter reads back. A goal read with no goals in scope, or whose goal request the provider rejected, keeps its site numbers and reports `meta.goalsUnresolved`. A rejected goal request is cached for the source's realtime TTL rather than its aggregate one, so a transient provider failure does not pin "no conversions" for an hour, and every goal surface (the view's goals panel and goal breakdown, the goals widget, the goals breakdown widget) renders an empty state that says the goals could not be read instead of the plain no-data one. A filter the source could not carry raises a notice of its own on the view and on the metric, trend and breakdown widgets. When conversions ride along with site metrics, Plausible and GA4 issue a second, goal-filtered request and merge it per row, so such a read costs up to two provider requests; the second one runs after the first, inside the same limiter permit. GA4's `keyEvents` counts only events the property marks as key events. Umami serves conversions as goal rows and a range total only, so a conversions trend there shows no data, and the view's trend renders its empty state rather than a flat line of zeros. The goals widget and the goals tab now register for every provider.

  **Behavioral (providers):** `conversions` on a provider means completions of this install's goals, as it does on native, rather than GA4's unfiltered key-event count. An install with no goals configured reads no conversions from a provider.

  **Additive: Plausible `revenueCurrency`.** Plausible's `total_revenue` requires a revenue goal, so the adapter now declares `revenue` only when `revenueCurrency` (the ISO code of the site's revenue goals) is set, in config or on the provider document, and requests it only inside a goal-filtered request. Before, any read asking for revenue sent `total_revenue` unfiltered, which the API rejects.

  **Additive: GA4 capture.** Set `measurementId` on the adapter or the provider document and the GA4 source fills a capture slot: the gtag tag loads from Google's own domain (no first-party proxy; the descriptor declares no routes), `gtag('config')` sends the first page view and history-change page views come from the web data stream's enhanced measurement (on by default, and the sink does not forward pageviews so it never double counts; an install that turns that stream option off should turn it back on), and the tracker forwards events and goals with `gtag('event', name, params)`. Consent is required by default, so the tag is not in the HTML before consent and is injected by the tracker once granted. The measurement id must match `^[A-Za-z0-9-]+$`; the provider document validates it and the adapter fills no slot otherwise. The tracker's own `file_download` auto-capture overlaps with enhanced measurement's, so downloads count twice on a GA4 slot unless one side is turned off. The sink is exported as `createGa4Sink` from `@10x-media/analytics/tracker`, beside the other vendor sinks. **Behavioral:** `CaptureClientKind` gains `'ga4'`, so an exhaustive `switch` over it in consumer code needs a new arm.

  **Behavioral (PostHog):** the query's time bounds are sent as `toDateTime('...', 'UTC')`. HogQL reads a bare literal in the project's timezone, so a project set to anything but UTC was reading a window shifted by its offset; buckets are still cut in the reporting timezone.

  **Fixed: two attacker-keyed lookups answer through the prototype.** `extractUtm` matched a page's query keys against an object literal, so `?constructor=x` or `?__proto__=x` resolved an inherited member and wrote a key `UtmParams` does not declare into the event row. The medium table the new `source` classifier reads is keyed by `utm_medium`, which is attacker-written in the same way, and an object literal there would have put a function in the `source` column, which a Postgres batch write rejects outright. Both lookups are `Map`s now, which answer nothing for a prototype name and make the return type honest; the view's channel-label table is guarded by a type predicate for the same reason.

  **Breaking (native installs): `source` is a traffic channel.** The native `source` dimension buckets each pageview into `direct`, `search`, `social`, `email`, `paid` or `referral`, classified at ingest from `utm_medium` first, then paid click ids in the query (`gclid`, `fbclid`, `msclkid`, `ttclid`), then the referrer host against a small built-in list of search engines and social networks (a brand's country sites count, `google.co.uk` and `google.de`, while a host that merely contains the brand, `google.evil.com`, does not); no referrer or a same-site referrer is `direct`, any other host `referral`. Webmail hosts (`mail.google.com` and the like) count as `referral`, since a referrer cannot prove a newsletter. The `referrer` dimension keeps the host. The six channel values are stored as lowercase tokens and rendered through typed translations in the view and the widgets, so a Sources tab reads **Search** or **Direct** in the admin's locale while filters and links carry the token; they are exported as `TRAFFIC_CHANNELS` and the `TrafficChannel` type from `@10x-media/analytics/types`. Only a native row is named that way: a provider serves `source` as a raw `utm_source`, where a row reading `email` is the campaign parameter and not the Email channel, so those rows are shown as stored. Rows ingested before the upgrade keep the host values `source` used to store, and nothing is backfilled, so a Sources tab spanning the upgrade mixes the two until the old days age out of the window.

- **Additive: widget filters.** Metric, trend and breakdown widgets take one optional filter (dimension, operator, value). The dimension is the gate, the operator defaults to `eq`, and the value is trimmed and capped at 256 characters; a dimension without a value fails validation rather than saving a filter that narrows nothing. The two pickers offer only what the widget's chosen data source declares as filterable, in contract order, falling back to the union over the request's sources when no source is chosen, and a stored value the current source no longer offers stays visible (clearable on the dimension, which is the gate; the operator always has a value). The read applies the filter, the caption states it ("Last 30 days where Country is DE"), and the "Open in Analytics" link carries it into the view as `filters=`. The caption's two halves are translated templates: the sentence is `widgetFilterCaption` (`'where {{dimension}} {{operator}} {{value}}'`) and the join that puts it after the window is its own key, `widgetCaptionWithFilter` (`'{{window}} {{filter}}'`), which `zh` ships without the space. Both are overridable through the `translations` option.

  A source that cannot apply the stored filter renders "This source cannot apply this filter" rather than silently ranking unfiltered rows: `readForWidget`, `readForWidgetBreakdown` and `readForWidgetSeries` answer `status: 'filter-unsupported'` without querying the adapter. Because the pickers offer the union when no source is chosen, a dimension filterable on one source and an operator declared on another can be configured together and answered this way at read time.

  **Breaking (types): `WidgetReadStatus` gains `'filter-unsupported'`.** The type is exported from `/rsc`, so an exhaustive `Record<Exclude<WidgetReadStatus, 'ok'>, T>` or a switch a consumer wrote over it stops compiling until the new member is handled. Runtime behavior of existing code is unaffected; the compiler is the thing that breaks.

  **Behavioral: a widget filter that the source cannot apply now reads `filter-unsupported` where it read `unavailable` before.** Code branching on `status === 'unavailable'` to render its own "no data" message will stop matching those reads.

  **Behavioral: a widget's caption renders only with the data it describes.** The breakdown widget used to render its range caption below a not-configured or unavailable message, captioning a window it had not read; it now returns title, message and link, as the metric and trend widgets already did.

  **Additive API.** `widgetFilters` and the `WidgetFilter` type are exported from the root entry, so a custom widget storing the built-in filter group turns it into an `AnalyticsFilter[]` under the same rules. `FilterDimensionSelectField`, `FilterOperatorSelectField`, `useFilterCapabilities` and the `AnalyticsSources` type are exported from `/client`; `FilterCapabilities` carries `resolved` alongside `loading` and `error`, and `useAnalyticsSources` reports `loading` and `error` beside `sources`. The server `Translate` type accepts interpolation vars. 15 new translation keys ship in all 11 locales.

## 1.0.0-beta.8

### Minor Changes

- **Additive: goal surfaces.** `goals.collection` (`true`, or `{ enabled, slug, scopeField, access, overrides }`) enables an `analytics-goals` collection scoped exactly like providers: rows filter by the request's resolved scope, `scope` is stamped on write and a forged one is refused, platform admins read every scope, and slugs are unique per scope, checked on every write and backed by a unique index on `slug` for an unscoped install or on `(slug, scope)` once a `scopeResolver` is configured and the plugin owns the scope field. Two cases stay hook-guarded only: install-wide rows on a scoped Postgres install (Postgres treats a NULL scope as distinct), and a host-owned `scopeField`, which the plugin does not index. Enabled collection goals merge over config goals by slug, cached for 30 seconds per scope and invalidated on change (one read serves at most 500 enabled goals per scope), and reach the native ingest, the browser tracker config and the new `GET /api/analytics/goals` endpoint (authenticated, per scope, `{ goals: [{ slug, name, source }], collection }`).

  `goalField()` is a field factory that stores a goal slug behind a picker of the request's goals, with `goalSlug()` for renderers; the picker follows native field rules (`admin.condition`, `admin.width`, `admin.description`, `admin.placeholder`), and it, `SourceSelectField` and `MetricSelectField` now resolve their path through Payload's field context, so all three behave inside blocks and array rows. `@10x-media/analytics/client` gains `GoalSelectField` and `useAnalyticsGoals` plus the `GoalsResponse` and `WireGoal` wire types, and `GoalFieldOptions` is exported from both the root and `/types`.

  `trackServerEvent(payload, event, { req, flush })` records a pageview, event or goal from server code through the native ingest (no HTTP round trip, same sanitizers and goal matching). With `req` the event inherits that request's headers, so geo, device and the visitor hash follow the real request; with neither a `req` nor an explicit `userAgent` it is attributed to a stable synthetic server visitor per day per hostname and reports no device at all rather than counting as desktop. `flush: true` awaits a buffered write. An explicit `scope` is ignored on an unscoped install and is never validated against the scopes that exist. A missing required field rejects with `AnalyticsTrackError` naming the field, and nothing is written. Needs the native adapter.

  `trackGoalAction({ hostname, path, scope })` returns a form-builder action definition (type `analyticsGoal`, exported as `GOAL_ACTION_TYPE`) with no form-builder dependency; register it as `actions: { [GOAL_ACTION_TYPE]: trackGoalAction({ hostname: 'example.com' }) }`. Treat `hostname` as required wherever a jobs runner queues actions, and `scope` as required there on a scoped install: a queued run carries the runner's request rather than the submitter's, so the fallback chain (option, request host, `serverURL` host, then throw) has nothing useful to fall back to. The action is not `essential`, so a failed write never fails the submission.

  **Breaking (scoped installs on a custom scope field):** where `providers.collection.scopeField` or `goals.collection.scopeField` names a field the plugin does not own, the plugin no longer adds its own hidden `scope` text field to that collection, since shadowing the host's field stored the scope twice. Generated types change accordingly, and a scoped Postgres install on a custom `scopeField` wants a migration dropping the now-unused `scope` column. Boot also fails with a named error when the collection carries no field of that name (`analytics: goals.collection.scopeField "tenant" does not exist on analytics-goals; register the collection with your tenant plugin or use the default scope field`), where the same misconfiguration previously booted and misbehaved silently.

  **Behavioral:** `resolveGoals` on the adapter register context and on the runtime resolves per scope once the collection is enabled, and a collection goal replaces the config goal of the same slug. The public tracker config, which was a snapshot of the config goals, now carries the request scope's merged goals, still trimmed to `slug`, `match`, `value` and `currency`, so an editor's fixed value and currency reach `trackGoal()` defaults and vendor sinks; a change reaches browsers within the 30 second resolver cache plus that endpoint's own `Cache-Control: private, max-age=60`. `AnalyticsAdapter.ingest` gains an optional `track`.

  **Consumer steps:** regenerate the admin import map (`payload generate:importmap`) once a `goalField()` is in the config, so `GoalSelectField` resolves. On Postgres, enabling `goals.collection` adds a table: run `payload migrate:create` in the app afterwards, which generates the DDL from the collection config the way every other schema change in this plugin does.

  Multi-tenant note: the goals collection uses the plugin's own `scope` field and the plugin's scope resolver. Registering it with `@payloadcms/plugin-multi-tenant` (a `tenant` relationship through `scopeField` plus an entry in that plugin's `collections`) is not supported yet: it hangs a tenant user's admin panel in the dev app and the cause is not diagnosed. Providers still support that wiring (`isGlobal: true`). Goals scope correctly either way (access, stamping, per-scope uniqueness, the picker, the tracker config and the endpoint all follow the resolved scope); what a multi-tenant install gives up today is the tenant selector filtering the goals list view. A fix is planned.

- **Additive: query endpoint.** `GET /api/analytics/query` reads any configured source through the surfacing engine for signed-in users allowed by `access.read`: metrics, up to two dimensions, a date range, granularity, filters, ordering, a row limit and an optional previous-period comparison, validated against the selected source's capabilities with coded `400` errors (`invalid_param`, `unsupported_metric`, `unsupported_dimension`, `unsupported_filter`, `unsupported_operator`, `unsupported_granularity`, `range_too_long`). Scope follows the same rules as the sources endpoint: it comes from the request, an explicit `scope` is honored only for platform readers (`400 untrusted_scope` otherwise), and a scoped install with no resolvable scope answers `404 unknown_source`. A listed shared source that cannot filter by scope still answers `403` for a tenant reader. Responses carry the normalized query (ISO date range), the source and its capabilities, and `meta.stale` when the engine served an expired cache entry; a provider outage with no cached answer is `503 unavailable` with `Retry-After`, and every answer is `Cache-Control: private, no-store`. Date-only bounds are interpreted in the reporting timezone (the whole `to` day included); datetime bounds must carry an offset. `fetchQuery`, `buildQueryUrl` and `QueryFetchError` from `/client` wrap the endpoint for admin code, and `QueryRequest` carries every parameter including the optional `scope` a platform reader needs; `QueryRequest`, `QueryResponse`, `QueryError` and the parser's own result types are exported from `/types`, where the contract's own key registries are now runtime values too: `DIMENSION_KEYS` and `FILTER_OPERATORS`, named here because picker and validator authors want the list rather than only the union type.

  **Additive: `access.read`.** A new access option gating every authenticated read endpoint (document, realtime, sources, goals, query); it defaults to allowing any signed-in user, so existing installs see no change until they set it. It is independent of scope gating: granting `read` never widens which scope a user reads.

  **Behavioral:** a `scopeResolver` that answers the platform wildcard (`'*'`) now requires `access.platformRead` on the sources endpoint too, so a non-platform user gets an empty source list instead of the config adapters.

  **Behavioral:** GA4 and Plausible reads now format both range bounds as calendar days in the reporting timezone, and every widget and field on those two providers with a non-UTC `reportingTimezone` changes its numbers as a result. East of UTC the start date was one calendar day early, so a 30-day widget was querying 31 days and totals drop after the upgrade; west of UTC the end date named the following UTC day whenever local time was past the UTC rollover, so a trailing partial day is no longer included. Native, PostHog and Umami installs are unaffected.

- **Additive: analytics view.** A dedicated admin view at `/admin/analytics` (option `view: { path, defaultRange, defaultMetric, navLabel }`, `view: false` to disable, `access.view` to gate it, defaulting to `access.read`) built on the query endpoint. It shows overview cards with a previous-period comparison, a trend, capability-gated breakdown tabs (pages, sources, technology, geography, events, goals) with click-to-filter chips, a goals panel with conversion rate, and a realtime strip, for any configured source. Range, comparison, source, metric, granularity, tab, filters, row limit and sort live in the URL, so a view is a shareable link and Back undoes a change. Every control appears only when the selected source's capabilities allow it. Scope follows the request (the tenant selector on multi-tenant installs). `AnalyticsView` is exported from `/rsc`, `AnalyticsViewClient` and `AnalyticsNavLink` from `/client`, the option types from `/types`; `AnalyticsViewClientProps` gains `scopeKey`, the resolved scope the server rendered for, which keys the client so a tenant switch refetches. `@payloadcms/next` and `next` are now peer dependencies.

  **Additive:** `BarList` gains two optional props. `onSelect` makes every row a button reporting its index (rows stay inert `div`s without it), and `fill="soft"` pales the bar and moves its label onto the elevation ramp, for a list whose rows can be zero-valued; the default `fill="solid"` is exactly the current widget look.

  **Behavioral:** the admin gains an "Analytics" nav link and the `/analytics` route by default; set `view: false` to opt out. The `visits` metric is now labelled "Visits" wherever a metric label is rendered (display fields, the document panel and the view's cards); it carried the "Visitors" label before. No widget metric picker offers `visits`, so widget configuration is unaffected.

  **Breaking: custom ranges follow the reporting timezone.** A custom widget range and a document read with a custom `from`/`to` now interpret the picked days in the reporting timezone and include the whole final day; captions show the picked days. Previously the picker's stored instant (the admin browser's local midnight) was used as-is, so the final day was mostly dropped and providers could disagree by hemisphere. Numbers move on installs whose admin browsers sit in a different zone from the reporting timezone, and on instant-comparing reads (filtered or hour-granular native reads, and the vendor adapters' calendar-day formatting), which used to drop the final day; day-rollup reads where the two zones coincide were already right. The picked day is recovered from a stored instant exactly for every browser offset in `(-12, +12]`; a browser at +12:45 or beyond recovers the previous day. Day strings (`YYYY-MM-DD`) are accepted on the document endpoint; offset-less datetimes and zero-width instant windows are rejected.

  **Behavioral: cache keys for a closed window carry its exact bounds.** A window ending on the final instant of its day is no longer day-snapped in the cache key, so an entry cached under the old, narrower window is never served after this upgrade. That covers every custom range and every comparison window, presets included (a previous period ends 1ms before the current window's first day), so each of those re-keys once and reads cold the first time after upgrading. Live preset windows, which end at `now`, keep their day-snapped key and their hit rate. The warm task re-keys its custom-range targets on the stored days and resolves them per scope, so it warms the keys a non-UTC install's widgets actually request.

- **Additive: more widgets.** Five new breakdown widgets (referrers, browsers, operating systems, campaigns, events) register from the same table as the existing ones, each gated on its own dimension. A goals widget (`analytics-goals`) lists conversions, revenue and conversion rate per goal for the widget's timeframe, under each goal's own name, with a previous-period delta on conversions when comparison is on; it needs a source that serves both `conversions` and the `goal` dimension, and costs one engine read, plus one for the rate's denominator where the source serves `visitors`, plus one for the deltas with comparison on. Every built-in widget gains an "Open in Analytics" link that opens the analytics view on the widget's source, range, metric or tab; the source is the adapter that actually served the widget, not the id it asked for, and the link serializes against the install's own `view.defaultRange` / `view.defaultMetric`, so anything already on a default is left out. A custom range becomes two day strings in the reporting timezone, clamped to the last 366 days of the window where it is wider than the view can hold; `allTime`, `thisMonth` and `thisYear` are windows the view's range picker does not offer, so those links carry no range and open the view on its default. - Native analytics engine core loop: a beacon ingestion endpoint, the events + rollups collections, cross-db atomic rollups (Mongo and Postgres), and the native() adapter (pageviews, events, avgDuration).

- Add Plausible and Umami provider adapters under the `@10x-media/analytics/adapters/plausible` and `@10x-media/analytics/adapters/umami` subpaths. Each implements the shared `AnalyticsAdapter` contract (per-URL queries, capability gating, normalized metrics) and plugs into the surfacing engine with no engine changes. Plausible uses Stats API v2 with self-hosted support; Umami supports both Cloud and self-hosted. GA4 and PostHog adapters follow in a later release.

- Provider adapters now honor `granularity: 'day'` and return a per-day series, so a trend widget backed by GA4, Plausible, PostHog, or Umami renders a real chart instead of a flat line. Range totals stay correct (distinct metrics are never summed across days). Umami's series covers pageviews and sessions; its other metrics keep a correct headline with an empty series.

- Add a realtime "active now" dashboard widget: native serves a live count of active visitors (or pageviews) in the last N minutes plus a per-minute sparkline, polled from an authenticated endpoint every 15 seconds. The widget registers only when a realtime-capable adapter is configured; providers can implement realtime later through the same capability gate.

- Add a public extension API for dashboard widgets: register your own widget with `widgets: { register: [...] }` (capability-gated, slug-validated), and build its server component from the now-public reads (`readForWidget`, `readForWidgetSeries`, `readForWidgetBreakdown`, `readForWidgetRealtime`) plus `formatMetricValue` from `@10x-media/analytics/rsc` and the chart primitives from `@10x-media/analytics/client`.

- Add a computed page-path resolver for on-document analytics fields: bind a collection with an async, request-aware `path(doc, ctx)` resolver and the field reads analytics for that path without persisting anything. Dashboard widgets gain a "Custom range" timeframe with a native date-range picker. Reads now coalesce within a UTC day, and over-long ranges are clamped to each provider's maximum lookback with a visible note.

- Add an opt-in scheduled cache-warm job. Set `cache: { warm: true }` (or `cache: { warm: { cron } }`) to register a Payload task (`analytics-warm-cache`) that pre-runs the dashboard's widget reads on a cron, deriving its targets from `admin.dashboard.defaultLayout`, so a provider-backed dashboard loads from warm `payload.kv` cache. Realtime and custom widgets are skipped; one provider failure does not abort the rest. Off by default.

- Add an opt-in sync tier. Set `sync: true` (or `sync: { cron, lookbackDays, collectionSlug, adapters }`) to register a queryable `analytics-daily` collection and a Payload task (`analytics-sync`) that, on a cron, ETLs each configured provider's last N days of daily metrics into one upserted row per `(source, date)`. The collection is queryable via Payload's APIs; native is excluded; one provider failure does not abort the rest. Off by default.

- Add a trend dashboard widget that draws a metric over time as a dependency-free SVG sparkline, backed by a new native day-granularity time-series read. The per-widget timeframe picker now offers a fuller set of relative ranges (today, last 7 days, last 30 days, last 90 days, this month, this year, last year, all time). The shared `TrendChart` primitive is exported from `@10x-media/analytics/client`. Provider adapters (Plausible, Umami, GA4, PostHog) do not yet emit time-series rows, so a trend widget pointed at a provider renders an empty line for now; the native engine is fully wired.

- Native engine now tracks unique visitors and sessions with exact cross-database distinct counting (Mongo and Postgres), plus a site-wide country breakdown dimension and a `page` breakdown for top-pages views. The seen-ledger is pruned by the retention task.

- Add dashboard widgets (Payload's experimental Modular Dashboard, PR #15700). The plugin registers capability-filtered widgets into `admin.dashboard.widgets`, starting with a configurable metric widget (pick a metric, a relative timeframe, and a data source when more than one adapter is configured) that reads through the surfacing engine. Widgets are on by default (`widgets: false` disables them, `widgets: { disabled: [...] }` drops specific slugs). Apps place widgets by spreading the exported `analyticsDefaultWidgets()` into their own `admin.dashboard.defaultLayout`; the plugin never sets `defaultLayout` itself.

- Native engine gains an opt-in in-process write buffer (`native({ buffer: true })`) that coalesces per-request event, rollup, and dedup writes into batched, per-bucket upserts to cut database round-trips under load. Off by default (writes stay synchronous and durable); `native().flush()` drains the buffer for graceful shutdown.
