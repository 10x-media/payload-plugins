---
title: Limits
description: What the plugin does not do.
---

## No per-field opt-out

The picker follows the collection: every drawer for a collection filed into a folder collection gets the folder tab. There is no way to say "folders in this field, but not in that one", because the list drawer carries no information about which field opened it.

## The folder tab ignores `filterOptions` and the admin `baseFilter`

The folder tab reads folders and documents over the REST API, so a field's `filterOptions` and a collection's `admin.baseFilter` do not narrow it the way they narrow the list tab. Access control still applies to every read. If a field must only offer a subset, pick from the **All** tab, where those filters hold.

## Folders, not tags

Only folder collections (`folders: true`, one folder per document) are browsable. A tag collection (`tags: true`) holds many values per document and has no single place to browse into, so a collection filed only into tags keeps the stock drawer.

## Folders can belong to collections

With `folders: { collectionSpecific: true }`, a folder lists the collections whose documents it may hold. A folder created for `files` does not appear when picking for `media`; one with no collections listed appears for every collection.

For a polymorphic upload field (`relationTo: ['media', 'files']`) this means one folder tree per collection, never a merged one. The drawer's collection select sits above the folder view as it does above the list, so switching between those trees takes one click. Payload's own **Type** filter is hidden there: the drawer already decides the type.

## Collections with a custom list view are skipped

If a collection already declares `admin.components.views.list.Component`, the plugin leaves it alone and the collection keeps the stock drawer. To get both, [render the plugin's view from your own](/folder-picker/configuration#rendering-the-view-yourself).
