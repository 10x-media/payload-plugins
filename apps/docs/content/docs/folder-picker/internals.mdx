---
title: How it works
description: The three undocumented Payload behaviors the plugin stands on, and the one place it is fragile.
---

The whole plugin is one config transform:

```ts
config.collections = config.collections?.map((collection) => {
  if (!collection.folders) return collection
  if (collection.admin?.components?.views?.list?.Component) return collection
  return { /* ...collection, list view swapped for the plugin's */ }
})
```

Three facts make that enough. None of them are in Payload's documentation; they are observable only in the compiled sources, so they are written down here.

## One component serves both the route and the drawer

`renderListView` in `@payloadcms/next/dist/views/List/index.js` is used by the `/admin/collections/<slug>` route **and** by the `render-list` server function that `ListDrawer` calls. Both end at the same resolution:

```js
Component: ComponentOverride ?? collectionConfig?.admin?.components?.views?.list?.Component,
Fallback: DefaultListView,
```

That is why a single swap reaches every consumer that opens a drawer, with no field patching. An implementation that goes through fields instead has to patch every upload field and then handle the lexical upload node separately, because a node in the editor is not a field.

## Swapping it does not change the list route

The swapped view returns Payload's own view when it is not inside a drawer:

```tsx
const { isInDrawer } = useListDrawerContext()
if (!isInDrawer) return <DefaultListView {...props} />
```

`isInDrawer` is nothing more than `Boolean(drawerSlug)` (`@payloadcms/ui/dist/elements/ListDrawer/Provider.js`), and the route passes no drawer slug. Payload's own tabs, filters and behavior come back with `DefaultListView`.

## The drawer drops the List/Folders tabs by design

`@payloadcms/ui/dist/views/List/ListHeader/index.js` returns a reduced header when `isInDrawer`, and that branch has no `DefaultListViewTabs`. The tabs are not hidden by CSS, they are never rendered.

`DefaultListViewTabs` is also absent from the client bundle of `@payloadcms/ui`, and it changes view by pushing an admin route, which a drawer cannot survive. So the plugin rebuilds the tabs row itself and puts a folder tab beside it.

## Where it is fragile

The drawer's header pieces (`ListHeader`, `SearchBar`, `SortByPill`, `NoListResults` and friends) are internal to `@payloadcms/ui`. The plugin reproduces their markup and class names and relies on `@payloadcms/next/css` shipping the matching styles.

Drift there shows up as **visual breakage, not a runtime error**: nothing throws, the drawer just looks wrong, so no test catches it and no log mentions it.

The peer range (`payload@^3.83.0`, same as every plugin here) is not a guarantee against that; semver has nothing to say about internal class names. Verified by hand: the markup and classes this copies are present from 3.83, and the suite runs green on 3.85. On a newer Payload, open a drawer and look at it once.

The file results themselves are not reproduced. They come from the `get-folder-results-component-and-data` server function already rendered, so the cards and tables in the drawer are Payload's own components, not copies.
