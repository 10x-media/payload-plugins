title: Consent
description: Checkbox consent with compliance defaults and proof stored by reference.
---

The `consent` field captures affirmative, checkbox-based consent with a compliance baseline built in: unchecked by default, required to submit unless marked optional, and proof stored as a reference to the policy, never as copied policy text.

```ts
// In a form's fields blocks:
{
  blockType: 'consent',
  name: 'terms',
  statement: 'I have read and agree to the Privacy Policy',
  source: 'static',
  sourceConfig: {
    label: 'Privacy Policy',
    url: 'https://example.com/privacy',
  },
  optional: false,
}
```

Set `optional: true` for marketing opt-ins and similar non-required consent. Keep terms-of-service consent separate and required.

## Rich text and inline links

`statement` is a localized rich text field, authored with your project's configured editor (the same one the [message field](/form-builder/fields#message) and action bodies use). In the admin UI, select a phrase and use the editor's link tool to link directly to your privacy policy or terms page, rather than relying solely on the separate policy-link row described under [Rendering](#rendering):

```ts
statement: {
  root: {
    type: 'root',
    children: [
      {
        type: 'paragraph',
        children: [
          { type: 'text', text: 'I have read and agree to the ' },
          { type: 'link', fields: { url: 'https://example.com/privacy' }, children: [{ type: 'text', text: 'Privacy Policy' }] },
          { type: 'text', text: '.' },
        ],
      },
    ],
  },
}
```

Keep the statement to a short sentence with inline links. Headings and lists render fine, but a checkbox reads best against one plain sentence; put longer terms in a [message field](/form-builder/fields#message) above the consent field or behind a link.

The plain string shown in the first example still works: a `statement` written before this field became rich text (or written directly through the Local API) renders as plain, escaped text rather than through the rich text pipeline, so it can never be mistaken for HTML. Either way, the checkbox keeps a single, unambiguous plain-text accessible name (the statement flattened to its visible words, links included), so formatting and inline links never affect screen reader users.

The statement renders as a sibling of the checkbox rather than wrapping it in a `<label>`, which is what makes an inline link safe: anchors are not labelable elements, so a link inside a `<label>` would toggle the checkbox when clicked. The flattening helper is exported as `textOfBody` (root and `./react`) for custom renderers that need the same accessible name, or a preview line, out of any body: it takes rich text, legacy Slate, or a plain string and never throws.

## Sources

The `source` decides how the policy link resolves. `static` (the default) is a fixed URL and label from `sourceConfig`; no server step, the renderer reads it directly. `pageReference` resolves the policy URL at display time from a Payload document (`relationTo`, `docId`, and optionally `urlField` in `sourceConfig`), the right choice when the policy is content whose URL can change. Anything else is a custom source via `defineConsentSource`:

```ts
import { defineConsentSource } from '@10x-media/form-builder'

const mySource = defineConsentSource({
  type: 'mySource',
  label: 'My policy source',
  resolve: async ({ config, payload, locale }) => ({
    links: [{ label: config.label as string, url: config.url as string }],
  }),
})

formBuilder({ consentSources: { mySource } })
```

The `consentSources` option follows the [opt-in convention](/concepts#the-opt-in-convention).

`pageReference`'s `relationTo` and `docId` are plain text fields in the admin UI, not a relationship picker: the editor must type the exact collection slug and document ID by hand. A typo or a deleted document isn't caught at authoring time (`resolve` falls back to a link with an empty `url` when the lookup fails), so review these fields carefully after renaming a collection or removing a document.

## Proof by reference

At submit, each consent field produces a `ConsentProof` stored on the submission's `consent` array:

```ts
// { agreed: true, ref: 'https://example.com/privacy', versionRef?: '...', at: '<ISO-8601>' }
```

`ref` is the policy URL resolved at submit time (not page load), `at` is the submission timestamp. Policy text is never stored, so a policy edit does not silently rewrite past proofs. This holds regardless of whether `statement` is a plain string or rich text: the statement is display-only copy and is never part of the proof.

### Version capture

Set `captureVersion: true` in `sourceConfig` for sources that support it (`pageReference` today). The proof then records which published version of the policy document the user agreed to, via `resolvePublishedVersionRef`. If drafts/versions are off for that collection, `versionRef` is omitted.

## Rendering

The `consent` renderer ships in `defaultRenderers`: the statement rendered next to the unchecked checkbox (as rich HTML when authored as rich text, as plain text for a legacy string), and the policy links (opening in a new tab with `rel="noopener noreferrer"`).

For the `pageReference` and custom sources, resolve links server-side before rendering so the visitor sees them without a client round trip (the client renderer never resolves a source itself, so skipping this step means the field renders with no policy link at all):

```ts
import { resolveConsentLinks } from '@10x-media/form-builder'

const resolved = await resolveConsentLinks(field, { registry, payload, locale: 'en' })
// Embed resolved.links on the field as `consentLinks` before passing the form to <Form>.
```

The `static` source needs none of this; the renderer falls back to `sourceConfig` directly.
