title: Goals
description: Mark conversions from a data attribute, a block field, a form action, or server code, and let editors manage goals from the admin.
---

A goal is a named conversion. Declare the goals an install cares about, hook up whatever completes them, and `conversions` and `revenue` become readable metrics alongside pageviews.

## Declare the goals

```ts title="payload.config.ts"
analytics({
  adapters: [native()],
  goals: [
    { slug: 'book-demo', name: 'Book a demo', match: { kind: 'goal' }, value: { fixed: 500 }, currency: 'EUR' },
    { slug: 'signup', name: 'Signup', match: { kind: 'event', name: 'signup' } },
    { slug: 'thank-you', name: 'Thank-you page', match: { kind: 'path', pattern: '/thank-you' } },
    { slug: 'purchase', name: 'Purchase', match: { kind: 'goal' }, value: { prop: 'total' }, currency: 'USD' },
  ],
})
```

`goals` also accepts the object form `{ defaults: [...], collection: true }`, where `collection` is the admin surface [editors manage their own goals through](#5-let-editors-manage-goals). Slugs must be unique and kebab-case, so a slug is safe in a URL, a data attribute, and a rollup bucket key; a duplicate or a non-kebab slug throws at config time, as does a negative or non-finite `value.fixed`. `name` is admin-facing and never reaches the browser.

### Match kinds

| Kind | Completes on |
|---|---|
| `{ kind: 'goal' }` | An explicit `trackGoal('<slug>')`, which is what the attribute hookup emits. |
| `{ kind: 'event', name }` | A `track(name, props)` custom event with that exact name. |
| `{ kind: 'path', pattern }` | A pageview whose path matches the glob. |

The kinds never cross: a custom event named `signup` does not complete a `{ kind: 'goal' }` goal whose slug is `signup`, and a `trackGoal('signup')` does not complete a `{ kind: 'event', name: 'signup' }` goal.

### Path globs

Anchored and case-sensitive. `*` is exactly one non-empty segment, `**` is one or more segments at any depth. A trailing slash is insignificant on both sides, a query string and a hash are cut off both the path and the pattern, and every other regex metacharacter is matched literally.

| Pattern | Matches | Does not match |
|---|---|---|
| `/thank-you` | `/thank-you`, `/thank-you/`, `/thank-you?ref=x` | `/thank-you/deep` |
| `/docs/**` | `/docs/intro`, `/docs/a/b/c` | `/docs` |
| `/checkout/*/done` | `/checkout/abc/done` | `/checkout/done`, `/checkout/a/b/done` |

### Value precedence

The event's own `value` wins (an explicit `0` included), then the goal's `value.fixed`, then `Number(props[value.prop])`, else `0`. A value that is not a finite number `>= 0` falls through to the next source, so a negative amount can never subtract from a bucket's revenue.

One event can complete several goals, and each completion carries its own value.

## Five ways to complete one

| Hookup | Reach for it when |
|---|---|
| [Data attribute](#1-tag-the-element) | The thing a visitor clicks or submits is markup you control. |
| [`goalField()`](#2-pick-a-goal-in-a-block) | Editors decide per document which goal a CTA completes. |
| [Form-builder action](#3-track-a-form-submission) | A `@10x-media/form-builder` submission is the conversion. |
| [`trackServerEvent()`](#4-track-from-server-code) | The conversion happens on the server: a webhook, a job, a server action. |
| [Goals collection](#5-let-editors-manage-goals) | Marketers add and edit the goals themselves, without a deploy. |

## 1. Tag the element

The simplest hookup is an attribute. The tracker's `goalAttribute` auto-capture (on by default) fires on click for any element and on submit for any form:

```html
<button data-analytics-goal="book-demo">Book a demo</button>

<form data-analytics-goal="newsletter-signup">
  <input name="email" type="email" />
  <button type="submit">Subscribe</button>
</form>
```

Add revenue on the element itself when the amount is per-instance:

```html
<button
  data-analytics-goal="purchase"
  data-analytics-value="49.00"
  data-analytics-currency="EUR"
>
  Buy
</button>
```

The attribute is read from the nearest ancestor carrying it, so wrapping a whole card works. A blank or non-numeric `data-analytics-value` is treated as absent rather than zero, so an unfilled template slot never books a zero-revenue conversion.

### Track it by hand

```ts
import { useAnalytics } from '@10x-media/analytics/react'

const { trackGoal } = useAnalytics()
trackGoal('book-demo')
trackGoal('purchase', { value: 49, currency: 'EUR' })
```

`trackGoal` is on the tracker itself too (`@10x-media/analytics/tracker`), for hosts that boot it without React. An unknown slug is still sent: the browser config is a server-rendered snapshot, and the server may know goals it predates.

## 2. Pick a goal in a block

`goalField()` is a field factory for your own collections, globals, and blocks. It stores the goal slug as text and renders a picker listing the goals the requesting scope can see:

```ts title="blocks/cta.ts"
import { goalField } from '@10x-media/analytics'
import type { Block } from 'payload'

export const ctaBlock: Block = {
  slug: 'cta',
  fields: [
    { name: 'heading', type: 'text' },
    { name: 'label', type: 'text', required: true, defaultValue: 'Book a demo' },
    goalField({ name: 'goal', required: true }),
  ],
}
```

Read it back with `goalSlug()` and hand the slug to whichever hookup fires the completion, usually the [data attribute](#1-tag-the-element):

```tsx title="app/[slug]/page.tsx"
import { goalSlug } from '@10x-media/analytics'

<button type="button" data-analytics-goal={goalSlug(block.goal) ?? undefined}>
  {block.label}
</button>
```

`goalSlug` accepts the stored string and returns `null` for an unset field, so a block whose goal was cleared renders no attribute at all rather than an empty one. It comes from the root entry, which pulls Payload in with it, so call it where the document is read and hand a client component the resolved slug as a prop.

| Option | Default | What it does |
|---|---|---|
| `name` | `'goal'` | Field name, and the property the slug is stored under. |
| `label` | the translated "Goal" | Any Payload label. |
| `required` | `false` | An empty value then fails with Payload's own `validation:required`. A non-empty one always has to be a kebab-case slug. |
| `admin` | | Merged under the factory's own admin config. Every slot but `Field` passes through. |
| `overrides` | | `({ field }) => TextField`, applied last. Spread the field, never deep-merge it. |

The picker is a client component, so regenerate the import map (`payload generate:importmap`) after adding the field. It behaves like a native select: `admin.condition`, `admin.readOnly`, `admin.description`, `admin.placeholder` and `admin.width` all apply, and it resolves its own path through Payload's field context, so it works inside blocks and array rows whose index moves.

Options come from `GET /api/analytics/goals`, an authenticated endpoint listing the config goals merged with the [goals collection](#5-let-editors-manage-goals) for the request's scope:

```jsonc
{
  "goals": [
    { "slug": "book-demo", "name": "Book a demo", "source": "config" },
    { "slug": "newsletter", "name": "Newsletter signup", "source": "collection" }
  ],
  "collection": { "slug": "analytics-goals" }  // null when the collection is off
}
```

The endpoint is registered whether or not the collection is enabled, so the picker works on a config-only install. It takes no scope parameter, so a tenant can only ever enumerate their own goals. A scope with no goals at all gets a notice instead of an empty menu (plus a link to the collection when the install has one), and the field stays editable, so a slug stored before the goals changed is still clearable.

Anything outside the admin reads the field by hand. The value is a plain slug string, and `goalSlug()` is the only normalization it needs.

## 3. Track a form submission

`trackGoalAction()` is a post-submit action for [`@10x-media/form-builder`](/form-builder). Analytics never imports form-builder, and form-builder never imports analytics: the action is registered by the host.

```ts title="payload.config.ts"
import { GOAL_ACTION_TYPE, trackGoalAction } from '@10x-media/analytics'
import { formBuilder } from '@10x-media/form-builder'

formBuilder({
  actions: { [GOAL_ACTION_TYPE]: trackGoalAction({ hostname: 'example.com' }) },
})
```

Each form then gets a **Track analytics goal** block under its Actions tab:

| Field | What it does |
|---|---|
| Goal | The goal this submission completes, through the same picker as `goalField()`. |
| Value | Revenue for one completion, overriding the goal's own fixed value. |
| Value from field | A submission field whose numeric answer becomes the value, used when Value is empty. |
| Currency | ISO 4217 code the value is denominated in. |

The completion is recorded against `/forms/<form id>` and carries `formId`, `formTitle` and `submissionId` as event props. Pass `path` to attribute it to the page the form lives on instead. Both `hostname` and `path` also take a function of the run arguments, for one Payload serving several sites: `hostname: ({ req }) => req?.headers.get('x-site') ?? 'example.com'`.

<Callout type="warn">
Set `hostname` on any install with a jobs runner. Form-builder queues every non-essential action, and a queued run carries the runner's request rather than the submitter's. The hostname falls back to the request's `Host` header, then to the host of `serverURL`, then throws, so an install that queues actions and does not configure either records nothing.

On a scoped install, pass `scope` for the same reason: the submitter's tenant cannot be recovered from the runner's request, so an unset scope resolves install-wide. It takes a literal, `null` for install-wide, or a function of the run arguments.
</Callout>

The action is deliberately not `essential`: a goal is a measurement, so a failed write is logged by form-builder and the submission still succeeds. It records through `trackServerEvent`, so it needs the native adapter.

## 4. Track from server code

`trackServerEvent()` records an event from anywhere on the server, through the native engine's own ingest pipeline: same sanitizers, same goal matching, same write path, no HTTP round trip.

```ts title="app/api/checkout/route.ts"
import { trackServerEvent } from '@10x-media/analytics'
import config from '@payload-config'
import { getPayload } from 'payload'

export const POST = async (request: Request) => {
  const order = await verifiedWebhookBody(request)
  const payload = await getPayload({ config })

  await trackServerEvent(payload, {
    type: 'goal',
    name: 'purchase',
    path: `/orders/${order.id}`,
    hostname: 'shop.example.com',
    value: order.total,
    currency: 'EUR',
    props: { plan: order.plan },
  })

  return new Response(null, { status: 204 })
}
```

`type`, `path` and `hostname` are required, and so is `name` on everything but a pageview. An event that fails one of them rejects with an `AnalyticsTrackError` naming the field, and nothing is written; the same input over the [ingest endpoint](/analytics/native#the-ingest-endpoint) answers `400`. Every optional field is sanitized exactly as it is on the wire.

| Option | What it does |
|---|---|
| `opts.req` | The request behind the event. Attribution, scope and reporting timezone all follow it. |
| `opts.flush` | Awaits the write on an install with a [write buffer](/analytics/native#write-batching-opt-in). Without it the call resolves as soon as the event is queued, and a failed flush only reaches the logger. |
| `event.ip`, `event.userAgent` | Overlaid on the request's own headers, for a proxy that knows better than the request it holds. |
| `event.scope` | Boundary to stamp, `null` for install-wide. See below. |
| `event.timezone`, `event.now` | Override the resolved reporting timezone and the event time. |

**Pass `opts.req` whenever there is a request.** The event then inherits that request's whole header set, so the platform geo headers reach the [geo resolver](/analytics/geo), the device classifies from the real user agent, and the visitor hashes to the same person the browser events did. Without a request and without an explicit `userAgent`, the event is attributed to a synthetic server visitor, stable for one day per hostname, and reports no device at all rather than padding the desktop bucket.

On a scoped install the scope comes from `opts.req` unless `event.scope` says otherwise, and goals resolve under the scope the event is stamped with, so a tenant's server event can only complete that tenant's goals. An explicit scope is never validated against the scopes that exist, and an unscoped install ignores it outright, exactly as the ingest endpoint ignores a scope on the wire.

`trackServerEvent` needs the native adapter. Provider slots have no server-side ingestion seam yet, so an install without `native()` throws rather than dropping the event.

## 5. Let editors manage goals

`goals.collection` adds an `analytics-goals` collection to the admin, so goals can be added and edited without a deploy:

```ts title="payload.config.ts"
analytics({
  adapters: [native()],
  goals: {
    defaults: [{ slug: 'book-demo', name: 'Book a demo', match: { kind: 'goal' } }],
    collection: true,
  },
})
```

`true` takes the defaults; the object form reshapes them:

| Option | Default | What it does |
|---|---|---|
| `enabled` | `true` | Set `false` to keep the rest of the object while leaving the collection off. |
| `slug` | `'analytics-goals'` | Collection slug. |
| `scopeField` | `'scope'` | Field matched against the resolved scope. Point it at a tenant plugin's own field where that plugin manages scoping. |
| `access` | scope-aware defaults | Overrides individual operations. |
| `overrides` | | `(collection) => CollectionConfig`, applied last. |

Each document carries the same shape config goals do: `name`, `slug`, `enabled`, a `match` group (kind `goal`, `event` or `path`, with the event name or the path pattern beside it), a `value` group (`fixed` and `prop`), and a `currency`. The slug validates as kebab-case and is unique per scope. Disabling a document is the soft delete: it stops matching immediately and leaves the history it already stamped alone.

**Collection goals win over config goals by slug.** A document whose slug matches a config goal replaces it in place, keeping config's order so reports built on it do not reorder; the collection's own extras follow. That is what makes the collection an editor's handle on what config declared, rather than a second, competing list.

Resolution is cached for 30 seconds per scope and dropped whenever a goal document changes or is deleted, so native ingest, which resolves goals on every single event, does not query the collection per request. A read that fails falls back to the config goals rather than taking ingest down with it.

Access is scope-aware out of the box, the same rules the provider collection follows: a tenant reads, updates and deletes only their own goals, every create is stamped with the request's resolved scope server-side (a forged one is refused, not silently rewritten), and `access.platformRead` lifts both restrictions for platform admins. See [Multi-tenancy](/analytics/multi-tenancy#goals-per-tenant).

<Callout type="warn">
Only the server resolves collection goals. The browser's tracker config is a snapshot of the **config** goals, and it exists so `trackGoal()` can attach a goal's fixed value and currency to the outbound event.

Native is unaffected: it matches every event at ingest, where the merged set applies, so a collection goal's `value.fixed` still books revenue. A vendor sink is not: a collection goal's value and currency are not attached to the event the vendor's own SDK receives, so send the amount explicitly (`trackGoal(slug, { value, currency })`, or `data-analytics-value`) when revenue has to reach a provider.
</Callout>

On Postgres the collection is a new table, so an existing install needs a migration (`payload migrate:create`) before the option ships.

## How native reports them

Goals are matched at ingest, against the same sanitized fields that get stored, and the completions are stamped onto the event. Editing a goal later never rewrites history.

The [native engine](/analytics/native) then serves three metrics and one dimension:

| Key | What it is |
|---|---|
| `conversions` | Completions in the bucket. Every bucket carries them, so a breakdown by country or device can report conversions too. |
| `revenue` | Summed completion values. See the currency note below. |
| `scrollDepth` | Average deepest scroll, over the pageviews that actually reported one. |
| `goal` (dimension) | Groups by goal slug. Groupable, not filterable. |

All three metrics appear in the widget metric, trend, and breakdown pickers, and the built-in `analytics-breakdown-goals` widget lists completions per goal (defaulting its metric to `conversions`). See [Dashboard widgets](/analytics/widgets).

A `goal` event counts under the `events` metric, not `pageviews`, and is deliberately kept out of the `event` dimension breakdown: its name is a goal slug and belongs to the `goal` dimension instead.

<Callout type="warn">
Revenue is stored and summed as a plain number in the event's own currency. There is no FX conversion and no `currency` dimension, so a bucket spanning currencies sums figures that are not comparable. Widgets and stat fields render the result as a bare number too, with no currency symbol and nothing marking which currencies went into it. Keep one currency per install, or read revenue per goal.
</Callout>

Existing native installs need the goal-counter migration before any of this reads correctly. See [Upgrading for goal metrics](/analytics/native#upgrading-for-goal-metrics).

## How providers report them

A goal travels to a vendor as an ordinary event named by its slug, so it shows up wherever that vendor lists event names. The plugin does not create the vendor's own goal or conversion definitions for you.

| Adapter | Call | Revenue |
|---|---|---|
| PostHog | `posthog.capture(slug, { ...props, value, currency })` | As the `value` and `currency` properties, which PostHog's revenue analytics reads. |
| Plausible | `plausible(slug, { props, revenue: { amount, currency } })` | Plausible's documented ecommerce shape. |
| Umami | `umami.track(slug, { ...props, value, currency })` | Umami has no revenue field; both ride along as event data. |

Reading `conversions` and `revenue` back still depends on the adapter's own capabilities: native and GA4 serve both, Plausible serves `revenue`, PostHog and Umami serve neither. That is what the [capability gate](/analytics/adapters#the-capabilities-model) enforces, so a widget whose active source cannot answer degrades rather than reporting a wrong number.
