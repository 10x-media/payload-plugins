Everything in the plugin reads through one interface. An adapter answers queries (`pageviews for /blog/post-1 over the last 30 days`) and declares what it can answer; the plugin never asks for more.

```ts title="payload.config.ts"
import { analytics } from '@10x-media/analytics'
import { plausible } from '@10x-media/analytics/adapters/plausible'
import { native } from '@10x-media/analytics/adapters/native'

analytics({
  adapters: [native(), plausible({ siteId: 'example.com', apiKey: process.env.PLAUSIBLE_API_KEY! })],
  defaultAdapter: 'plausible', // used when a field or widget does not name one
})
```

Adapters ship as code-split subpaths, so a site bundles only what it imports. Each adapter has a stable `id` (`native`, `plausible`, `umami`, `ga4`, `posthog`) that fields and widgets reference via their `adapter` / data source options.

## The capabilities model

Each adapter declares an `AnalyticsCapabilities` object: which `metrics` and `dimensions` it supports, which of those `dimensions` also accept an `AnalyticsQuery.filters` entry (`filters`) and with which operators (`filterOperators`, from `eq` / `contains` / `matches`), whether it can query per page (`perPageQuery`) or in `realtime`, its `maxLookbackDays`, rate-limit hints, and recommended cache TTLs.

`comparison` is optional and defaults to `true`. The previous-window read is the engine's own, and it works against any source, so an adapter of your own compares without declaring anything; set `comparison: false` to opt a source out. The serialized form the pickers read still carries a plain boolean.

Every surface is gated by it:

- A [dashboard widget](/analytics/widgets) whose metric or dimension no configured adapter supports is not registered at all.
- A [display field](/analytics/display-fields) drops unsupported metrics from its request and renders the rest.
- A custom range that exceeds a provider's `maxLookbackDays` is narrowed to the provider maximum, visibly.

Metric keys: `pageviews`, `visitors`, `visits`, `sessions`, `bounceRate`, `avgDuration`, `scrollDepth`, `events`, `conversions`, `revenue`. Dimension keys include `page`, `referrer`, `source`, `channel`, `device`, `country`, and the UTM set. No adapter supports all of them; the gating exists so that never matters.

## `source` and `channel`

The two mean the same thing on every adapter. **`source`** is the visit's named origin: the `utm_source` tag when there is one, otherwise the referrer. **`channel`** is the classification of that origin into an acquisition channel, in each source's own vocabulary.

| Adapter | `source` | `channel` | Filterable |
|---|---|---|---|
| native | `utm_source` lowercased, else the referrer host, else `direct` | the engine's own [twelve tokens](/analytics/native#traffic-channels), classified at ingest | both, `eq` and `contains` |
| Plausible | `visit:source`, which Plausible fills from a `utm_source` / `source` / `ref` tag or the `Referer` header | `visit:channel`, Plausible's acquisition channel | both |
| GA4 | `sessionSource` | `sessionDefaultChannelGroup` (`Direct`, `Organic Search`, `Paid Social`, ...) | both |
| PostHog | not served | `session.$channel_type`, the sessions table's classification of the session's entry URL, honoring a project's custom channel rules | `channel` only |
| Umami | not served | `/metrics?type=channel` (`direct`, `organicSearch`, `paidSocial`, ...) | neither: the route takes no channel filter parameter, so `channel` groups and never filters |

Each source reports its own casing: native lowercases the `utm_source` it stores in `source`, so one tag spelled two ways is one row, where a provider answers whatever it holds. Only native's channel tokens are translated in the admin. A provider's values render exactly as that provider reports them, so a channel breakdown reads `Paid Search` on GA4 and `paidSearch` on Umami.

An unconfigured adapter (missing credentials) degrades to an empty state and makes no network calls.

## Capture support

Reading and capturing are separate concerns. An adapter that declares `capture` can also fill a [capture slot](/analytics/capture#capture-slots): the browser tracker boots its snippet, and its tracker traffic is served through the [first-party proxy](/analytics/proxy) rather than the vendor domain, wherever the adapter declares proxy routes. Read credentials are never part of it; only what the browser is allowed to see.

| Adapter | Capture | Extra config it needs |
|---|---|---|
| native | Yes | None. The plugin's tracker posts straight to the ingest endpoint; nothing is proxied or injected. |
| PostHog | Yes | `projectToken` (the public `phc_...` browser key, distinct from the read `apiKey`) and `region` (`us` / `eu`, derived from `host` when omitted). |
| Plausible | Yes | `domain` for the legacy `data-domain` tag, or `scriptId` for the per-site `pa-<id>.js` model. `domain` wins when both are set; with neither, no snippet is emitted. |
| Umami | Yes | None beyond `websiteId`. `host` doubles as the app origin for capture: a trailing `/api` is stripped, so one value serves the Stats API and the tracker. |
| GA4 | Yes | `measurementId` (the public `G-XXXXXXX`). The tag loads from googletagmanager.com rather than a first-party proxy, so this is the one capture slot that is not proxied. |

Capture support is declared only when the public capture config it needs is actually present, so a PostHog adapter configured for reads alone (no `projectToken`), a Plausible one with neither `domain` nor `scriptId`, or a GA4 one without a `measurementId` declares no `capture` at all: no proxy route, no snippet, and it fills no slot. Reads are unaffected either way.

The exact routes and snippets each one declares are on the [proxy page](/analytics/proxy#per-vendor-routes).

## Filters

`AnalyticsQuery.filters` narrows a read to rows matching one or more `{ dimension, operator, value }` entries. A widget or field requesting a filter dimension no configured adapter declares in `filters` is gated the same way an unsupported metric or dimension is; the read helpers drop into an unavailable state rather than silently ignoring the filter.

| Adapter | Filterable dimensions | Operators |
|---|---|---|
| native | every dimension it serves except `goal`: `page`, `referrer`, `source`, `channel`, `utmSource`, `utmMedium`, `utmCampaign`, `utmContent`, `utmTerm`, `device`, `browser`, `os`, `country`, `region`, `city`, `language`, `event` | `eq`, `contains` |
| PostHog | `page`, `channel`, `event` | `eq`, `contains`, `matches` |
| Plausible | `page`, `source`, `channel`, `referrer`, `device`, `browser`, `os`, `country`, `region`, `city`, `utmSource`, `utmMedium`, `utmCampaign` | `eq`, `contains`, `matches` |
| GA4 | `page`, `referrer`, `source`, `channel`, `medium`, `campaign`, `utmSource`, `utmMedium`, `utmCampaign`, `device`, `browser`, `os`, `country`, `region`, `city`, `language`, `event` | `eq`, `contains`, `matches` |
| Umami | `page`, `referrer`, `browser`, `os`, `device`, `country`, `region`, `city`, `language`, `event`, `utmSource`, `utmMedium`, `utmCampaign`, `utmContent`, `utmTerm` | `eq`, `contains`, `matches` |
| `memoryAdapter` (testing) | `page` | `eq` |

`goal` is nowhere in this table. It is a breakdown on every source that serves it, narrowed by the read's own goal slugs rather than by a filter a caller writes; see [goals on a provider](/analytics/goals#how-providers-report-them).

`matches` is provider-only, and each provider's regex is its own dialect: Plausible's `matches` is an re2 **full** match, GA4's `FULL_REGEXP` likewise (so a pattern must cover the whole value, `/docs/.*` rather than `^/docs`), Umami's `re.` is a case-insensitive **partial** match, and PostHog's is re2 through `match()`. Native declares no `matches` at all, because the two database adapters have no portable flavor to match any of them with.

`contains` is case-insensitive on native, Umami (`ilike`) and GA4 (`CONTAINS` with `caseSensitive: false`); Plausible's is case-sensitive, since the adapter does not send its case-insensitive modifier. GA4's `eq` and `matches` compare literally. On native, `contains` goes through Payload's own `contains` operator: case-insensitive on both Mongo and Postgres, but the two DBs differ on what a raw `%` or `_` in the filter value does. Mongo regex-escapes the value first, so it always matches as a literal substring; Postgres wraps it in an ILIKE pattern without escaping it, so `%`/`_` act as SQL wildcards there. PostHog's `contains` escapes wildcard characters in the value itself before building its `ILIKE` pattern, so a `%` or `_` matches literally regardless of DB.

Umami takes **one value per query parameter**, so a read can carry filters it cannot send. Two `eq` filters on one dimension with different values are an AND that matches nothing, which the adapter answers as an empty result without calling the API; any other collision keeps the first filter, except that a per-page read's own path always wins the `path` parameter. Whatever was dropped comes back in `meta.unappliedFilters`, so a surface can say the rows are wider than it asked for.

## Plausible

```ts
import { plausible } from '@10x-media/analytics/adapters/plausible'

plausible({ siteId: 'example.com', apiKey: process.env.PLAUSIBLE_API_KEY! })
```

Uses the Stats API v2 (`POST /api/v2/query`). Pass `host` for a self-hosted Community Edition instance, and `domain` or `scriptId` to capture through it. Metrics: pageviews, visitors, visits, sessions, bounceRate, avgDuration, events, scrollDepth, conversions, and revenue where `revenueCurrency` is set. Dimensions include `channel`, which maps to `visit:channel`, and `goal`, which maps to `event:goal`. Durations are normalized to milliseconds. Default `maxLookbackDays: 730` (set `null` to disable clamping).

`revenueCurrency` is the ISO code of the site's revenue goals, and it is what turns the `revenue` metric on: Plausible serves `total_revenue` only inside a goal-filtered request on a site that has a revenue goal, and errors the request on a site that has none. Unset, the adapter neither declares `revenue` nor asks for it.

## Umami

```ts
import { umami } from '@10x-media/analytics/adapters/umami'

// Umami Cloud
umami({ websiteId: 'xxxx', apiKey: process.env.UMAMI_API_KEY! })

// Self-hosted (token from POST /api/auth/login)
umami({ websiteId: 'xxxx', token: process.env.UMAMI_TOKEN!, host: 'https://analytics.example.com/api' })
```

Targets Umami 3.x, cloud and self-hosted. Metrics: pageviews, visitors, visits, sessions, plus bounceRate and avgDuration derived from visit totals, and conversions. The `page` dimension maps to `/metrics?type=path` (`type=url` was the 2.x name and 3.x rejects it). Umami has no per-day source for visitors, bounce rate, or duration, so trend series on those metrics are empty while headlines stay correct.

`/metrics` reports one number per row, and on every dimension but `goal` that number is the count of distinct sessions, so **a breakdown row carries `visitors`** whatever metric the read asked for; a breakdown that asks for something else charts the first metric its rows do carry rather than a column of zeros under the wrong name. `event` is filterable but not groupable, since the install-wide `events` metric has no source in `/stats`; `goal` and `channel` are the reverse, groups with no matching filter parameter. `channel` is `/metrics?type=channel`, Umami's own acquisition classification (`direct`, `organicSearch`, `paidSearch`, `paidSocial`, `email`, `affiliate`, ...), carrying the read's date range and filters like every sibling type.

Filter values carry an operator prefix (`eq.`, `c.`, `re.`), and Umami reads any of its operator names followed by a dot as an operator, so the adapter always writes `eq.` explicitly and a value like `s.example.com` stays literal. Umami splits an `eq.` value on commas into a value list with no escape, so a goal slug containing a comma cannot be asked for and is reported in `meta.unappliedFilters`.

## GA4

```ts
import { ga4 } from '@10x-media/analytics/adapters/ga4'

ga4({
  propertyId: '123456789',
  credentials: {
    client_email: process.env.GA4_CLIENT_EMAIL!,
    private_key: process.env.GA4_PRIVATE_KEY!,
  },
})
```

Uses the GA4 Data API (`runReport`) through the official SDK, declared as an optional peer dependency and loaded lazily:

```bash
pnpm add @google-analytics/data
```

Metrics: pageviews, visitors, visits, sessions, bounceRate, avgDuration, events, conversions, revenue. Dimensions include `channel`, which maps to `sessionDefaultChannelGroup`, and `goal`, which maps to `eventName` restricted to the read's own goals. Durations normalize to milliseconds, bounce rate to a percentage. GA4 bills a token quota, so the adapter recommends a long aggregate TTL (6 hours); [cache warming](/analytics/cache) pairs well with it. Default `maxLookbackDays: 425` (GA4's rolling window).

`conversions` reads GA4's `keyEvents`, which counts only events the property itself marks as key events: an event that is a goal here but is not marked there reports 0. Set `measurementId` to capture through the same property; see [Capture](/analytics/capture#ga4).

## PostHog

```ts
import { posthog } from '@10x-media/analytics/adapters/posthog'

posthog({ projectId: '123', apiKey: process.env.POSTHOG_API_KEY! })
```

Derives web metrics with HogQL through the Query API. `apiKey` is a personal API key with the Query Read scope and never reaches the browser; capture takes the public `projectToken` (`phc_...`) instead. Pass `host` for EU Cloud (`https://eu.posthog.com`) or self-hosted; US Cloud is the default, and `region` pins the proxied capture hosts independently. Metrics: pageviews, visitors, visits, sessions, events. `events` counts every captured event (matching PostHog's own Events definition); requesting it (or the `event` dimension) switches the read off the `$pageview`-only filter, and the pageview-family metrics stay pageview-scoped through conditional aggregation. Dimensions: `page` (top-pages breakdown), `channel` (`session.$channel_type`, reached through the events table's own `session` join on `$session_id`), `event` (per-event-name breakdown) and `goal`, which is the event name restricted to the read's own goals. A `channel` read stays pageview-scoped, since a session property is not an event name; a pageview captured with no `$session_id` joins nothing and lands in an empty channel, which the admin shows as **Not set**. `conversions` counts those goal events; PostHog serves no revenue. A binding `hostname` filters on `properties.$host`.

Time bounds are sent as `toDateTime('...', 'UTC')`. A bare HogQL date literal parses in the project's timezone, so a project set to anything but UTC used to read a window shifted by its offset; buckets are still cut in the reporting timezone.

## Testing: memoryAdapter

```ts
import { memoryAdapter } from '@10x-media/analytics/testing'

const adapter = memoryAdapter()
adapter.record({ path: '/a', timestamp: new Date(), visitor: 'v1' })
// ...assert against widgets/fields; adapter.reset() between tests
```

A deterministic in-memory adapter for tests and local development, with wide declared capabilities so gated surfaces stay visible.

## Writing your own adapter

Implement `AnalyticsAdapter` from `@10x-media/analytics/types`: an `id`, a `label`, honest `capabilities`, `isConfigured()`, and `query(query, ctx)` returning rows and totals. A read that asks for `conversions` or the `goal` dimension also carries `query.goalSlugs`, the scope's goal slugs, which is `'unresolved'` when resolving them failed; a provider adapter restricts its goal rows to them, sets `meta.goalsUnresolved` when it was given no slugs to restrict by, and answers empty rows unflagged when the scope configured no goals. Optional extras: `realtime(query, ctx)` for the realtime widget, and `register(config)` to add collections or endpoints (the native engine uses this hook). `capabilities.filters` and `capabilities.filterOperators` are required fields, even if empty (`new Set()`) for an adapter that honors no `AnalyticsQuery.filters` entry at all. Declare only capabilities you actually serve; the plugin trusts them.
