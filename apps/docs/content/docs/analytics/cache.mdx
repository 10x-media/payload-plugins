---
title: Caching and warming
description: How reads are cached in payload.kv, and the opt-in warm job for provider-backed dashboards.
---

Every read (widgets, display fields, sync) goes through a surfacing engine that caches in `payload.kv`, coalesces concurrent identical requests into one in-flight read, bounds concurrency, and backs off exponentially on provider errors. The engine is built for the dashboard's worst case: one page load fires many widget reads at once, and several providers bill per query. Caching absorbs repeat reads across requests; coalescing absorbs them within one, so a burst of identical queries costs a single provider call. Unconfigured adapters and provider outages degrade to empty states, never crashes.

## TTLs

Cache entries are keyed per adapter and query and snapped to the day of the [reporting timezone](/analytics/timezone) (UTC by default). Two reads on the same day therefore share a cached result, and reads in different timezones never collide. Two TTLs apply:

```ts
analytics({
  adapters: [/* ... */],
  cache: {
    ttl: {
      aggregate: 3600, // seconds; historical reads.
      realtime: 300,   // seconds; realtime reads.
    },
  },
})
```

Each adapter recommends its own TTLs through its capabilities (GA4 suggests 6 hours because its quota is token-billed; the native engine suggests short TTLs because reads are local). Those recommendations are the default. A value you set in `cache.ttl` overrides the adapter recommendation for every adapter; leave a value unset to keep each adapter's own recommendation.

## Invalidation

A TTL alone means a corrected provider document keeps serving the old numbers until every entry it fed expires, up to an hour on most sources. Every cache key therefore carries a **cache epoch** as its second segment: an opaque token, one per scope, stored in `payload.kv` under `analytics:epoch:global` for the install-wide token and `analytics:epoch:s:<scope>` for a named scope, URL-encoded. Bumping a scope's token retires that scope's cached reads at once, on every instance, because the keys those entries sit under stop being built. Nothing is deleted; the old entries expire on their own TTL under keys no read asks for any more.

Three things bump a token:

- Saving or deleting a document in the [providers collection](/analytics/multi-tenancy#2-register-the-provider-collection-per-tenant). That document's own scope is bumped, and an update that moved it between scopes bumps the scope it left as well.
- Saving or deleting a [goal](/analytics/goals) document, the same way. Goals declared in the plugin's `goals` option are fixed at config time and cannot change while the process runs, so they never bump.
- [`POST /api/analytics/refresh`](/analytics/data-sources#refresh-endpoint), which the **Refresh** button in the [analytics view](/analytics/analytics-view) calls.

An instance reads a scope's token at most once every ten seconds and serves that reading from memory in between, so one KV get covers a burst of reads and a bump made on one instance reaches every other within ten seconds. The interval is fixed and not an option.

A token that cannot be read falls back to `0`, the value every scope starts on, and one warning is logged. The read still answers: an unreachable counter never turns into a failed analytics read. That fallback is memoized like a successful reading, so a broken KV costs one get per scope per ten seconds rather than one per read, and for that window the instance keeps serving entries written before the bump it could not see.

A bump that fails, or that has not settled after two seconds, is logged and dropped rather than failing the document save that triggered it. The save goes through and that scope's cached reads stay until their TTL runs out.

An instance bumps a given scope at most once every five seconds for the refresh endpoint; inside that window the endpoint answers the token already in force and retires nothing again. A looped `POST` therefore costs one round trip rather than one cold provider read per cached query. The two document hooks are not debounced, so a save is always visible on the next read. This is a debounce of invalidation, not request rate limiting: how often a caller may ask is the edge's decision, not the plugin's.

### The refresh endpoint is state-changing and cookie-authenticated

`POST /api/analytics/refresh` changes server state and Payload authenticates it from the admin session cookie, so configure Payload's [`csrf`](https://payloadcms.com/docs/authentication/cookies#csrf-attacks) allowlist on any install that exposes it:

```ts
buildConfig({
  csrf: ['https://admin.example.com'],
  // ...
})
```

With Payload's default `csrf: []` there is no allowlist to check, so a request carrying any `Origin` at all is accepted on its cookie. What stops a forged cross-site `POST` then is browser behavior rather than a check: the auth cookie's `SameSite=Lax` default keeps it off a cross-site `POST` in the first place, and the `Content-Type: application/json` a real client sends forces a CORS preflight no foreign origin passes. Only the first of those covers a forger, who picks the content type. An allowlist is the check itself, and it costs one line.

<Callout type="warn">
**Every entry cached by an earlier release is invalidated once on upgrade.** The epoch segment changed the key format, so entries written before it are never read again: the first read of each query after the upgrade reaches the source, and caching resumes normally from there. Nothing has to be cleared by hand, and the orphaned entries expire on their own.
</Callout>

### Cross-scope entries key on the install-wide token

A cross-scope read stamps no scope on its query, so its entries key on `analytics:epoch:global`. That covers a platform reader passing `scope=*`, and a scoped read through a shared config adapter that cannot narrow to one scope, which answers install-wide totals rather than that tenant's (see [Multi-tenancy](/analytics/multi-tenancy#4-who-sees-what)).

A tenant saving a provider document bumps that tenant's token, which leaves such an entry in place. It expires on its TTL, or a platform reader retires it by refreshing with `scope: '*'`.

## Scheduled warming (opt-in)

For provider-backed dashboards, the first load after an entry expires pays a cold provider round trip. The warm job pre-runs the dashboard's reads on a cron so that first load hits a warm cache:

```ts
analytics({
  adapters: [plausible({ /* ... */ })],
  cache: { warm: true },                       // default cron: every 30 minutes
  // cache: { warm: { cron: '0 * * * *' } },   // hourly
})
```

The job registers a Payload task (`analytics-warm-cache`) whose work list derives from your `admin.dashboard.defaultLayout`: each metric, trend, and breakdown widget becomes one warm read with the same metric, timeframe, and data source it renders. The realtime widget is skipped (the live poller keeps it warm), as is any custom widget whose read shape the plugin cannot know. One provider failure is logged and does not abort the rest.

On a [multi-tenant](/analytics/multi-tenancy) install, configure `scopes` to fan the same work list out per tenant: every target runs once for the install-wide scope (unchanged) plus once per scope `scopes()` returns, each pass resolving that tenant's own runtime providers. Without `scopes`, warming stays install-wide only, even with `providers.collection` enabled. See [Cron tiers](/analytics/multi-tenancy#5-cron-tiers).

Warming is off by default because it spends provider API quota on a schedule. It pays off most for provider-backed dashboards; the native engine is fast enough that warming it is harmless but low value.

<Callout>
The warm task runs through Payload's jobs runner. Enable cron `autoRun`, run a [worker](/jobs/workers), or invoke the queue from an external scheduler, or the schedule never fires. The same applies to [sync](/analytics/sync) and retention pruning.
</Callout>

## Resilience

Every provider read runs under a timeout, retries transient failures with backoff, respects the adapter's declared rate limits, and can serve a stale cached result rather than fail outright.

### Timeout

```ts
analytics({
  adapters: [/* ... */],
  cache: {
    timeoutMs: 15000, // default; per-read budget in ms
  },
})
```

`cache.timeoutMs` bounds one adapter read end to end, including any retries and time spent waiting on the rate limiter. Past the budget, the in-flight request is aborted and the read fails over to a stale cache entry if one is available, otherwise it degrades to an empty or unavailable state.

### Retry policy

A failed read retries only when the failure looks transient. The policy is fixed and not configurable:

| Failure | Retries |
|---|---|
| HTTP 429 or 5xx | Up to 2, with exponential backoff |
| Other HTTP 4xx | None (treated as a caller bug) |
| Aborted (timeout) | None |
| Non-HTTP (network error) | 1 |

### Rate limiting

Each adapter declares its own provider rate limits through `capabilities.rateLimit`, and the engine throttles reads per adapter with a token bucket so a burst of dashboard reads never exceeds what the provider allows:

| Adapter | Limit |
|---|---|
| PostHog | 240 requests/minute, 2400 requests/hour |
| Plausible | 600 requests/hour |
| GA4 | 10 concurrent requests |
| Umami, native | None declared |

A limiter waits for a free slot rather than rejecting outright; that wait counts against `cache.timeoutMs`.

### Stale-while-error

When a cache entry expires and the refresh fails, the engine falls back to serving that expired entry rather than surfacing the failure, as long as the entry is still within a 24 hour stale window. The result carries `meta.stale: true` so callers can distinguish a fresh read from a stale one. Past the 24 hour window, or with no cached entry at all, the read degrades to an unavailable state instead. Every failed refresh is logged with the adapter id, never the underlying credentials.
