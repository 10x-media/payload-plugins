title: Native engine
description: Self-hosted, cookieless analytics stored inside Payload.

`native()` is an adapter that stores analytics in your own database. No external service, no cookies, no client fingerprinting beyond a salted daily visitor hash.

```ts title="payload.config.ts"
import { analytics } from '@10x-media/analytics'
import { native } from '@10x-media/analytics/adapters/native'

analytics({ adapters: [native()] })
```

Registering it adds three hidden collections (`analytics-events`, `analytics-rollups`, `analytics-seen`) and a public beacon endpoint. Metrics served: `pageviews`, `visitors`, `sessions`, `events`, `avgDuration`, `conversions`, `revenue`, `scrollDepth`. Dimensions: `page`, `referrer`, `source`, `channel`, `utmSource`, `utmMedium`, `utmCampaign`, `utmContent`, `utmTerm`, `device`, `browser`, `os`, `country`, `region`, `city`, `language`, `event`, `goal`, each of them detailed under [dimensions](#dimensions). Realtime is supported.

## The ingest endpoint

`POST /api/analytics/ingest` (path configurable via `ingestPath`) accepts one event per request. The plugin's own [browser tracker](/analytics/capture) posts exactly this shape:

```ts
interface RawEventInput {
  type: 'pageview' | 'event' | 'goal'
  path: string          // required
  hostname?: string     // optional; the stored hostname comes from the request, see below
  name?: string         // event name, or the goal slug; required unless type is 'pageview'
  referrer?: string
  query?: string        // the page's query string, no leading '?'; read on any type
  durationMs?: number
  props?: Record<string, unknown>
  value?: number        // revenue for a goal completion, in `currency`
  currency?: string     // ISO 4217
  scrollDepth?: number  // deepest scroll on a pageview, 0-100
}
```

An event is rejected only on its required fields: a known `type`, a non-empty string `path`, and a non-empty string `name` on everything but a pageview. `hostname` is not one of them: it is optional on the wire, and a body that carries one is only type-checked, since the stored value comes from the request rather than from the body (see [Where the hostname comes from](#where-the-hostname-comes-from)). Optional fields are sanitized rather than rejected, so one malformed attribute costs an attribute instead of the whole event: `value` must be a finite number `>= 0`, `currency` must match `/^[A-Z]{3}$/`, `scrollDepth` is clamped to 100 and rounded, `durationMs` must be a finite number between 0 and 86,400,000 (a day) or it is dropped, `name` is truncated to 128 characters (it is the `event` dimension's bucket key), `path` to 512 and the resolved hostname to 253 (both are rollup bucket keys), and `props` keeps at most 20 flat scalar entries with keys up to 64 characters and string values truncated to 256. The request body is capped at 64 KiB (`413 payload_too_large` above it) and unparseable JSON answers `400 invalid_param`.

The server derives the rest at ingest time: the hostname the event is stored under, the [dimensions](#dimensions) below, a salted daily visitor hash (the salt rotates per UTC day, so visitors cannot be tracked across days), and the [goals](/analytics/goals) the event completed, stamped onto the stored event. The endpoint responds `202` on success and `400` on an invalid body.

A refusal is the same [error envelope](/analytics/data-sources#errors) the authenticated endpoints answer: `{ "error": { "code", "message", "param"? } }`. The `400` names the first field the event failed on in `param`, checked as `type`, `path`, `hostname`, `name`, so a tracker author is not left guessing which one was refused; a missing `hostname` never lands there, only a non-string one does. Unparseable JSON names `type`, and a body that died in transit (a beacon from an unloading tab) names nothing. The `413` is `payload_too_large` and names nothing either.

`query` never reaches storage. It is capped at 512 characters, parsed for its five `utm_*` keys and for the [ad click ids](#traffic-channels) the channel classifier reads, and thrown away, so a session token or an email address that happens to be in the URL is not written to the events collection. The endpoint reads it on any event type; the tracker only sends it with pageviews, and sending it at all is optional: [`capture.autoCapture.query: false`](/analytics/capture#auto-capture) stops the tracker putting it on the wire.

A `goal` event counts under `events`, never under `pageviews`, and is kept out of the `event` dimension breakdown: its name is a goal slug, and it appears under the `goal` dimension instead. `revenue` is summed as a plain number in the event's own currency, with no conversion; see the currency note on [Goals](/analytics/goals#how-native-reports-them). `scrollDepth` averages over the pageviews that actually reported one, tracked by its own sample counter so a pageview whose tracker never sent a depth does not drag the average down.

Events are written atomically, via `$inc` on Mongo and `ON CONFLICT DO UPDATE` on Postgres, so concurrent ingestion is safe.

### Where the hostname comes from

The stored hostname is the host the request itself carried, not the one its body claims. That is `x-forwarded-host`'s first value when the plugin's [`trustedProxyHops`](#trusted-proxies) is 1 or more, and the `Host` header otherwise, lowercased, with the port and a trailing root dot stripped and the result capped at 253 characters. A request that yields no usable host at all is dropped.

The `Origin` header is deliberately never read. A scripted client can pair a valid `Host` with any `Origin` it likes, so reading it would leave the hole this closes: one client minting unlimited hostname bucket families inside a scope it is legitimately allowed to send to. The request host is what the edge routes on, so it can only ever be a host that reaches the install.

The body's `hostname` is therefore optional, and the tracker keeps sending it: a [resolver](#a-resolver) receives it as `claimed`. [`trackServerEvent`](/analytics/goals#4-track-from-server-code) is trusted server code with no request to attribute to, so it keeps supplying its own hostname and still requires one.

The `hostname` option on `native()` takes three forms.

#### `'request'`

The default, and the whole rule above:

```ts
native({ hostname: 'request' })
```

#### A list

The request host is stored only when the list holds it, and the event is dropped otherwise:

```ts
native({ hostname: ['example.com', 'www.example.com'] })
```

Entries are bare hostnames, lowercased at boot: a scheme or a port in an entry fails the boot rather than silently matching nothing, and an empty list is refused for the same reason. **This is the form to use on a single-site install with no `scopeResolver` and no edge that validates `Host`.** There, `Host` is exactly as forgeable as the body was, and the list is the only thing that bounds which hostnames can be written.

#### A resolver

```ts
native({
  hostname: async ({ req, scope }) => {
    // A split deployment: the page is on the tenant's domain, the API is not, so the
    // page's own origin is validated against what the scope already resolved. `claimed`,
    // the body's own hostname, is available here too and is the one value never trusted.
    const origin = req.headers.get('origin')
    return origin && (await tenantOwnsOrigin(req, scope, origin)) ? new URL(origin).hostname : null
  },
})
```

It receives the body's claim, the request, and the scope the request already resolved to, and returns the hostname to store or `null` to drop the event. The answer is normalized and capped like any other, and a resolver that throws drops the event too: ingest is a public path, so a broken lookup loses one event rather than the response.

#### Scoped installs and `platformHostnames`

On an install with a `scopeResolver`, an event whose request resolves no scope is dropped. Nothing is listed for that: a tenant who adds a custom domain is counted the moment the tenant document is saved, because the rule is "the request resolved to a tenant" and that lookup is the install's own. See [Multi-tenancy](/analytics/multi-tenancy#capture-slots-per-tenant) for the resolver to write.

`platformHostnames` is the exception, and it is a static list on purpose:

```ts
native({ platformHostnames: ['app.example.com', 'www.example.com'] })
```

Those are the platform's own domains, which are infrastructure rather than tenants: they change with a deploy, not with a signup, so listing them costs nothing. A request from one of them ingests under the null scope even though it resolves no tenant. Tenant domains never belong here.

<Callout type="info">
**A dropped event answers exactly what an accepted one answers**: `202` with `{ "ok": true }`, the same headers, and nothing logged. A prober therefore learns nothing about which hosts or tenants exist, and a public endpoint is not a log amplifier. The cost is that a misconfigured `hostname` list or resolver is silent: if events stop arriving, check the option before the tracker.
</Callout>

### Trusted proxies

`trustedProxyHops` is a plugin option rather than a native one, because the same client address is read by the native visitor hash, by the [geo resolvers](/analytics/geo), and by the [capture proxy](/analytics/proxy#runtime-endpoint):

```ts
analytics({ adapters: [native()], trustedProxyHops: 1 })
```

Unset, the leftmost `x-forwarded-for` entry is used, which is correct for honest traffic and is whatever the client wrote for the rest. Set to `n`, the entry `n` from the right is used, which is the address the outermost trusted proxy saw, and a chain shorter than `n` yields no address rather than falling back to the client-writable `x-real-ip`. It also lets the native ingest read `x-forwarded-host` for the event's hostname. It must be a non-negative integer or the boot fails.

There is no default of 1. An install behind a CDN plus a proxy would then read the CDN's address for every visitor, collapsing geo and the visitor hash onto one value, which is worse than a spoofable one. Count the hops your own deployment actually has.

## Dimensions

Everything the engine can know about a hit is classified once, at ingest, and stored on the event row. A breakdown then reads the stored value rather than re-deriving it, so the day-bucketed rollups and the raw-event path can never disagree about what a bucket is called.

| Dimension | Derived from | Stored as |
|---|---|---|
| `page` | the event's `path` | verbatim, capped at 512 |
| `referrer` | the referring URL's host | lowercased, `www.` stripped, capped at 253; nothing for a same-site referral |
| `source` | `utm_source`, else the referrer host | the visit's named origin, lowercased: the tag (capped at 128), the host, or `direct` when it has neither |
| `channel` | `utm_medium`, the ad click ids, `utm_source` and the referrer host | one of the twelve [traffic channel](#traffic-channels) tokens, lowercase |
| `utmSource`, `utmMedium`, `utmCampaign`, `utmContent`, `utmTerm` | the `query` field's `utm_*` keys | decoded, trimmed, case as sent, capped at 128 |
| `device` | `user-agent` | `desktop`, `mobile`, `tablet` |
| `browser` | `user-agent` | `chrome`, `safari`, `firefox`, `edge`, `opera`, `samsung`, `other` |
| `os` | `user-agent` | `ios`, `android`, `windows`, `macos`, `linux`, `chromeos`, `other` |
| `country`, `region`, `city` | the [geo resolvers](/analytics/geo) | as the resolver reports them, each capped at 128 |
| `language` | the first `accept-language` tag | lowercased without its `q` factor (`de-de`), capped at 16 |
| `event` | a custom event's `name` | verbatim, capped at 128 |
| `goal` | the [goals](/analytics/goals) the event completed | a json column: groupable, but the one dimension a filter cannot name |

A dimension the event does not carry emits no bucket at all, so an unattributed hit never lands in an "unknown" row. Keys are capped because each value becomes a rollup bucket key: an uncapped one exceeds Mongo's index key limit, and on Postgres a btree key over 2704 bytes fails the write outright.

Every cap is applied server-side, on a public endpoint, so a hand-rolled body cannot get past it. `browser`, `os` and `language` come off the request headers, so a [server-side event](/analytics/goals#4-track-from-server-code) without a request reports none of them rather than inventing a visitor.

### Referrers

Three things happen to a referrer:

- **`referrer` on the event row** keeps the origin and the path, with everything from the first `#` or `?` onwards removed, capped at 512. A same-origin navigation puts the previous page's whole URL in `document.referrer`, so the query string routinely carries a reset token or an email address; stripping it is what keeps that out of the events collection.
- **The `referrer` dimension** groups by the bare host: lowercased, no scheme, port, path or `www.`. A **same-site referral reports no host at all**, so a site's own domain can never top its referrers breakdown.
- **The `source` dimension** is the visit's named origin: its `utm_source` tag when it carries one, else the referrer host, else `direct`. That is what `source` means on Plausible (`visit:source`) and GA4 (`sessionSource`), so a report reads the same column whichever source answered it. The tag is lowercased and capped at 128 characters like every other campaign key, so `utm_source=Newsletter` and `utm_source=newsletter` are one row while the `utmSource` dimension keeps the tag as written; the host arrives lowercased and `www.`-stripped from the `referrer` dimension's own derivation. A campaign tagged `utm_source=direct` shares the `direct` bucket with untagged traffic.
- **The `channel` dimension** is the acquisition channel that origin classifies into, which is what a report is usually asked for ("how much of last month was paid search?").

### Traffic channels

`channel` holds one of twelve lowercase tokens: `direct`, `organic-search`, `paid-search`, `organic-social`, `paid-social`, `organic-video`, `paid-video`, `email`, `affiliate`, `display`, `referral`, `paid-other`. Paid is split per platform rather than pooled, because that is the split every vendor reports and the one a budget question is asked in.

A hit is classified once, at ingest. First the **platform** is resolved, then the rules run in order:

- **Platform** is the family the visit's origin belongs to: `search`, `social` or `video`. It comes from the referrer host matched against the built-in lists below, and from `utm_source` matched by name when there is no referrer host at all. An `fbclid` with no referrer host also names `social`, which is the in-app browser case it exists to cover.

1. **A paid `utm_medium`** wins outright, because a campaign states its own channel and the referrer host is then only its last hop. `cpc` and `ppc` say "paid" and nothing more; `paidsearch`, `paid-search`, `paid_search`, `paidsocial`, `paid-social`, `paid_social`, `paidvideo`, `paid-video` and `paid_video` name their platform themselves, and any other medium starting with `paid` says "paid" and nothing more. The platform is taken from the medium, else from a paid click id, else from the platform resolved above, else from `utm_source` by name, which is what keeps an ad click arriving through a network's own redirect host on its platform. With no platform at all the visit is `paid-other`. A referrer host that names a platform wins over the tag, so `utm_medium=cpc` from `facebook.com` tagged `utm_source=google` is `paid-social`; GA4 and Plausible classify that visit from the tag instead.
2. **Any other known `utm_medium`**, trimmed and lowercased, classifies directly: `email` and `newsletter` are `email`, `affiliate` and `affiliates` are `affiliate`, `display`, `banner`, `cpm`, `retargeting` and `remarketing` are `display`, `social`, `social-media` and `sm` are `organic-social`, `organic` and `search` are `organic-search`. Any other medium falls through to the rules below, so `utm_medium=referral` with no referrer is `direct` rather than `referral`.
3. **A paid click id** in the page's query string with a non-empty value, matched case-insensitively: `gclid`, `gbraid` and `wbraid` (Google Ads) and `msclkid` (Microsoft Ads) are `paid-search`; `ttclid` (TikTok Ads) is `paid-social`. An ad click carries one whatever host it bounced through. A valueless `?gclid=` is not a click.
4. **The platform**, organically: `organic-search`, `organic-social` or `organic-video`.
5. **`referral`** for any other referrer host, and **`direct`** when there is no usable host at all (none sent, unparseable, or the site itself).

`fbclid` is **not** a paid signal. Facebook appends it to every outbound link, organic posts included, so it proves the platform and never the spend: with no referrer host, and when no `utm_source` names a platform either, it names the social platform inside whichever branch the other signals chose (`utm_medium=cpc` and an `fbclid` is `paid-social`), and a hit carrying nothing but `fbclid` is `organic-social`.

The host lists: search is `bing.com`, `duckduckgo.com`, `baidu.com`, `ecosia.org`, `search.brave.com`, `qwant.com`, `startpage.com`, `naver.com`, `seznam.cz`, `sogou.com`, plus the `google`, `yahoo` and `yandex` brands. Social is `facebook.com`, `fb.com`, `instagram.com`, `twitter.com`, `x.com`, `t.co`, `linkedin.com`, `lnkd.in`, `reddit.com`, `tiktok.com`, `threads.net`, `mastodon.social`, `bsky.app`, `web.telegram.org`, `t.me`, `wa.me`, `whatsapp.com`, plus the `pinterest` brand. Video is `youtube.com`, `youtu.be` and `vimeo.com`. Subdomains of a listed host count. The same platforms are matched by name for `utm_source`, and a `utm_source` spelled as a domain is matched as one, so `utm_source=google.com` is not an unknown.

The brands that run one site per country are matched on the label rather than a fixed suffix: `google.de`, `google.co.uk` and `news.google.com` are search, while `google.evil.com` is not, because the label must be followed by exactly one more label, or by two when the first is a registrar second level (`co`, `com`, `net`, `org`, `ac`, `gov`, `edu`).

Webmail hosts (`mail.google.com`, `mail.yahoo.com`, `outlook.live.com`, `outlook.office.com`, `mail.proton.me`) belong to no platform, so a visit from one is `referral` rather than `email`. A referrer proves a link was opened in a mail client, never that the mail was the newsletter an `email` bucket would take credit for.

Every event also stores `channelVersion`, the version of the rules that classified it. It exists so that a later task that reclassifies stored rows can find the ones an older rule set decided; nothing reads it today, and it is stamped on events only, never on rollups.

<Callout type="warn">
**Nothing is backfilled.** Rows written before this release stored a traffic channel in `source` (one of the earlier six tokens: `direct`, `search`, `social`, `email`, `paid`, `referral`) and carry no `channel` at all. A Sources tab spanning the upgrade therefore mixes those tokens with origins until the older days age out of the window, and a channel breakdown starts at the upgrade rather than at the beginning of your data.
</Callout>

The tokens are what is stored, filtered and put in a URL; the admin renders them through [typed translations](/analytics/i18n), so a channel breakdown reads **Paid search** or **Direct** in the reader's language. A `source` row is shown as it was stored, except `direct`, which renders through the same translated label.

## Write batching (opt-in)

By default each ingest is persisted before the endpoint responds. Under load, batch writes in memory:

```ts
native({ buffer: true }) // flush at 50 events or 2000 ms, whichever first
native({ buffer: { maxSize: 100, maxAgeMs: 1000 } })
```

Batching coalesces per-bucket upserts and cuts database round trips. The trade is durability: the endpoint responds before the batch is persisted, so a hard crash can lose up to `maxAgeMs` of events (the same best-effort model Plausible and Umami use). Call `native().flush()` on graceful shutdown to drain the buffer; keep a reference to the adapter instance if you need to.

Whether or not you opt in, **every flush writes its rollup buckets and its seen-ledger rows in a handful of statements**, not one per bucket. The rollup upserts go out as two multi-row statements, the counters and then the visitor and session increments the ledger gate just granted (a Mongo `bulkWrite`, a Postgres `ON CONFLICT DO UPDATE` that reads each row's own increments), and the ledger's insert-if-new gate as a single `insertMany` / `ON CONFLICT DO NOTHING ... RETURNING`. A fully attributed pageview therefore costs 4 round trips rather than the 161 the bucket-at-a-time path needed, and a buffered batch pays those three writes once for the whole batch, though each event row is still its own insert. Counting is unchanged: bumps landing on the same bucket are summed before the statement goes out, which Postgres requires anyway, since it rejects a statement whose `DO UPDATE` would touch one row twice.

## Uniques and sessions

Distinct counts are exact per UTC day: a dedicated `analytics-seen` ledger records first-sightings at every granularity they are queried (per page, site-wide, site-wide per country), so uniques are read directly, never summed across breakdowns. Across a multi-day range the daily counts are summed, so longer-range uniques are approximate, the same trade Plausible, Fathom, and Umami make.

### Production note (Mongo)

Exact distinct counting relies on a unique index on `analytics-seen` being live under concurrent ingestion. Configure the Mongoose adapter with `ensureIndexes: true`:

```ts
import { mongooseAdapter } from '@payloadcms/db-mongodb'

mongooseAdapter({ url: process.env.DATABASE_URI, ensureIndexes: true })
```

On Postgres the unique index comes from migrations; nothing extra is needed once they have run.

## Filters and hour granularity

`AnalyticsQuery.filters` narrows a read to matching raw events, honored on **every dimension above except `goal`** with the `eq` and `contains` operators (`contains` is case-insensitive on both Mongo and Postgres; on Postgres `%` and `_` in the value act as wildcards, while Mongo escapes them; a `matches` filter is dropped, since native has no regex engine over stored events). `contains` on `source` takes a free-text value like any other dimension, so that same `%` and `_` difference applies to it. `granularity: 'hour'` buckets a series into UTC hours instead of days.

Both a filtered read and an hour-granularity read bypass the day-bucketed rollups and aggregate raw events directly, so they are bounded by [retention](#retention-pruning): a range reaching further back than `retentionDays` is clamped, and the read is capped at the same 50,000-event window as realtime, past which `meta.sampled` reports `true`. `realtime()` scans raw events under that same cap and sets `meta.sampled` the same way. An unfiltered, day-granularity read still comes from the exact rollup buckets and has no such cap. Hour buckets floor to the UTC hour regardless of `reportingTimezone`; day buckets stay timezone-aligned. `binding.hostname` (see [display fields](/analytics/display-fields)) filters both paths.

## Hostname buckets

Rollups are keyed by hostname: every delta write emits both a hostname-less bucket family and a per-hostname family, so `binding.hostname` filters native reads with exact unique counts instead of an approximation. This doubles rollup storage for installs that ingest from more than one hostname, one extra bucket set per distinct hostname.

## Geo resolution

The engine resolves country, region, and city per event: platform headers first (Vercel, Cloudflare), MaxMind only when headers do not supply a country. Pass `geoDbPath` for MaxMind or `geoResolver` for a custom pipeline. Details on [Geo](/analytics/geo).

## Retention pruning

Raw events are kept indefinitely unless you opt in to pruning:

```ts
native({ retentionDays: 90 })
```

This registers a Payload task (`analytics-prune-events`) on a nightly schedule (03:00 UTC) that deletes raw `analytics-events` and `analytics-seen` rows older than the window. Rollups are untouched, so long-range aggregates survive pruning. Like all scheduled work here, the task fires only if Payload's jobs runner is active (cron `autoRun`, a [worker](/jobs/workers), or an external scheduler).

<Callout type="info">
`retentionDays` covers the events and the seen ledger, and nothing else. **Rollups are never pruned**, by design, and they now grow per day with the cardinality of the new dimensions: one row per distinct referrer host, `source`, city, campaign, `utmContent` and `utmTerm` you receive, plus one extra bucket set per distinct hostname you ingest from. `source` is the one to watch, since it holds whatever `utm_source` a visit was tagged with: its cardinality is bounded only by the 128-character cap, not by a fixed vocabulary the way `channel` is. A site with a long tail of campaign URLs should plan storage for that tail rather than assume a retention window bounds it.
</Callout>

## Upgrading an existing install

The hostname bucket family above adds a required `hostname` column to `analytics-rollups`; the [sync tier](/analytics/sync) separately adds a required `scope` column to its collection. Existing installs need a migration backfilling both to `''` (the hostname-less / no-scope sentinel):

```ts
import type { MigrateUpArgs } from '@payloadcms/db-mongodb'

export async function up({ payload }: MigrateUpArgs): Promise<void> {
  if (payload.db.name === 'mongoose') {
    const db = payload.db as unknown as {
      collections: Record<string, { collection: { updateMany: (f: object, u: object) => Promise<unknown> } }>
    }
    await db.collections['analytics-rollups']?.collection.updateMany(
      { hostname: { $exists: false } },
      { $set: { hostname: '' } }
    )
    await db.collections['analytics-daily']?.collection.updateMany(
      { scope: { $exists: false } },
      { $set: { scope: '' } }
    )
    return
  }
  const db = payload.db as unknown as { drizzle: { execute: (q: string) => Promise<unknown> } }
  await db.drizzle.execute(
    `ALTER TABLE analytics_rollups ADD COLUMN IF NOT EXISTS hostname varchar NOT NULL DEFAULT ''`
  )
  await db.drizzle.execute(
    `ALTER TABLE analytics_daily ADD COLUMN IF NOT EXISTS scope varchar NOT NULL DEFAULT ''`
  )
}
```

Push-mode dev installs pick up the new columns and the widened unique indexes (rollups gain `hostname`; sync's becomes `source + date + scope`) automatically on next boot; the snippet above is for migrate-mode installs, where a schema push never runs. On Postgres, migrate-mode installs also need to rebuild both unique indexes to include the new column: Payload only creates them from the current config on a fresh index build, so an existing production Postgres install keeps its old `(granularity, period, path, dimension, dimvalue)` and `(source, date)` unique indexes until this migration (or a follow-up one) drops and recreates them with `hostname` and `scope` appended.

The two consequences of skipping that rebuild are not the same. Rollups write through `ON CONFLICT`, and the conflict target must match the unique index exactly; once the config declares `hostname` in the target list but the live index still lacks it, Postgres cannot infer an arbiter index for the conflict, and **every** native rollup write fails, not just the ones that would collide, with error `42P10` (`no unique or exclusion constraint matching the ON CONFLICT specification`). The sync collection instead upserts via a find-then-create, so its stale `(source, date)` index does not reject writes outright; rows that only differ by `scope` can still collide against it and stomp on each other's synced values.

Previously-scoped rollups installs already carry `scope` on their old index, so their rebuilt index is `(granularity, period, path, dimension, dimvalue, hostname, scope)`, not just `(..., hostname)`.

Rebuild the indexes explicitly. `payload migrate:create` in the consumer app will typically generate the equivalent DDL automatically once the collection config above is in place; the statements below are the Postgres shape it produces, for reference or for a hand-written migration. Index names are assigned by Payload/Drizzle per install and can differ from the ones below, so confirm the actual name first with `\d analytics_rollups` (or `\d analytics_daily`) before dropping anything:

```sql
DROP INDEX IF EXISTS analytics_rollups_granularity_period_path_dimension_dimvalue_idx;
CREATE UNIQUE INDEX analytics_rollups_bucket_idx
  ON analytics_rollups (granularity, period, path, dimension, dimvalue, hostname);
DROP INDEX IF EXISTS analytics_daily_source_date_idx;
CREATE UNIQUE INDEX analytics_daily_source_date_scope_idx
  ON analytics_daily (source, date, scope);
```

If your `sync` config sets a custom `collectionSlug`, adjust the `analytics-daily` table/collection name in both the migration snippet and the DDL above to match; the reference migration only knows the default slug.

## Upgrading for goal metrics

Goal support adds four required numeric counters to `analytics-rollups` (`conversions`, `revenue`, `scrollDepthSum`, `scrollSamples`, all defaulting to 0), four optional fields to `analytics-events` (`value`, `currency`, `scrollDepth`, `goals`), and the `goal` member of the events `type` select. Push-mode dev installs pick all of that up on the next boot; migrate-mode installs need a migration. This one mirrors the plugin's own:

```ts
import type { MigrateUpArgs } from '@payloadcms/db-mongodb'

export async function up({ payload }: MigrateUpArgs): Promise<void> {
  if (payload.db.name === 'mongoose') {
    const db = payload.db as unknown as {
      collections: Record<string, { collection: { updateMany: (f: object, u: object) => Promise<unknown> } }>
    }
    // One pass per counter, each matching only its own absence, so a row half-patched by
    // an interrupted run is completed without resetting what it already carries.
    for (const counter of ['conversions', 'revenue', 'scrollDepthSum', 'scrollSamples']) {
      await db.collections['analytics-rollups']?.collection.updateMany(
        { [counter]: { $exists: false } },
        { $set: { [counter]: 0 } }
      )
    }
    return
  }
  const db = payload.db as unknown as { drizzle: { execute: (q: string) => Promise<unknown> } }
  for (const column of ['conversions', 'revenue', 'scroll_depth_sum', 'scroll_samples']) {
    await db.drizzle.execute(
      `ALTER TABLE analytics_rollups ADD COLUMN IF NOT EXISTS ${column} numeric NOT NULL DEFAULT 0`
    )
  }
  await db.drizzle.execute(`ALTER TABLE analytics_events ADD COLUMN IF NOT EXISTS value numeric`)
  await db.drizzle.execute(`ALTER TABLE analytics_events ADD COLUMN IF NOT EXISTS currency varchar`)
  await db.drizzle.execute(`ALTER TABLE analytics_events ADD COLUMN IF NOT EXISTS scroll_depth numeric`)
  await db.drizzle.execute(`ALTER TABLE analytics_events ADD COLUMN IF NOT EXISTS goals jsonb`)
  await db.drizzle.execute(`ALTER TYPE enum_analytics_events_type ADD VALUE IF NOT EXISTS 'goal'`)
}
```

Mongo needs only the rollup backfill: an absent event field is simply absent there. Every statement is idempotent, so running it against a schema that already has the columns is a no-op.

Two Postgres details worth keeping if you hand-write your own version. The statements go through `payload.db.drizzle`, the pool handle, rather than the transaction-bound `db` argument, so each one autocommits; that is what keeps `ALTER TYPE ... ADD VALUE` out of an open transaction and lets the new enum member be usable straight away. And the migration is deliberately irreversible: Postgres cannot drop an enum member once it exists, so `down` does nothing.

Rows written before the migration read back as zero rather than `NaN`, so an install that has not run it yet reports 0 conversions instead of breaking, but it cannot ingest a `goal` event on Postgres until the enum member exists.

## Upgrading for dimension columns

Serving the dimensions above adds eleven optional fields to `analytics-events`: `browser`, `os`, `language`, the five `utm*` keys, `referrerHost` (the bare host the `referrer` dimension reads, derived at ingest because a `where` cannot reduce a URL to its host at read time), `channel`, and the numeric `channelVersion` beside it. The rollups collection is unchanged, since its rows are keyed by `(dimension, dimvalue)` text columns.

Mongo needs nothing: the fields are optional, and an event written before this release simply carries none of them, which is already what "no bucket for that dimension" means. Push-mode dev installs pick the columns up on the next boot. A migrate-mode Postgres install needs this, which is the plugin's own migration statement for statement:

```ts
import type { MigrateDownArgs, MigrateUpArgs } from '@payloadcms/db-mongodb'

export async function up({ payload }: MigrateUpArgs): Promise<void> {
  if (payload.db.name === 'mongoose') {
    return
  }
  const db = payload.db as unknown as { drizzle: { execute: (query: string) => Promise<unknown> } }
  for (const column of [
    'browser',
    'os',
    'language',
    'utm_source',
    'utm_medium',
    'utm_campaign',
    'utm_content',
    'utm_term',
    'referrer_host',
    'channel',
  ]) {
    await db.drizzle.execute(
      `ALTER TABLE analytics_events ADD COLUMN IF NOT EXISTS ${column} varchar`
    )
  }
  await db.drizzle.execute(
    `ALTER TABLE analytics_events ADD COLUMN IF NOT EXISTS channel_version numeric`
  )
}

/** Deliberately irreversible: dropping the columns would discard already-attributed events. */
export async function down(_args: MigrateDownArgs): Promise<void> {}
```

Every statement is `ADD COLUMN IF NOT EXISTS`, so the migration is re-runnable and leaves a push-mode schema alone. Events ingested before it runs keep their old attribution: nothing backfills a browser onto a row whose user agent was never stored, so the new breakdowns start at the migration rather than at the beginning of your data.
