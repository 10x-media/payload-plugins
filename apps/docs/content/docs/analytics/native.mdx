title: Native engine
description: Self-hosted, cookieless analytics stored inside Payload.

`native()` is an adapter that stores analytics in your own database. No external service, no cookies, no client fingerprinting beyond a salted daily visitor hash.

```ts title="payload.config.ts"
import { analytics } from '@10x-media/analytics'
import { native } from '@10x-media/analytics/adapters/native'

analytics({ adapters: [native()] })
```

Registering it adds three hidden collections (`analytics-events`, `analytics-rollups`, `analytics-seen`) and a public beacon endpoint. Metrics served: `pageviews`, `visitors`, `sessions`, `events`, `avgDuration`, `conversions`, `revenue`, `scrollDepth`. Dimensions: `page`, `country`, `source`, `device`, `event`, `goal`. Realtime is supported.

## The ingest endpoint

`POST /api/analytics/ingest` (path configurable via `ingestPath`) accepts one event per request. The plugin's own [browser tracker](/analytics/capture) posts exactly this shape:

```ts
interface RawEventInput {
  type: 'pageview' | 'event' | 'goal'
  path: string          // required
  hostname: string      // required
  name?: string         // event name, or the goal slug; required unless type is 'pageview'
  referrer?: string
  durationMs?: number
  props?: Record<string, unknown>
  value?: number        // revenue for a goal completion, in `currency`
  currency?: string     // ISO 4217
  scrollDepth?: number  // deepest scroll on a pageview, 0-100
}
```

An event is rejected only on its required fields: a known `type`, a non-empty string `path` and `hostname`, and a non-empty string `name` on everything but a pageview. Optional fields are sanitized rather than rejected, so one malformed attribute costs an attribute instead of the whole event: `value` must be a finite number `>= 0`, `currency` must match `/^[A-Z]{3}$/`, `scrollDepth` is clamped to 100 and rounded, `name` is truncated to 128 characters (it is the `event` dimension's bucket key), and `props` keeps at most 20 flat scalar entries with keys up to 64 characters and string values truncated to 256.

The server derives the rest at ingest time: device class from the user agent, traffic source from the referrer, geo from [resolvers](/analytics/geo), a salted daily visitor hash (the salt rotates per UTC day, so visitors cannot be tracked across days), and the [goals](/analytics/goals) the event completed, stamped onto the stored event. The endpoint responds `202` on success and `400` on an invalid body.

A `goal` event counts under `events`, never under `pageviews`, and is kept out of the `event` dimension breakdown: its name is a goal slug, and it appears under the `goal` dimension instead. `revenue` is summed as a plain number in the event's own currency, with no conversion; see the currency note on [Goals](/analytics/goals#how-native-reports-them). `scrollDepth` averages over the pageviews that actually reported one, tracked by its own sample counter so a pageview whose tracker never sent a depth does not drag the average down.

Events are written atomically, via `$inc` on Mongo and `ON CONFLICT DO UPDATE` on Postgres, so concurrent ingestion is safe.

## Write batching (opt-in)

By default each ingest is persisted before the endpoint responds. Under load, batch writes in memory:

```ts
native({ buffer: true }) // flush at 50 events or 2000 ms, whichever first
native({ buffer: { maxSize: 100, maxAgeMs: 1000 } })
```

Batching coalesces per-bucket upserts and cuts database round trips. The trade is durability: the endpoint responds before the batch is persisted, so a hard crash can lose up to `maxAgeMs` of events (the same best-effort model Plausible and Umami use). Call `native().flush()` on graceful shutdown to drain the buffer; keep a reference to the adapter instance if you need to.

## Uniques and sessions

Distinct counts are exact per UTC day: a dedicated `analytics-seen` ledger records first-sightings at every granularity they are queried (per page, site-wide, site-wide per country), so uniques are read directly, never summed across breakdowns. Across a multi-day range the daily counts are summed, so longer-range uniques are approximate, the same trade Plausible, Fathom, and Umami make.

### Production note (Mongo)

Exact distinct counting relies on a unique index on `analytics-seen` being live under concurrent ingestion. Configure the Mongoose adapter with `ensureIndexes: true`:

```ts
import { mongooseAdapter } from '@payloadcms/db-mongodb'

mongooseAdapter({ url: process.env.DATABASE_URI, ensureIndexes: true })
```

On Postgres the unique index comes from migrations; nothing extra is needed once they have run.

## Filters and hour granularity

`AnalyticsQuery.filters` narrows a read to matching raw events, honored on `page`, `country`, `region`, `city`, `device`, `source`, and `event` with the `eq` and `contains` operators (`contains` is case-insensitive on both Mongo and Postgres; on Postgres `%` and `_` in the value act as wildcards, while Mongo escapes them; a `matches` filter is dropped, since native has no regex engine over stored events). `granularity: 'hour'` buckets a series into UTC hours instead of days.

Both a filtered read and an hour-granularity read bypass the day-bucketed rollups and aggregate raw events directly, so they are bounded by [retention](#retention-pruning): a range reaching further back than `retentionDays` is clamped, and the read is capped at the same 50,000-event window as realtime, past which `meta.sampled` reports `true`. An unfiltered, day-granularity read still comes from the exact rollup buckets and has no such cap. Hour buckets floor to the UTC hour regardless of `reportingTimezone`; day buckets stay timezone-aligned. `binding.hostname` (see [display fields](/analytics/display-fields)) filters both paths.

## Hostname buckets

Rollups are keyed by hostname: every delta write emits both a hostname-less bucket family and a per-hostname family, so `binding.hostname` filters native reads with exact unique counts instead of an approximation. This doubles rollup storage for installs that ingest from more than one hostname, one extra bucket set per distinct hostname.

## Geo resolution

The engine resolves country, region, and city per event: platform headers first (Vercel, Cloudflare), MaxMind only when headers do not supply a country. Pass `geoDbPath` for MaxMind or `geoResolver` for a custom pipeline. Details on [Geo](/analytics/geo).

## Retention pruning

Raw events are kept indefinitely unless you opt in to pruning:

```ts
native({ retentionDays: 90 })
```

This registers a Payload task (`analytics-prune-events`) on a nightly schedule (03:00 UTC) that deletes raw `analytics-events` and `analytics-seen` rows older than the window. Rollups are untouched, so long-range aggregates survive pruning. Like all scheduled work here, the task fires only if Payload's jobs runner is active (cron `autoRun`, a [worker](/jobs/workers), or an external scheduler).

## Upgrading an existing install

The hostname bucket family above adds a required `hostname` column to `analytics-rollups`; the [sync tier](/analytics/sync) separately adds a required `scope` column to its collection. Existing installs need a migration backfilling both to `''` (the hostname-less / no-scope sentinel):

```ts
import type { MigrateUpArgs } from '@payloadcms/db-mongodb'

export async function up({ payload }: MigrateUpArgs): Promise<void> {
  if (payload.db.name === 'mongoose') {
    const db = payload.db as unknown as {
      collections: Record<string, { collection: { updateMany: (f: object, u: object) => Promise<unknown> } }>
    }
    await db.collections['analytics-rollups']?.collection.updateMany(
      { hostname: { $exists: false } },
      { $set: { hostname: '' } }
    )
    await db.collections['analytics-daily']?.collection.updateMany(
      { scope: { $exists: false } },
      { $set: { scope: '' } }
    )
    return
  }
  const db = payload.db as unknown as { drizzle: { execute: (q: string) => Promise<unknown> } }
  await db.drizzle.execute(
    `ALTER TABLE analytics_rollups ADD COLUMN IF NOT EXISTS hostname varchar NOT NULL DEFAULT ''`
  )
  await db.drizzle.execute(
    `ALTER TABLE analytics_daily ADD COLUMN IF NOT EXISTS scope varchar NOT NULL DEFAULT ''`
  )
}
```

Push-mode dev installs pick up the new columns and the widened unique indexes (rollups gain `hostname`; sync's becomes `source + date + scope`) automatically on next boot; the snippet above is for migrate-mode installs, where a schema push never runs. On Postgres, migrate-mode installs also need to rebuild both unique indexes to include the new column: Payload only creates them from the current config on a fresh index build, so an existing production Postgres install keeps its old `(granularity, period, path, dimension, dimvalue)` and `(source, date)` unique indexes until this migration (or a follow-up one) drops and recreates them with `hostname` and `scope` appended.

The two consequences of skipping that rebuild are not the same. Rollups write through `ON CONFLICT`, and the conflict target must match the unique index exactly; once the config declares `hostname` in the target list but the live index still lacks it, Postgres cannot infer an arbiter index for the conflict, and **every** native rollup write fails, not just the ones that would collide, with error `42P10` (`no unique or exclusion constraint matching the ON CONFLICT specification`). The sync collection instead upserts via a find-then-create, so its stale `(source, date)` index does not reject writes outright; rows that only differ by `scope` can still collide against it and stomp on each other's synced values.

Previously-scoped rollups installs already carry `scope` on their old index, so their rebuilt index is `(granularity, period, path, dimension, dimvalue, hostname, scope)`, not just `(..., hostname)`.

Rebuild the indexes explicitly. `payload migrate:create` in the consumer app will typically generate the equivalent DDL automatically once the collection config above is in place; the statements below are the Postgres shape it produces, for reference or for a hand-written migration. Index names are assigned by Payload/Drizzle per install and can differ from the ones below, so confirm the actual name first with `\d analytics_rollups` (or `\d analytics_daily`) before dropping anything:

```sql
DROP INDEX IF EXISTS analytics_rollups_granularity_period_path_dimension_dimvalue_idx;
CREATE UNIQUE INDEX analytics_rollups_bucket_idx
  ON analytics_rollups (granularity, period, path, dimension, dimvalue, hostname);
DROP INDEX IF EXISTS analytics_daily_source_date_idx;
CREATE UNIQUE INDEX analytics_daily_source_date_scope_idx
  ON analytics_daily (source, date, scope);
```

If your `sync` config sets a custom `collectionSlug`, adjust the `analytics-daily` table/collection name in both the migration snippet and the DDL above to match; the reference migration only knows the default slug.

## Upgrading for goal metrics

Goal support adds four required numeric counters to `analytics-rollups` (`conversions`, `revenue`, `scrollDepthSum`, `scrollSamples`, all defaulting to 0), four optional fields to `analytics-events` (`value`, `currency`, `scrollDepth`, `goals`), and the `goal` member of the events `type` select. Push-mode dev installs pick all of that up on the next boot; migrate-mode installs need a migration. This one mirrors the plugin's own:

```ts
import type { MigrateUpArgs } from '@payloadcms/db-mongodb'

export async function up({ payload }: MigrateUpArgs): Promise<void> {
  if (payload.db.name === 'mongoose') {
    const db = payload.db as unknown as {
      collections: Record<string, { collection: { updateMany: (f: object, u: object) => Promise<unknown> } }>
    }
    // One pass per counter, each matching only its own absence, so a row half-patched by
    // an interrupted run is completed without resetting what it already carries.
    for (const counter of ['conversions', 'revenue', 'scrollDepthSum', 'scrollSamples']) {
      await db.collections['analytics-rollups']?.collection.updateMany(
        { [counter]: { $exists: false } },
        { $set: { [counter]: 0 } }
      )
    }
    return
  }
  const db = payload.db as unknown as { drizzle: { execute: (q: string) => Promise<unknown> } }
  for (const column of ['conversions', 'revenue', 'scroll_depth_sum', 'scroll_samples']) {
    await db.drizzle.execute(
      `ALTER TABLE analytics_rollups ADD COLUMN IF NOT EXISTS ${column} numeric NOT NULL DEFAULT 0`
    )
  }
  await db.drizzle.execute(`ALTER TABLE analytics_events ADD COLUMN IF NOT EXISTS value numeric`)
  await db.drizzle.execute(`ALTER TABLE analytics_events ADD COLUMN IF NOT EXISTS currency varchar`)
  await db.drizzle.execute(`ALTER TABLE analytics_events ADD COLUMN IF NOT EXISTS scroll_depth numeric`)
  await db.drizzle.execute(`ALTER TABLE analytics_events ADD COLUMN IF NOT EXISTS goals jsonb`)
  await db.drizzle.execute(`ALTER TYPE enum_analytics_events_type ADD VALUE IF NOT EXISTS 'goal'`)
}
```

Mongo needs only the rollup backfill: an absent event field is simply absent there. Every statement is idempotent, so running it against a schema that already has the columns is a no-op.

Two Postgres details worth keeping if you hand-write your own version. The statements go through `payload.db.drizzle`, the pool handle, rather than the transaction-bound `db` argument, so each one autocommits; that is what keeps `ALTER TYPE ... ADD VALUE` out of an open transaction and lets the new enum member be usable straight away. And the migration is deliberately irreversible: Postgres cannot drop an enum member once it exists, so `down` does nothing.

Rows written before the migration read back as zero rather than `NaN`, so an install that has not run it yet reports 0 conversions instead of breaking, but it cannot ingest a `goal` event on Postgres until the enum member exists.

## Options

| Option | Type | Default | Description |
|---|---|---|---|
| `buffer` | `boolean \| { maxSize?, maxAgeMs? }` | off | In-memory write batching (50 events / 2000 ms). |
| `geoDbPath` | `string` | none | Path to a MaxMind `.mmdb`; enables IP-level geo lookup. |
| `geoResolver` | `GeoResolver` | platform headers (+ MaxMind when `geoDbPath` set) | Custom geo pipeline. |
| `ingestPath` | `string` | `/analytics/ingest` | Beacon endpoint path (served under `/api`). The tracker config follows it, so the browser posts to the moved mount. |
| `retentionDays` | `number` | keep forever | Nightly pruning window for raw events. |
