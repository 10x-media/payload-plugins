1.0.0-beta.16 removes no option. It adds one collection, `analytics-provider-status`, which keeps each provider document's last connection result, so Postgres and SQLite in migrate mode need one migration. The other changes are in what provider documents read from and what tenants see when one fails.

## Before you start

Work through these in order; each links to its details below. The commands use pnpm; with npm run `npx payload ...`, with yarn `yarn payload ...`.

1. **On Postgres or SQLite in migrate mode, generate and run a migration** ([The migration](#the-migration)). Push mode and MongoDB need nothing.
2. **Regenerate the import map** (`pnpm payload generate:importmap`): the provider form renders a new Connection panel.
3. **Pick a Region on every PostHog provider document whose Host is blank** ([PostHog's Region](#posthogs-region)).
4. **Under a `fallback` policy, know what a tenant with a failing source now sees** ([Failing sources under `fallback`](#failing-sources-under-fallback)).

## The migration

On Postgres or SQLite in migrate mode, generate a migration (`pnpm payload migrate:create`), review it and run it (`pnpm payload migrate`). It creates the `analytics-provider-status` table, or the table `providers.collection.status` names. Nothing else in the schema changes.

Until it runs, reads, saves and deletes of provider documents go on: a connection check fails, no status is written or cleared, and under a `fallback` policy no source counts as failing, with a warning logged once a minute.

## PostHog's Region

A PostHog provider document with a blank **Host** now reads from its Region's cloud (`https://<region>.posthog.com`), where it used to read from US Cloud whatever the Region said. A document on EU Cloud that was refused with a 403 reads again as it is stored: nothing to migrate, and its key is kept.

A document with a blank Host also needs a Region now. One saved without it keeps reading from US Cloud, and saves again once a Region is picked.

## Failing sources under `fallback`

Under `sources.<id>.tenants: 'fallback'`, a tenant whose own sources all fail reads the shared source again, where one failing document used to cost it every number. A document is failing while its last result is a refusal, or a vendor that did not answer while its reads rest. The shared source is listed beside the failing ones, opens as the default in place of a failing one, and the view and the providers list say why (`notice: 'ownSourceFailing'`). See [Letting tenants read a shared source](/analytics/multi-tenancy#fallback).

A save that changes how a document connects clears its result, and a document failing for more than 10 minutes is checked again in the background, so a source that works again takes its tenant back by itself.

## Connection status

A provider document's sidebar shows its connection: works, refused or unreachable, when it last worked and failed, and the vendor's own answer, with a **Test connection** button for readers who may edit it ([Checking a connection](/analytics/providers#checking-a-connection)). Code reads the same through `GET /api/_x/provider-status?id=`, and `POST` checks the connection first ([Provider status endpoint](/analytics/reference/endpoints#provider-status-endpoint)).
