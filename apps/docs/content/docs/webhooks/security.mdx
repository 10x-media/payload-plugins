The plugin's security posture is simple to state: **admin access is the trust boundary**. Everything below follows from it.

## Operator-supplied URLs (SSRF)

Deliveries POST to whatever URL a subscription specifies, including private and internal hosts. That is the feature working as designed for trusted admins, and an SSRF vector if your admins are not fully trusted. In that case:

- restrict outbound egress from the Payload host at the network layer, or
- front receivers with an allowlist, or
- drop admin-managed subscriptions entirely and use only [code subscriptions](/webhooks/subscriptions#code-subscriptions), whose URLs live in your repository and environment.

## Access defaults

- Both collections require a logged-in user for every permitted operation; delivery rows additionally refuse create and update from any user (server-only writes).
- **Rotate secret** runs the subscriptions collection's configured `update` access for the target document. Overriding that access, including scoping it per tenant, governs the endpoint as well, so rotation cannot outlive the rule that guards ordinary writes.
- **Redeliver** authorizes by login only: any authenticated user may redeliver any delivery. It cannot defer to the deliveries collection's access the way rotation does, because that collection denies create and update to everyone by design. Gate it at the network or reverse-proxy layer if that matters to you.

Tighten either with your own access control by overriding the collections through standard Payload config if you need role-based rules.

## Secrets at rest

Signing secrets are encrypted before they reach the database, using Payload's own `encrypt`, whose key derives from your `PAYLOAD_SECRET`. A database dump, a backup, or a read replica contains ciphertext rather than usable signing keys.

Reads stay masked. The plaintext leaves the server on exactly two paths:

- the create response and the rotation response, each revealing the new secret once
- internal delivery signing, which decrypts in memory to compute the HMAC

Everything else, admin, REST, GraphQL, exports, sees `__redacted__`.

### What this does and does not protect

Encryption at rest defends against **read** exposure of the database: dumps, backups, replicas, a stolen disk.

It is not a defence against an attacker who can **write** to your database. Such an attacker can already point a subscription at their own URL and receive your events. They can also copy one subscription's encrypted secret into another row, since the ciphertext is not bound to the row it sits in, and so receive deliveries signed with a secret they cannot read. If your database is writable by an untrusted party, the webhook secrets are not the first thing to worry about, and encryption at rest does not change that.

The cipher (`aes-256-ctr`) carries no authentication tag. A decrypt that does not yield a well-formed `whsec_` secret is treated as a failure, and the delivery is **refused**: the row is marked `dead` with `signing secret could not be decrypted`, an error is logged, and nothing is sent.

<Callout type="warn">
A subscription that is supposed to be signed is never downgraded to an unsigned delivery. Receivers commonly verify only when a signature header is present, so an unsigned POST would sail through that check. A refused delivery is a visible failure you can act on; a silently unsigned one is not.
</Callout>

That refusal is about the **current** secret. If only a retired secret inside an open [rotation window](/webhooks/signing#rotation) is unreadable, the delivery still goes out signed with the current secret and a warning names what was dropped: a correctly signed delivery beats no delivery, and the only loss is the overlap for receivers that have not switched over yet.

This applies to subscriptions that predate encryption at rest, too: until [migrated](#migrating-subscriptions-created-before-encryption) or rotated, their deliveries fail rather than going out unsigned. Subscriptions with no secret at all are unaffected and continue to deliver unsigned, which is what they always did.

## PAYLOAD_SECRET and stored secrets

Because the encryption key derives from `PAYLOAD_SECRET`, **changing `PAYLOAD_SECRET` makes every stored webhook secret unreadable.** Deliveries for those subscriptions then fail, marked `dead` with an error logged for each, rather than being sent unsigned.

`PAYLOAD_SECRET` also keys other Payload internals, so this is not a webhooks-specific hazard, but webhook signing fails loudly and is easy to miss in staging.

To change `PAYLOAD_SECRET` safely, decrypt before the switch and re-encrypt after. Capture **both** secret fields: a subscription in an open [rotation grace period](/webhooks/signing#rotation) has a retired secret encrypted under the old key too, and restoring only the current one leaves receivers that have not switched over failing for the rest of the window.

1. **Before changing it**, record the current plaintext secrets while the old key still works:

   ```ts
   const subs = await payload.find({
     collection: 'webhook-subscriptions',
     limit: 0,
     overrideAccess: true,
     context: { webhooksRevealSecretForSigning: true },
   })
   // secret and previousSecret are both plaintext here; store them somewhere safe, briefly
   const recorded = subs.docs.map((doc) => ({
     id: doc.id,
     secret: doc.secret,
     previousSecret: doc.previousSecret,
     previousSecretExpiresAt: doc.previousSecretExpiresAt,
   }))
   ```

2. Change `PAYLOAD_SECRET` and restart.

3. **After the switch**, write each secret back. The `beforeChange` hook re-encrypts under the new key:

   ```ts
   for (const row of recorded) {
     await payload.update({
       collection: 'webhook-subscriptions',
       id: row.id,
       data: {
         secret: row.secret,
         // Carry the rotation window across too, or drop both to end it early.
         previousSecret: row.previousSecret ?? null,
         previousSecretExpiresAt: row.previousSecretExpiresAt ?? null,
       },
       overrideAccess: true,
     })
   }
   ```

   Restoring only `secret` still leaves deliveries working, because an unreadable retired secret is dropped rather than failing the delivery. It just ends the rotation overlap early, and logs a warning naming that.

If you did not capture the secrets first, they are gone: [rotate](/webhooks/signing#rotation) each subscription and distribute the new secrets to receivers. Set `graceSeconds: 0` for those, since the old secret is already unusable and there is nothing to overlap with.

## Migrating subscriptions created before encryption

Subscriptions created before this release hold plaintext secrets, and **their deliveries fail until you migrate or rotate them**, because an unmigrated secret cannot be decrypted and a signed subscription is never sent unsigned. Run the adoption utility once, ideally after a dry run:

```ts
import { encryptExistingSecrets } from '@10x-media/webhooks'

const report = await encryptExistingSecrets(payload, { dryRun: true })
// { scanned, migrated, alreadyEncrypted, noSecret, failed: [{ id, field, reason }] }
```

Drop `dryRun` to write. It is idempotent, so re-running is safe.

The utility does not invent new secrets: a legacy 48-character hex secret is already valid base64, so it keeps its characters and gains a `whsec_` prefix. Anything it cannot normalize is reported by row id and field name rather than rewritten; rotate those. A row's other secret field still migrates, so one unusable value does not strand a recoverable one in plaintext, which is why a row can appear in both `migrated` and `failed`.

<Callout type="warn">
Receivers must be updated regardless of this migration. The signature format, the header names, and the key derivation all changed, so an unchanged receiver will reject every delivery. See [Signing](/webhooks/signing).
</Callout>

## Receiver-side checklist

- Prefer an off-the-shelf Standard Webhooks library over hand-rolled verification.
- Verify against the raw body, before any JSON parsing.
- Enforce a timestamp tolerance (300 seconds is the usual choice).
- Accept any of the signatures in the header, so rotation does not break you.
- Compare in constant time, never with `===`.
- Treat `data` as untrusted input; it is whatever the document (or your `transform`) contained.
- Respond quickly and process async. The sender aborts at `timeoutMs` (default 10s) and a slow receiver burns retry attempts.
