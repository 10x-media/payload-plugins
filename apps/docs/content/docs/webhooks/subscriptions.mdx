A webhook fires when three things line up: a collection is opted in for the operation, and at least one enabled subscription listens for the resulting event.

## Opting collections in

```ts title="payload.config.ts"
webhooks({
  collections: {
    posts: true, // shorthand: all three operations
    orders: {
      operations: ['create', 'delete'],
      includePreviousData: true,
      transform: ({ doc, operation }) => ({
        id: doc.id,
        status: doc.status,
        operation,
      }),
    },
  },
})
```

| Field | Type | Description |
|---|---|---|
| `operations` | `('create' \| 'update' \| 'delete')[]` | Which writes emit events. Default: all three. |
| `includePreviousData` | `boolean` | Add a `previousData` key to the body on `update` events. |
| `transform` | `({ doc, previousDoc, operation, req, target }) => unknown` | Reshape or redact before sending. Applied to the body's `data` and, with `includePreviousData`, to `previousData` as well, so redaction covers both. `target` (`'data'` or `'previousData'`) names the slot; on the `previousData` call `doc` is the prior document. |

Events are named `<collection>.<created|updated|deleted>`: a create in `posts` emits `posts.created`. The hooks run `afterChange` and `afterDelete`, so a webhook never blocks or fails the write that caused it.

## Admin-managed subscriptions

The **Webhook Subscriptions** collection (slug `webhook-subscriptions` by default) is where operators register receivers:

- `name`, `url`, and an `enabled` toggle
- `events`: a multi-select of every event the opted-in collections can emit
- `secret`: set on the create form only (generate one or supply your own), then write-only. It is encrypted at rest and stripped from every read; a read carries `secret_set` and `secret_hint` instead. On an existing subscription the **Rotate secret** button is the only way to change it. See [Signing](/webhooks/signing)
- `previousSecretExpiresAt`: set while a rotation grace period is open, when deliveries carry two signatures
- `headers`: extra key/value headers injected on every delivery to this subscription. The names the plugin sets (`webhook-id`, `webhook-timestamp`, `webhook-signature`, `X-Webhook-Event`) are reserved and rejected here
- `description`: free-form notes

All operations on the collection require a logged-in user.

## Code subscriptions

For receivers that belong in code (your own services, environment-dependent URLs), register them on the plugin. No admin record is created:

```ts title="payload.config.ts"
webhooks({
  collections: { orders: true },
  subscriptions: [
    {
      id: 'my-crm',
      url: 'https://crm.example.com/hooks/orders',
      events: ['orders.created', 'orders.updated'],
      secret: process.env.WEBHOOK_SECRET,
      headers: { 'x-source': 'payload' },
    },
  ],
})
```

`CodeSubscription` fields: `id`, `url`, `events`, plus optional `secret`, `headers`, and `enabled` (default on). Code and admin subscriptions are merged at delivery time; each matching subscription gets its own delivery row.

`secret` must be in `whsec_<base64>` form, the same as an admin-managed one. A malformed value fails at startup, naming the subscription, rather than silently producing signatures no receiver can verify. Code subscriptions are not stored, so they are neither encrypted nor rotatable: change the environment variable and redeploy.

## Renaming or hiding the collections

```ts
webhooks({
  collections: { posts: true },
  subscriptionsCollection: { slug: 'endpoints', hidden: false },
  deliveriesLog: { slug: 'endpoint-deliveries', hidden: true },
})
```

`hidden: true` keeps a collection out of the admin nav while it continues to function.

<Callout type="warn">
The subscriptions slug can be renamed freely: the stored secrets are bound to a [pinned scope](/webhooks/security#secrets-at-rest) rather than to the slug, so a rename does not make them unreadable.
</Callout>

## Collection overrides

Both collections take an `overrides` slot, the same shape the other plugins in this family use. Top-level keys spread over the plugin's defaults, `access` and `admin` merge key by key, your hooks append after the plugin's, and `fields` receives the defaults to compose with. The slug is not overridable here (it has its own option, and the plugin wires it into the delivery task and the endpoints before the override runs).

```ts title="payload.config.ts"
webhooks({
  collections: { posts: true },
  subscriptionsCollection: {
    overrides: {
      access: { update: ({ req }) => req.user?.role === 'admin' },
      admin: { group: 'Integrations' },
      fields: ({ defaultFields }) => [...defaultFields, { name: 'tenant', type: 'text' }],
    },
  },
  deliveriesLog: {
    overrides: { admin: { defaultColumns: ['event', 'status', 'createdAt'] } },
  },
})
```

Overriding `access.update` on the subscriptions collection also governs the [rotate-secret endpoint](/webhooks/security#access-defaults), which defers to it.
