title: Embedded views
description: Putting a registered admin view in the panel, and how a lazy item reaches the server.
---

A `view` item mounts a view already registered in `admin.components.views`, with the page props it was written for. It works unchanged, with one exception: a view that wraps itself in `DefaultTemplate` brings the admin sidebar and header with it, and draws them inside the panel.

## How a lazy item reaches the server

A `view` item, and a `component` item marked `lazy`, are rendered when the row is opened rather
than with the page. Two channels can carry that render. They produce the same result and differ
only in what installation costs.

### `lazyTransport: 'widget'`, the default

**Nothing is asked of you.** The plugin registers one internal dashboard widget and renders
through it.

That widget's slug appears in the dashboard's "Add widget" drawer, which readers see only while
editing their dashboard. It is registered only when your config holds a lazy item, so an overlay
of collections and globals never triggers it.

### `lazyTransport: 'server-function'`

No widget is registered at all. In exchange you wire the plugin's own function into the admin's server-function handler yourself. On Next.js that is the root layout:

```ts title="app/(payload)/layout.tsx"
import config from '@payload-config'
import { handleServerFunctions, RootLayout } from '@payloadcms/next/layouts'
import { settingsOverlayServerFunctions } from '@10x-media/settings-overlay/rsc'
import type { ServerFunctionClient } from 'payload'

import { importMap } from './admin/importMap.js'

const serverFunction: ServerFunctionClient = async (args) => {
  'use server'
  return handleServerFunctions({
    ...args,
    config,
    importMap,
    serverFunctions: settingsOverlayServerFunctions,
  })
}
```

On TanStack Start it is the server function file next to the import map:

```ts title="src/app/_payload/server.functions.ts"
import { settingsOverlayServerFunctions } from '@10x-media/settings-overlay/rsc'

const runPayloadServerFn = createServerFn({ method: 'POST' })
  .validator((args: ServerFunctionClientArgs): ServerFunctionClientArgs => args)
  .handler(async ({ data }) => {
    const { handleServerFunctions } = await import('@payloadcms/tanstack-start/server')
    return handleServerFunctions({
      args: data.args,
      config: await getConfig(),
      importMap: await getImportMap(),
      name: data.name,
      serverFunctions: settingsOverlayServerFunctions,
    })
  })
```

```ts title="payload.config.ts"
settingsOverlay({ lazyTransport: 'server-function', overlays: [...] })
```

Payload generates both files and marks them as its own, so this one is opt in.

Forget the wiring and the panel says so in as many words, naming both the fix and the way back.

### Choosing

Take the default unless a stray row in the dashboard's widget drawer bothers you more than an
edit to a generated file. If no overlay holds a lazy item, neither is used: nothing is registered
and nothing is called.

## Your own view

Read the `settingsOverlayEmbed` prop and skip the template:

```tsx title="views/AuditView.tsx"
import { DefaultTemplate } from '@payloadcms/ui/rsc'
import { Gutter } from '@payloadcms/ui'
import type { SettingsOverlayEmbedServer } from '@10x-media/settings-overlay/types'
import type { AdminViewServerProps } from 'payload'

type Props = AdminViewServerProps & {
  settingsOverlayEmbed?: SettingsOverlayEmbedServer
}

export const AuditView = ({ initPageResult, params, searchParams, settingsOverlayEmbed }: Props) => {
  const body = <AuditTable />

  if (settingsOverlayEmbed) {
    return <div className="audit-view--embedded">{body}</div>
  }

  return (
    <DefaultTemplate
      i18n={initPageResult.req.i18n}
      locale={initPageResult.locale}
      params={params}
      payload={initPageResult.req.payload}
      permissions={initPageResult.permissions}
      searchParams={searchParams}
      user={initPageResult.req.user ?? undefined}
      visibleEntities={initPageResult.visibleEntities}
    >
      <Gutter>{body}</Gutter>
    </DefaultTemplate>
  )
}
```

The prop is present only inside a panel. A hook would not do here: the view is a server component, and it needs the answer before it renders.

## Somebody else's view

A view from another plugin cannot be asked to read the prop. Until its author adds that check, it draws its sidebar and header inside the panel.

**Symptoms:** the panel opens with a second sidebar inside it, or a second admin header above the content. The plugin cannot detect this and will not warn about it.

Use a `link` item for such a view, which opens it as the page it was written to be, or ask its author to read `settingsOverlayEmbed`.
