## What is blocked

On every collection and global in scope, while a window is active:

| Operation | Collections | Globals |
|---|---|---|
| create | blocked | |
| update, including bulk updates | blocked | blocked |
| delete, including bulk deletes | blocked | |
| autosave and version restore | blocked | blocked |
| find, count, read | allowed | allowed |

This applies on every channel: REST, GraphQL, the admin, custom endpoints, and the Local API **with `overrideAccess: true`**. No option, role or user bypasses it; only server code running inside `withoutContentLock` does (see [Maintenance code](#maintenance-code)). Bulk operations are rejected as a whole.

Logins, token refresh, logout and password resets keep working.

## What clients receive

A blocked write throws `ContentLockedError`, an `APIError` with status `503`:

```json
{
  "errors": [{
    "message": "Content is locked for maintenance. Please try again later.",
    "data": { "endsAt": "2026-01-10T13:00:00.000Z", "lockIds": ["..."] }
  }]
}
```

- `endsAt` is the latest known end of the active windows, or `null` when any of them ends manually.
- The response carries `Retry-After`: 3600 seconds by default, or the seconds until the known end with `retryAfter: 'untilEnd'`. GraphQL errors carry it too, with `extensions.statusCode: 503`.
- The message is translated to the request's language.
- The error logs at `info`, not as a server fault.

In server code, check with `isContentLockedError(error)`.

## The admin

During a lock, `create`, `update` and `delete` access is denied in scope, so the admin renders documents read-only and hides the buttons that would fail. Outside a lock and out of scope, your access functions apply unchanged. Read access is never touched.

<Screenshot src="/images/content-lock/locked-document.webp" width={720} alt="A product during a lock on the catalog: the banner on top, the fields read-only, no save buttons" />

A page opened before the lock started still shows editable fields until it refreshes; saving it answers with the 503 toast. The banner refreshes the page when a window it shows changes stage.

## Checking the lock in server code

```ts
import { getContentLockState, isContentLocked } from '@10x-media/content-lock'

if (await isContentLocked(payload, { collection: 'products' })) {
  return // skip, or postpone the work
}
// also { global: 'header' }, or { custom: 'crm-sync' } for a custom target

const state = await getContentLockState(payload)
// { locked, scope, endsAt, active, announced, resolvedAt }
```

Code that must not start work a lock would stop halfway asserts instead: `assertContentUnlocked` throws the lock's own `ContentLockedError`, so a job treats it like a blocked write and defers or fails per its [interruption policy](/content-lock/jobs), before it has paid for anything.

```ts
import { assertContentUnlocked } from '@10x-media/content-lock'

// inside a task handler
await assertContentUnlocked(req, { collection: 'products' })
const body = await translate(input.body) // only paid for while products is writable
await req.payload.update({ collection: 'products', id: input.id, data: { body }, req })
```

In custom admin components, `useContentLock()` from `@10x-media/content-lock/client` returns `{ state, locked, isLocked(entity), endsAt, activeWindow }`. Exempt collections and globals never count as locked, in either.

## Timing

A lock that starts or ends reaches every server within a few seconds. If the lock state cannot be read, writes are rejected until it can.

## Maintenance code

A lock keeps editors, integrations and jobs out while you change the content yourself: a migration, an import, a restore. Run that code inside `withoutContentLock` so its own writes go through:

```ts
import { withoutContentLock } from '@10x-media/content-lock'

await withoutContentLock(async () => {
  await payload.update({
    collection: 'products',
    where: { legacySku: { exists: true } },
    data: { legacySku: null },
  })
})
```

- Everything the callback runs is covered: nested Local API calls, the hooks they fire and the writes those make, and work it starts and leaves running.
- Requests handled at the same time stay locked. Only the callback's own async chain is let through.
- The lock itself stays in place: the banner, `isContentLocked`, `getContentLockState` and paused queues report it as before.
- Keep it to trusted maintenance code. Never wrap a request handler, a custom endpoint or a job run in it.

## Limits

- Writes through `payload.db.*` or the raw database driver are not blocked. Code that writes this way should check `isContentLocked` itself.
- Frontend writes to collections in scope get the same 503. List them in `exempt` if they must keep working.
