---
title: Measurement field
description: A number field that stores one canonical unit and lets every viewer edit and read in their own.
---

```ts
import { measurementField, presets } from '@10x-media/fields/measurement'

measurementField({
  ...presets.bodyWeight,        // storageUnit, units, preferenceKey, name, localeDefaults for this preset
  fallbackUnit: 'lb',           // display fallback with no saved viewer preference, ahead of locale detection
  units: ['kg', 'lb'],          // narrow the preset's offered units; still dimension-constrained
  precision: { lb: 1 },         // per-unit display fraction digits, overriding the engine defaults
  min: 20,                      // bounds in the storage unit, enforced by Payload's native number validation
  max: 300,
  label: 'Body weight',
  required: true,
  localized: false,
  index: false,
  overrides: ({ field }) => field,
})
```

Eight presets ship built in: `bodyWeight` (kg, lb, st-lb), `personHeight` (cm, m, in, ft-in), `distance` (m, km, mi), `mass` (g, kg, oz, lb), `length` (mm, cm, m, km, in, ft, yd, mi), `volume` (ml, l, fl-oz, gal), `temperature` (c, f), `speed` (km/h, mph, m/s). Spread one into `measurementField()` and override whatever the field needs; every option after the spread narrows to the preset's dimension, so TypeScript rejects a unit from the wrong family.

## Free-form fields

There is no `usage` gate: any field can declare `storageUnit` and `units` directly, and units are constrained only by dimension, not by a fixed catalog.

```ts
measurementField({
  storageUnit: 'mm',
  units: ['in', 'ft-in'],
  preferenceKey: 'cutout',
})
```

`storageUnit` still has to be a scalar unit; `units` still has to share its dimension. Everything else is inferred: `name` defaults to `preferenceKey`, and `units` defaults to every built-in unit of the storage unit's dimension when omitted.

## Preference buckets

The display unit a viewer picks is stored under a bucket key (`preferenceKey`), not per field: every field sharing a key flips together. Three ways a field lands in a bucket:

- Spreading a shipped preset carries its `preferenceKey` (`bodyWeight`, `personHeight`, `distance`, `mass`, `length`, `volume`, `temperature`, `speed`), the same eight keys v1 used, so saved preferences keep resolving.
- A free-form field with no `preferenceKey` defaults to its storage unit's dimension name (`mass`, `length`, `volume`, `temperature`, `speed`). This deliberately shares a bucket with the generic `mass`/`length` presets, which use the same default.
- Passing `preferenceKey` explicitly overrides either default, for a field that should share a bucket with something else or stay isolated from one.

## Display unit resolution

Display unit resolves in this order, skipping any candidate the field doesn't offer in `units`:

1. The viewer's saved preference for the field's `preferenceKey`.
2. The field's own `fallbackUnit`.
3. The plugin's `fields({ measurement: { defaultUnits } })` for that `preferenceKey`.
4. The field's `localeDefaults[system]`, where `system` is `'metric'`, `'us'`, or `'uk'`, derived from the browser's language (US and Liberia get US, Great Britain and Myanmar get UK, everyone else metric).
5. The per-dimension `DIMENSION_LOCALE_DEFAULTS[dimension][system]` table, covering the five built-in dimensions. A custom dimension has no entry here.
6. The field's first configured unit, as the final floor.

Setting `fallbackUnit` (or `defaultUnits` for a bucket in the plugin) is an explicit choice that outranks locale detection. Leave both unset on most fields so a UK visitor sees stone and pounds without any config; the shipped presets already carry the right `localeDefaults` for that (step 4 wins before the generic dimension table in step 5).

Preference persistence and the same-bucket flip are wired by the `fields()` plugin, which registers the unit preference provider. Standalone `measurementField()` still works, but a unit picked without the plugin lasts only for that field until the page reloads, and its list cells skip locale detection entirely: they fall back through the field's `fallbackUnit` (step 2), then straight to its first configured unit (step 6), never reaching steps 4 or 5.

## What's stored

The field is a plain `number` column holding a canonical value in `storageUnit`, so it sorts, filters, and groups like any other number and needs no custom query logic. To adopt on an existing numeric column, set `storageUnit` to whatever unit that column already holds: no migration, no data rewrite. Storage is rounded to 6 fraction digits regardless of display precision, and non-numeric or NaN writes are rejected server-side on every database adapter. The field stores a single number; `hasMany` is not supported.

The factory also stamps its resolved config onto `field.custom['@10x-media/fields']`, so tooling and a second app reading the same collection can discover `storageUnit`, `units`, and `preferenceKey` without re-declaring the field. Two apps sharing a database must still declare the same `storageUnit` themselves: the field only round-trips whatever is on disk, it does not reconcile a mismatch between apps.

## Faithful drafts

The editable input always shows what's actually stored, not a rounded preview of it. Switching a field's display unit shows the shortest draft that writes the same stored value back: display precision first, then one more fraction digit at a time up to the 6-digit storage precision. A value entered in the current unit always round-trips exactly, since it was never converted. Rounding for display only happens in read-only contexts, list cells and `formatMeasurement`, never in the field the viewer is editing. Each part of a compound value (`ft-in`, `st-lb`) is faithful independently.

## The row and the unit menu

The field row is a constant 40px: a numeric input with the unit adjacent to it, as a clickable chip. With more than one unit in `units`, the chip itself is the trigger: it shows a small caret, highlights on hover, and opens a popup listing every unit (checkmark on the current one). Picking one converts the displayed value in place and calls the same bucket-wide preference update described above; the stored number is unaffected until the next edit. With only one unit configured, or when the field is read-only, the chip renders as a static muted label instead: no caret, no hover state, not clickable, since there's nothing to open. Clicking empty space inside the row focuses whichever input is nearest, the way a native control would.

## Compound entry

`personHeight` and `bodyWeight` include a compound display unit, `ft-in` and `st-lb`: two inputs, major and minor, each with its own unit chip as the trigger for the same popup. Compound units are display-only. Storage is always a single scalar number in `storageUnit`; picking `ft-in` never changes what's on disk, only how the value is split for editing.

## Custom units and dimensions

A field can declare units and dimensions the engine doesn't ship, as plain serializable data:

```ts
measurementField({
  storageUnit: 'km',
  units: ['km', 'mi', 'nmi'],
  preferenceKey: 'sailing',
  custom: {
    units: {
      nmi: { dimension: 'length', factor: 1852, intlUnit: null, shortLabel: 'nmi' },
    },
  },
})
```

`CustomUnitDef` is `{ dimension, factor, offset?, intlUnit, shortLabel, precision? }`: linear (or affine, with `offset`) against the dimension's canonical unit, same as the built-ins. `CustomDimensionDef` is `{ canonicalUnit }`, naming one of `custom.units` with `factor: 1` and no `offset` as that dimension's canonical. Both travel with the field's `clientProps` as plain data, so the client rebuilds the same engine without a bundle of conversion code shipping separately. Custom unit and dimension ids can't collide with a built-in one; the factory throws at config time if they do.

`intlUnit: null` means the unit has no ECMA-402 identifier for `Intl.NumberFormat`'s `style: 'unit'`. Formatting falls back to a plain localized decimal plus `shortLabel` (`"1.5 nmi"` rather than an `Intl`-rendered unit string), and the unit picker's long label falls back to `shortLabel` too.

Compound units (`ft-in`, `st-lb`) are always built-in: custom units are scalar-only. A field can still store in a custom unit and display a compound one, or the reverse; the engine bridges through the compound's built-in major unit, converting your custom storage value into it before splitting into major/minor. The nautical-mile example above works the same way if you add `'ft-in'` to `units`.

This is new: pairing errors (a `dimension` referencing nothing built-in or declared, an id colliding with a built-in) throw immediately at field-definition time with the field's name in the message, rather than failing silently at runtime. Reciprocal unit kinds and a client-supplied conversion function are not supported yet; both are documented future work.

## Options

| Option | Default | Notes |
|---|---|---|
| `storageUnit` | required (or from a spread preset) | Unit the number is stored in. Must be a scalar unit. Match existing data to adopt with zero migration. |
| `units` | every built-in unit of the storage unit's dimension | Offered in the unit picker; narrows to the dimension when `storageUnit` is a literal. The first entry is the final display fallback when nothing else resolves. |
| `preferenceKey` | shipped presets carry their own; free-form defaults to the dimension name | Preference bucket shared with every field using the same key. |
| `name` | `preferenceKey` (presets also carry their own) | |
| `fallbackUnit` | none | Field-level display fallback, ahead of the plugin and locale defaults. Must be in `units`. |
| `localeDefaults` | none | `Partial<Record<'metric' \| 'us' \| 'uk', UnitId>>`, ahead of the per-dimension table. |
| `precision` | engine defaults per unit | `Partial<Record<UnitId, number>>`, overriding individual units' display fraction digits. Integers 0 to 100; the factory throws otherwise. For compound units, key the compound id (`'ft-in'`), which controls the minor part's digits. |
| `custom` | none | `{ units?, dimensions? }`, serializable custom unit/dimension definitions; see above. |
| `min` / `max` | none | Bounds in the storage unit, enforced by Payload's native number validation. The edit view converts the message to the display unit. |
| `overrides` | none | `({ field }) => field` escape hatch with explicit spreads. |

## Limitations

- The list view's filter input operates in storage units. Payload passes custom `Filter` components no props at all, so there is no viewer, locale, or preference to convert against; filtering "under 150" on a `personHeight` field filters on centimeters even for a viewer displaying feet and inches.
- `fields({ measurement: { defaultUnits } })` reaches the edit view (resolved per request, server-side) but not the list view's cell, which falls back to the viewer's preference, then the field's own `fallbackUnit`, then locale detection.
- The field stores a single number; `hasMany` is not supported.
- Reciprocal conversions (value inverts rather than scales, e.g. frequency/period) and a client-supplied conversion function are not supported by `custom`. Both are future work; today's custom units are linear or affine only.

## Frontend use

The stored value is a plain number in `storageUnit`; convert and format it for your frontend with [`/measurement/utils`](/fields/measurement/utils), the same engine the field runs.
