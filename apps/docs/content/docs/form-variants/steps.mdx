## Field steps

A field step renders the listed paths with Payload's own field rendering against the form state. A field that carries custom components gets them. Fields not listed on any step stay in form state with their values and are submitted with the document.

On a forward move, only the current step's paths are validated (server-side, nested paths included). Invalid fields show their errors and the move is refused. Payload's `submitted` flag is form-wide and is not reset, so after the first refused move any invalid field shows its error as soon as it appears on screen.

If the save itself returns an error for a field on no step, Payload shows it as a toast. The plugin does not check at config time that required fields are covered, because a component step may cover them.

## Layout

A step lists fields in one column by default. Three containers give it a shape: `row`, `collapsible` and `group`. They nest freely and may hold component items too.

```ts
fields: [
  { type: 'row', fields: ['firstName', 'lastName'] },
  {
    type: 'row',
    fields: [
      { path: 'title', admin: { width: '70%' } },
      { path: 'status', admin: { width: '30%' } },
    ],
  },
  {
    type: 'group',
    label: 'Reaching them',
    fields: [{ type: 'row', fields: ['email', 'phone'] }, 'address.city'],
  },
  {
    type: 'collapsible',
    label: 'Rarely needed',
    initCollapsed: true,
    fields: ['notes'],
  },
]
```

| Container | Properties |
|---|---|
| `row` | `fields` |
| `collapsible` | `label` (required), `initCollapsed`, `fields` |
| `group` | `label`, `description`, `fields` |

These are the step's containers, not the collection's. They carry no name and contribute no path, exactly as Payload's own `row`, `collapsible` and unnamed `group` do, and the collection's own containers are unaffected: a field keeps the path, condition, validation and custom components it has on the native form wherever a step puts it. So a step can put fields that sit in different tabs of the collection side by side in one row, and a field from the sidebar next to one from the main column.

Each field inside is still rendered on its own rather than handed to Payload's container fields, which would push a schema path segment of their own onto everything inside.

Payload's own containers are not reproduced by the plugin. Listing `firstName` and `lastName` out of a collection row gives two stacked fields; put them in a step `row` to get the row back.

### Width

`admin.width` on a field item is Payload's own `admin.width`: any CSS length, and it sizes the field inside a `row`. Fields without one share what the sized ones leave. Widths in a row add up to the row, so `70%` and `30%` sit on one line; the gap between them is taken out of the widths rather than added to them, as on the native form. Below Payload's mid breakpoint a row stacks and widths are ignored.

Outside a row `admin.width` does nothing, as on the native form.

### Not containers

`tabs` inside a step and `admin.position: 'sidebar'` are not supported. A step has one column, and a tab strip inside a step of a variant whose steps are already tabs is a question of design rather than of plumbing.

## Component steps

A component step is a Payload component rendered on the server with `{ collection, variant, step }` as props. A server component is a static frame rendered once at page load; anything live inside it is a client child reading the hooks below. The same holds for slots.

```tsx title="components/DuplicateCheckStep.tsx"
'use client'

import { useWizard, useWizardState } from '@10x-media/form-variants/client'
import { useFormFields } from '@payloadcms/ui'

export const DuplicateCheckStep = () => {
  const { back, finish, save } = useWizard()
  const [checked, setChecked] = useWizardState<boolean>('duplicateCheckPassed')
  const lastName = useFormFields(([fields]) => fields.lastName?.value)
  // search, then either save() or finish({ title: 'Request sent' })
}
```

## Conditions

A step's `condition` runs on the server with the current values and wizard state. It is evaluated at page render against the saved document, on every step change, and again after each edit the form settles on, so a step appears or disappears as soon as the field its condition reads changes rather than at the next move. On a new document the first render has empty values, so a condition that depends on them is false until the first edit.

The step the user is on is the one exception: it stays on screen even when its condition turns false under them, so that typing cannot move them off the step they are filling in. It goes away on the next move.

Re-evaluation rides on Payload's own `onChange`, which is debounced and fires only when form state really changed, so it is one request per settled edit. What that request costs depends on whether the document exists yet:

| | Reads per call |
|---|---|
| Create, no document yet | none |
| Existing document | 2 |
| Existing document, drafts enabled | 3 |

On create, the permission check runs without fetching, there is no document to load and `hasPublishedDoc` answers `false` outright, so re-evaluation reads nothing at all. On a saved document it is the permission check's own fetch plus the document the endpoint loads with access enforced, and on a drafts collection one more for the published version. Guided variants are meant for creating a document, where this is free; a `save: 'always'` sections variant with conditions pays the reads above while it is edited.

## Gates

A `gate` runs on the server when the user leaves the step forwards, after the step's validation passed. It answers one of:

| Result | Effect |
|---|---|
| `{ result: 'continue' }` | Move on |
| `{ result: 'block', message }` | Stay, show the message |
| `{ result: 'patch', values?, state? }` | Apply, then move on |

`patch.values` replaces the value at each given path without deep merging. Paths are not limited to the current step: setting a field that is on no step (a value derived from a lookup) is a reason to have a gate. An `array` or `blocks` field is replaced whole, which rebuilds the form state from the server. `patch.state` shallow-merges into wizard state.

Anything richer (show the matches, offer a request to admins) is a component step.

## Wizard state

A JSON object scoped to the document page or drawer, shared by the steps and never saved to the document. It survives switching variants; a reload or a locale change clears it. Steps must work with it empty. It is sent to the evaluate endpoint with every call, so server logic sees it, and must not treat it as proof of anything: `duplicateCheckPassed: true` in wizard state guarantees nothing.

## The hooks

From `@10x-media/form-variants/client`:

| Hook | Gives |
|---|---|
| `useWizard()` | `step`, `steps`, `index`, `count`, `isFirst`, `isLast`, `next()`, `back()`, `goTo(key)`, `save()`, `finish(outcome)`, `blockSave(reason)` / `allowSave()`, `saveAllowed`, `saveBlockedReason`, `onBeforeNext(fn)`, `busy`, `error`, `readOnly` |
| `useWizardState<T>(key)` | `[value, setValue]` over one key of wizard state |
| `useOutcome()` | The data `finish()` or an `outcome` after-save action left behind |
| `useFormVariants()` | `active`, `available`, `switchTo(key)`, `inDrawer` |
| Payload's `useForm`, `useField`, `useFormFields`, `useDocumentInfo` | The form and the document, unchanged |

`finish(outcome)` ends the wizard without a native save and shows the `Outcome` slot. `onBeforeNext` is the client-side counterpart of `gate`; returning `false` refuses the move.

## Read-only documents

When the document is locked by another user or otherwise read-only, the runner is read-only too: Back and Next still move between steps so the document can be read, no validation runs, the evaluate endpoint is not called, and saving is disabled.
